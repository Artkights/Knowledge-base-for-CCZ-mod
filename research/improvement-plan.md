# 知识库与 data 管理器改进方案

本方案依据 2026-10-28 的分支整合、6.4 洗隋样本补证、6.5/6.6 data 管理器资料审阅和来源冻结结果制定。知识库层面的项目已经落地；后续项目按证据门禁推进，不能因为工具能够解析某个字节就自动授予写回权限。

## P0：保持事实源可复核

1. 继续把 `data/` JSON 作为唯一事实源，把 `reference/` 和 `index.json` 作为确定性生成物。每次新增或合并实体都运行 `build_reference.py --check`、`build_index.py --check`、`validate_kb.py` 和 `query_smoke.py`。
2. 新来源先登记原始路径、原始 SHA-256、来源类型和可用性。可发布的小型文本证据放入 `sources/evidence/` 并记录快照哈希；EXE、DLL、游戏基底和发布包只保留身份与提取结论。来源快照的派生、脱敏或不可复核限制写进 `verification.reason`。
3. 版本差异始终通过 Profile、Variant、物理表、Codec、能力和消费者表达。6.4、6.5、6.5pl、6.6 不共享固定地址；6.5pl 在独立画像完成前继续保持研究域。

完成判据：干净克隆可离线验证所有来源快照、实体关系、索引哈希和生成物；查询指定版本时不会返回其它版本的固定地址。

## P1：补齐消费者证据和写回门禁

1. 对 6.4 洗隋以表为单位补齐独立消费者：人物 32 字节、兵种 80×35、撤退台词、特殊暴击映射、R/S 指定和策略地形。每张表分别记录物理可写性、玩法语义确认程度和管理器实现状态，失败时执行 `Preserve/ReadOnly`。
2. 对 F36 与其它 6.6 构建继续拆分磁盘物理布局、运行时解码和消费者语义。任何共享 N、selector、255 哨兵或复合绑定都记录影响范围、原始字节、写入前提和冲突关系。
3. 将 CSV/XLSX 交换、事务写回、撤回重做和跨版本迁移的契约扩展到每个可编辑表。迁移按 `TableKey/ID/逻辑字段/目标 Codec` 进行；画像、修订或字段策略不匹配时拒绝导入并保留原始草稿。

完成判据：每个可写字段都有目标样本 SHA、边界、Codec、消费者引用、expected bytes 或等价的事务前置条件；缺一项只能查询，不能自动写回。

## P1：建立 6.5pl 独立画像队列

先取得 6.5pl EXE、Data/Star/Imsg 等配套文件的完整 SHA-256，再定位 PE 映射、表计数/步长和函数 ABI。随后用同一组静态探针、消费者追踪和最小游戏内回归构成画像。完成前只允许研究条目和版本隔离查询，不复制 6.5 或 6.6 地址。

完成判据：至少一个固定提交或仓库内快照可复核，Profile 与所有地址绑定，关键表有边界样本和消费者证据，动态验收结果与静态结论分开记录。

## P2：改进 data 管理器实现

1. 从统一版本配置生成 Profile/Variant/Codec 能力矩阵，在 UI 中同时显示“物理字段可写”“玩法语义已确认”“当前构建已实现”三个状态。
2. 导入器先执行样本指纹、表边界、编码和消费者门禁，再创建事务草稿；写入前显示受共享 N 或复合绑定影响的行，写后按目标 Codec 复读并比较未编辑字节。
3. 对失败路径加入原始文件 SHA、事务日志、回滚结果和可复现报告。发布包验证保持只读，禁止通过旧报告或旧版本地址证明当前构建。
4. 将结构化事实、验证报告和运行时验收分开保存，使管理器业务代码的改造可以独立于知识库审阅和发布。

完成判据：任何编辑操作都能生成输入样本、Profile、Codec、门禁、变更字节、复读结果和回滚结果；没有画像或证据时界面只提供查看与导出。

## P2：持续验证与研究队列

CI 继续执行确定性生成、结构/来源校验、版本边界查询和 `git diff --check`。研究队列中的每条缺口补充“已知事实、缺失证据、优先级、完成判据和禁止自动写回条件”；历史工具测试保留实际验证层级，不改写成当前运行结果。每次新分支合并都生成逐实体处置回执，说明保留、合并、拆分、降级或排除原因。
