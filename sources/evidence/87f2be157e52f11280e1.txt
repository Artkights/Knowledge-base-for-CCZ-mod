# 人物 R/S 形象保存后自动同步存档

日期：2026-10-23。交付版本：1.2026.1023.3。此功能默认启用，沿用管理器的离线编辑方式。

## 问题原因与基底证据

人物 R/S 指定不只存在于 Ekd5.exe。游戏保存时，把运行时地址 `0x501000` 起的 `0x30000` 字节写入 `.E5S` 首段；读档时又恢复到同一片内存，其中包含人物 S、R 两张指定表。因此，修改 EXE 后开新游戏可以使用新指定，但读取修改前的存档，会恢复旧指定。这解释了管理器预览正确、进游戏读旧档却不匹配的现象。

洗隋 6.4、加强版 6.5、复刻版 6.6 山贼、V10.1 的当前引擎均核验了这一关系。两张表各有 1024 个小端 UInt16 值：

| 字段 | 这些样本中的 EXE 文件位置 | E5S 文件位置 |
|---|---|---|
| S 指定 | `0xD2800 + 人物ID × 2` | `0 + 人物ID × 2` |
| R 指定 | `0xE1000 + 人物ID × 2` | `0xE800 + 人物ID × 2` |

真实样本中，加强版 6.5 的人物 ID 0 在 EXE 中 S=1，而 `SV004.E5S` 中 S=249；ID 1 分别为 2、160。6.4 模组样本也存在 EXE R=0、旧档 R=367 的差异。旧的指定器另有更新所有存档的操作，集成管理器原来的数据及图片保存流程没有调用相同功能。

上述偏移用于回归核对，程序不会仅凭版本号和固定偏移写档。每次同步均探测当前 EXE 的 PE 映射、人物 R/S 消费者、首段保存和读取地址、Win32 文件 I/O 调用及场景分支，再由运行时地址差推导档内位置。未知或经过不兼容改造的引擎会报告无法验证并跳过存档同步。

## 使用后的行为

人物页输入 R/S 编号仍先保留为草稿。按顶部保存后，程序将本次实际改变的人物指定同步到相关磁盘存档。只改 R 就只覆盖对应人物的 R，只改 S 就只覆盖 S；同一人物没有改变的字段不参与同步。物理表编辑、批量操作、CSV 和人物工作簿走相同保存入口。

图片替换、动作条导入、参考图导入、像素保存及整包替换仍即时保存。保存 R/S 图片时，程序比较原包和候选包在相同位置的解压后内容，找出实际变化的 R 逻辑编号或 S 物理图号，再读取磁盘上已保存的人物指定及兵种，定位本次关联人物。人物页未保存的草稿不会被用来重写存档，也不会被图片操作清除。

R 的正面或背面任一条目变化均命中该 R。S 汇总移动、攻击、特技三个包的变化，人物紧凑 S1～32 的任一转变化均命中对应人物；S33 起按单转映射；S0 按已保存兵种和对应阵营资源建立关联。写入存档的仍是人物紧凑 S 编号，不是 Unit 的物理图号。

包重建造成目录或压缩偏移变化，但解压后图片内容一致时，不会扩大同步范围。追加无人引用的图片不改存档。删除导致位置前移时，只按变化的位置计算本次影响，仍需自行检查原有资源引用；本次未增加人物引用重排。

迁移时，使用目标临时项目的最终指定和图片差异，在真实目标存档上执行相同同步；源存档不会迁入目标，源项目不被改写。

## 同步范围及格式支持

| 对象 | 处理方式 |
|---|---|
| 当前项目 SV 目录的原生槽位 E5S | 同步本次目标字段；只枚举直接子文件 |
| 当前版本 `patch/xiaoan64、65、66/autosave` | 由同名索引 INI 找到实际自动档；只处理当前版本目录 |
| `SV.E5S`、`SVCMN.E5S` | 索引或公共文件，排除 |
| EXS | 不包含本次原生 R/S 数组，不改写 |
| 备份、临时文件、其他项目、重定向目录 | 不自动写入 |
| 原生内政档 | 验证段头、非战场分支和长度 `0x40650` |
| 原生战场档 | 验证段头、场景类型 3 和长度 `0x43A86` |
| schema 2 内嵌统计 | 验证 `XASTAT2F` 168 字节尾部、统计载荷、原生及统计 SHA；只更新原生段的大写 ASCII SHA |
| schema 1 `.stats` | 验证 `XA66STAT`、记录边界和原档关联；只更新头部的小写 ASCII 全档 SHA |
| 已有索引 INI | 更新 `[Save] Hash`，保留编码、BOM、换行、注释及其余内容；不补建缺失文件 |
| 仅含 `[User] Note` 的普通存档注释 INI | 属于补丁合法输出，原样保留；自动档或已有 `[Save]` 节必须有唯一有效 Hash |
| 未知扩容、未知校验尾、截断、损坏、关联 SHA 不符 | 整个存档组跳过并说明原因 |

原生长度来自当前引擎的分段契约：`0x30000 + 0xD4F0 + 0x313D + 0x23 = 0x40650`；战场再加 `0x4F2 + 250×0x2A + 0x640 = 0x3436`。某些非战场旧档保留了更长的过期尾部，无法按已识别格式验证时也会跳过，不猜测截断或修复。

存档中的其他人物可能因为剧情换装而与 EXE 不同，这不视为损坏，也不做全表统一。即使本次目标人物旧编号超出当前图库容量，也不会仅凭这一点拒绝；同步使用最终已保存的指定值。职业、阵营、等级、装备、战场单位缓存和统计内容均保留原字节。当前引擎读档后的初始化会按人物指定重新加载图片。

## 异常、历史与恢复

一份 E5S 与它必须随同更新的统计及索引组成一组。准备时检查原始 SHA 和格式；提交前再次检查整组；写后逐字节复读。准备失败跳过该组，写入中失败则先恢复本组已经改写的成员，再继续其余组。文件占用、外部改写、统计损坏都不会使普通坏档阻断主形象保存。

结果报告“已更新、已一致、已跳过”的存档数量及具体文件原因。有跳过或无法完成准备的警告时，界面显示部分同步状态，可在保存诊断或历史详情查看原因，不把部分结果显示为全部完成。

成功组和本次主数据或图片进入同一操作历史。数据保存的一次撤回/重做、图片历史恢复以及迁移历史会同时恢复成功组；跳过的文件不记作已修改。资源迁移涉及新增文件时，历史同时记录原本不存在这一状态，撤回删除本次新文件，重做重新创建。

如果主文件、图片事务或历史持久化等全局步骤失败，则恢复本次已经成功同步的组。恢复前仍检查原始和候选 SHA；文件又被外部程序修改时，保留外部内容并明确报告冲突，持久化未恢复快照供排查。不要在游戏运行或另一个编辑器同时写档时操作；此程序不会修改游戏进程内存。

## 实现入口

- Core 的 `Appearance` 目录提供统一请求、布局验证后的存档准备、分组提交、回滚及格式校验。
- `ProjectWorkspace.SaveCore` 从实际保存的 `person-r-assign` / `person-s-assign` 变更提取最终值。
- `ProjectImageHistory.Commit` 接入图片影响分析与存档贡献，覆盖集成图库和资源适配器的提交路径。
- `MigrationCommitCoordinator` 将目标最终值及资源影响合并，同步真实目标存档并记录迁移备份和历史。
