## 六、★★★★★ 加载机制与**字段重排**（2026-10-16 第 15 轮）——对编辑器最关键的一节

### 6.1 ★ 物品是**两张连续的表**，由同一个函数加载

`0x4010B0` 全反汇编：
```asm
004010B0  55              push ebp
004010B1  8B EC           mov  ebp, esp
; ── 第一张：Data.e5 段 #1 ──
004010B3  68 20 F8 49 00  push 49F820h        ; ★ 目标表
004010B8  6A 01           push 1              ; 段号 1
004010BA  68 60 BB 48 00  push 48BB60h        ; "DATA.E5"
004010BF  E8 6F A4 01 00  call 0041B533       ; Ls12 段加载
; ── 第二张：star.e5（裸表，专用加载器）──
004010C4  B9 48 02 4A 00  mov  ecx, 4A0248h    ; ★ 目标表（紧邻第一张之后）
004010C9  BA 30 C5 48 00  mov  edx, 48C530h    ; "star.e5"
004010CE  E8 40 02 05 00  call 00451313       ; ★ 裸表加载器
; ── ★★★ 字段重排循环 ──
004010DA  8B 4D F8        mov  ecx, [ebp-8]
004010DD  3B 4D FC        cmp  ecx, [ebp-4]
004010E0  73 1B           jae  004010FD
004010E2  E8 DB 26 08 00  call 004837C2       ; 取记录指针（ecx）
004010E7  C6 41 0E 00     mov  byte [ecx+0Eh], 0        ; ★ 名字第 15 字节清零
004010EB  8A 51 12        mov  dl, byte [ecx+12h]       ; A = 原 +0x12
004010EE  8B 41 13        mov  eax, dword [ecx+13h]     ; 读 +0x13 起 4 字节
004010F1  66 89 41 12     mov  word [ecx+12h], ax       ; 新 +0x12 = 原 +0x13,+0x14
004010F5  88 51 14        mov  byte [ecx+14h], dl       ; 新 +0x14 = 原 +0x12
004010F8  FF 45 F8        inc  dword [ebp-8]
004010FB  EB DD           jmp  004010DA
004010FD  E8 96 69 02 00  call 00427A98
00401105  C3              ret
```

**★ 两条硬结论**：

| # | 结论 | 证据 |
|---|---|---|
| **①** | **两张表连续**：`0x49F820` ← `Data.e5` 段 #1（2600 B = 104×25，**ID 0~103**）；`0x4A0248` ← `star.e5`（**ID 104 起**）。`0x4A0248 − 0x49F820 = 0xA28 = 2600` **正好是第一张表大小** | 立即数 + 算术 |
| **②** | **文件 → 内存有字段重排**：`+0x0E` 清零（**名字实际 14 字节**）；**`+0x12`/`+0x13`/`+0x14` 三字节轮转**：文件 `[a][b][c]` → 内存 `[b][c][a]` | `mov dl,[ecx+12h]` / `mov word [ecx+12h],ax` / `mov [ecx+14h],dl` |

### 6.2 ★★★★ 实测验证（`Star.e5` 记录 0）

```
文件态:  +0x12 = 91    +0x13 = FF    +0x14 = ED
内存态:  +0x12 = FF    +0x13 = ED    +0x14 = 91
```
**⇒ 重排后 `+0x12` 恒为 `0xFF`（全表皆然）** ⇒ **它是 flag（疑"宝物 / 不可丢弃"标记）** ✓

**⇒ 这解释了"直接读文件字段对不上"** —— 编辑器若不做这步重排，`+0x12~+0x14` 三字节就是错的。

## 八、字段分布统计（可复现的判据）+ 一处库内修正线索（2026-10-16 第 17 轮）

> **方法**：统计各字段的「取值种数」与「`0xFF` 出现次数」，再与**已知基准**（`Data.e5` 段#1，它不被重排 ⇒ 文件态 == 内存态）比对。
> 判据：若某内存字段与基准同型（种数/FF 数相近），则该位语义一致。

### 8.1 基准：`Data.e5` 段#1（104 条，不重排）

| 偏移 | 种数 | FF 数 | 前 5 值 | 判读 |
|---|---:|---:|---|---|
| `+0x11` | 22 | 0 | 21(11), 5(10), 11(9), 1(8), 23(8) | **小值 ⇒ type** ✓ |
| `+0x12` | 62 | **31** | FF(31), 105(3), 95(2), 78(2) | **有 FF ⇒ effect（`FF`=无效果）** ✓ |
| `+0x13` | **4** | **72** | **FF(72)**, 10(11), 30(11), 5(10) | ⚠ 见 8.3 |
| `+0x14` | **95** | 0 | 2(2),3(2),4(2),5(2),205(2) | **多样性高 ⇒ 效果值/参数** |
| `+0x17` | 10 | 0 | 11(30), 12(21), 10(14), 7(10) | 像成长率 |
| `+0x18` | **2** | 0 | 1(73), 0(31) | **flag（仅 0/1）** ✓ |

### 8.2 `Star.e5`（254 条）两种读法

### 8.3 ★ 库内修正线索：段#1 的 `+0x13` 说"price×100"，证据不足

实测段#1 的 `+0x13` **只有 4 种取值**：`FF`(72 条) / `10`(11) / `30`(11) / `5`(10)。
若是"价格×100"，取值种数不可能只有 4 ⇒ **更像"商店价格档 / 可购标记"**。
**⇒ 标为待复核，未擅自改动库内既有页。**

### 8.4 ★ 重排后与基准的对照：**只有 effect 位吻合**

| 内存偏移 | 重排来源 | 种数 / FF 数 | 与基准对照 |
|---|---|---|---|
| **`+0x12`** | 文件 `+0x13` | 18 / **61** | ✅ 与基准 `+0x12`（62 / 31）**同型 ⇒ effect 吻合** |
| `+0x13` | 文件 `+0x14` | 80 / 0 | ❌ 基准是 4 / 72 ⇒ **不吻合** |
| `+0x14` | 文件 `+0x12` | 8 / 0 | ❌ 基准是 95 / 0 ⇒ **不吻合** |

**⇒ 结论**：**"重排使两表内存布局完全一致"的假设只在 `+0x12`（effect）位成立** ✗
