# 界面框架与资源索引（Ekd5.exe）

> 目标样本：`复刻版6.6山贼\Ekd5.exe`
> SHA256 `BE86A64935BFC1314AB2B51D9519E5625435B239756115476F69315C31C3213A`
> 证据类型：**Resource Hacker 权威导出 + .rsrc 二进制解析 + 运行时 Win32 菜单读取**

## 结论速览

- **对话框 41 个**（RT_DIALOG），全部解析出标题/尺寸/控件数/文件偏移，逐控件明细已导出。
- **菜单 6 组 / 命令项 21 条**，含命令 ID 与 GRAYED 状态。
- ✅ **字符串编码 = 标准 UTF-16LE**（2026-10-14 推翻早期错误结论）：
  `确定` 的字节就是 `6E 78 9A 5B`（U+786E 确 + U+5B9A 定）、
  `环境设定` 就是 `AF 73 83 58 BE 8B 9A 5B`；在 exe 中分别命中 7 处 / 3 处。
  **不存在自定义编码，改文本可放心按标准 Unicode DIALOGEX 处理。**
  早期「编码非标准」的错误来自自写解析器的 header 步进 bug（见下）。
- ★ **改界面前必读 2**：控件的显示数据常与生效数据分离。
  例：「环境设定」列表框是**三份** —— 文本表 `0x4BEEC0`、界面源 `0x500FA4+i`、生效/存档源 `0x501A65+i`。
  设计新界面前必须先定位「这个控件的数据源在哪」。

### 2. 资源解析要点（踩坑）

- RVA→文件偏移：`pefile` 常规换算（`s.PointerToRawData + (rva - s.VirtualAddress)`），**不要额外加/减 bias**。
- 资源名是 **ASCII 字节**（`KANKYOU`/`APPMENU`），`pefile` 会按 UTF-16 解成 `AKNKYOU` 之类乱码 → **按 latin1 读**。
- `.rc` 里同时存在 `DIALOG` 与 `DIALOGEX` 两种关键字，正则必须写成 `DIALOG(?:EX)?`；
  且文件首行 BOM 会粘在名字上，需 lstrip 掉 \ufeff。
- 旧工具 `_对话框资源.py` 写死 `bias=-16`，当前 exe 下 **41 个全部解析失败**，已被 `_界面资源索引v2.py` 取代。

## 风险与边界

- **字符串编码未闭环**：资源模板文本非标准 GBK/UTF-16，改文本前必须先反推编码映射，否则写回即乱码。
- 改模板 = 改 `.rsrc` 段 → 动 PE（`SizeOfImage`/校验和），**必须走 `_dsh写锁` + 备份 + 复读**。
- 新增控件要考虑 **ID 冲突**：`1030~1043`（0x406~0x413）、`1235`（0x4D3）、`1488~1489`（0x5D0~0x5D1）已被占用。
- 控件数据显示源 ≠ 生效源（见结论速览），新界面必须**两处都接**。
- 标题页与战场共用同一套菜单对象，部分项 GRAYED 状态随场景变化（如「结束回合」「胜利条件」）。

### 5. 自写 DIALOGEX 解析器的取证（2026-10-14）

`_对话框解析v4.py` 在 `KANKYOU`（file `0x1121E0`）上实测到的**正确**布局：

| 偏移 | 内容 | 实测字节 |
|---|---|---|
| `0x00` | dlgVer / signature | `01 00 FF FF` |
| `0x04` | helpID | `00 00 00 00` |
| `0x08` | exStyle | `00 00 00 00` |
| `0x0C` | style | `C0 08 C8 80` |
| `0x10` | cdit（控件数） | `19 00` = 25 |
| `0x12` | x,y,cx,cy | `00 00 00 00 DC 00 C3 00` = (0,0,220,195) |
| `0x1A` | menu | `00 00`（空串，**占 2 字节**）|
| `0x1C` | class | `00 00`（空串，**占 2 字节**）|
| `0x1E` | title | `AF 73 83 58 BE 8B 9A 5B 00 00` = `环境设定` |
| `0x28` | pointsize | `09 00` = 9 |
| `0x2C` | typeface | `8B 5B 53 4F 00 00` = `宋体` |
| `0x34` | 对齐填充 | `00 00 00 00` |
| **`0x38`** | **第 1 个控件项起** | exStyle=`00000000` style=`50010001` |

**第 1 个控件项（`0x38`）逐段**：
```
0x38  exStyle  00 00 00 00
0x3C  style    01 00 01 50        = 0x50010001 (WS_CHILD|WS_VISIBLE|WS_TABSTOP|BS_DEFPUSHBUTTON)
0x40  rect     32 00 B1 00 32 00 0E 00  = (50,177,50,14)
0x48  id       01 00 00 00        = 1
0x4C  class    FF FF 80 00        = <ord 128> = BUTTON（序号占 4 字节）
0x50  title    6E 78 9A 5B 00 00  = "确定"
0x56  extra    00 00
```
→ 与 Resource Hacker 导出 `CONTROL "确定", 1, BUTTON, ..., 50, 177, 50, 14` **完全一致**。

**踩坑（三个，均已定位）**：
1. 把空字符串 `00 00` 当成 `<ord 0>`（该跳 4 字节）→ header 多走字节 → 控件表全错。
   实际 `00 00` = 空串 + 对齐 = **2 字节**；序号必须 `FF FF` 起头才占 4 字节。
2. 控件项里 **exStyle 在 style 之前**（`04 F6` 的 DIALOGEX 顺序），读反会让 rect/id 全错。
3. RVA→文件偏移用 pefile 常规换算即可，**不要加 bias**。
