## 用途与边界

本 skill 只讲"怎么用调试器拿到**可复核的运行时证据**"。机制解释、补丁设计、代码审查仍走静态分析与
`engine-feature-development` 流程。**本页不写样本专属地址**（地址一律现读，见 `_样本时间线.py`）。

## 选型定案（不纠结）

- 本样本 `Ekd5.exe` 是 **PE32 / x86 / ImageBase 0x00400000** ⇒ **固定用 `x32dbg`**；
  **x64dbg 无法调试 32 位进程**（架构不匹配），不存在"更好的另一个选择"。
- 路径：`[本地盘]\新建文件夹\snapshot_2026-05-27_12-11\release\x32\x32dbg.exe`；
  工作区已有 **MCP 桥（端口 3000，约 80 个工具）**，工具链最全 ⇒ 优先用 MCP 调，不要手点。

## 开始前（四条）

1. **先进战场再 attach**（`debug_attach_pid`）；不要在标题页挂，**别让调试器当启动器**。
2. **地址一律按"模块基址 + RVA"核对**：来自其它进程、重启或旧构建的绝对地址不得直接使用
   （旧构建地址在当前样本可能已是别的东西）。
3. **先明确要证明的具体事件**：触发输入 → 预期执行点 → 应观察的寄存器/内存/画面结果，写成短检查项。
4. **断点要收敛**：一次不超过几个关键点；跑完立刻清。

## ★ 死规则：先放行，再叫人（`AGENTS.md` §7）

设断点/附加会让游戏**暂停**；不放行就叫用户操作 = 用户什么都做不了。

1. 设断点 / 附加调试器；
2. **循环 `debug_run` 直到 `state == running` 且 `Ekd5.Responding == True`**（间隔 ≥1.5s，通常 2~5 次）；
3. 打印"✓ 已恢复可操作"作为凭据；
4. **然后才**告诉用户可以操作；
5. 用户操作期间用 `_x32保活.py` 或轮询脚本自动放行，命中后立即再放行。

工具：`_先放行再叫人.py`（设断点+放行+确认，一条命令）、`_等命中读数.py`（命中读值后自动放行）、
`大鲸鱼自动战斗.py --go --breakpoint --set-bp 0xADDR=名`（观测挂在推进循环上、收尾自动删自设点；全清用 `--cleanup-bps`。旧 `_x32断点探针.py` 已于 2026-10-26 退役）。

## 选择观察方式

| 目标 | 合适方式 | 留意 |
|---|---|---|
| 确认执行经过一条指令 | 软件执行断点 | 必须落在目标事件**真正执行**的位置；高频位置用条件/日志方式 |
| 观察少数地址的读写或执行 | 硬件断点 | 数量与对齐受限制；先确认设置成功 |
| 找出某个内存区域的访问 | 内存断点 | 范围可能极大且频繁触发；先缩小范围或加筛选 |
| 观察模块加载、异常、特定线程 | 事件断点 | 先确认事件定义与异常传递，别把程序自处理的异常当故障 |
| 地址固定、只在条件满足时暂停 | 条件断点 | 条件**只在该断点实际命中时**求值；先少次命中验证条件 |
| 不知条件在哪条指令首次成立 | 条件跟踪 | 记录量大、明显拖慢；限制范围/线程/长度 |
| 只统计或采样、不应暂停 | 命中计数 / 日志断点 | 避免高频路径过量输出 |

## ★ 条件断点陷阱（本工作区新增认知，直接约束 `AGENTS.md` §6 的用法）

x64dbg **原生**软件条件断点在命中时**无条件先递增命中计数**，然后才求值 break condition
（默认 `1`，任何非零值都暂停）⇒

> **"命中次数增加"只能证明"执行到该地址"，不能证明条件成立、也不能证明调试器已暂停。**

要分别核对四件事：① 断点状态；② 条件表达式与**进制**（表达式中数字默认按十六进制解释）；
③ 实际暂停状态；④ 适配器如何解释命中计数。
条件可能在其他位置成立时，改用**条件跟踪**而不是条件断点。

## 命中后的取证顺序（每次暂停都按这个来）

1. 确认进程、模块、线程、当前地址；记录**模块基址与 RVA**。
2. 查看当前指令及前后控制流：确认停在**预想分支**，而不是相邻的准备 / 派发 / 清理阶段。
3. 记录寄存器、标志位、调用栈与必要的内存范围；**读指针前先确认它可读**；
   不要只凭一个瞬时数值给字段命名。
4. 对比命中前后的状态，追关键值的**写入者、后续修饰与实际消费者**；
   只看到"读取或函数返回"不等于证明了最终效果。
5. 需要继续游戏时，**先完成当前采样再恢复执行**；一次只列需要用户触发的步骤与回报内容，
   **不要**在动作已自动完成后把先前的命中当成结果验收。

**单步**：Step Into 进调用、Step Over 越过、Step Out 到返回附近；
"运行到选中地址"前确认目标仍属当前模块与预期路径（未命中会继续跑 ⇒ 准备明确停止条件）；
不要为看完整机制逐条穿过无关大段代码——先用静态调用关系缩小窗口。

## 运行时内存写入（临时实验，5 步）

1. 暂停并记录**原始字节**、模块/RVA、保护属性、当前线程状态；
2. 只写已确认的最小字节范围（**不要把未知区域当空闲空间**）；
3. **立即读回并逐字节比对**，不符就停并还原；
4. 记录实验后状态，结束前还原或重启到干净基线；
5. **运行时写入只证明当前进程的临时状态** —— 它**不证明磁盘文件已改变，也不等于补丁已验收**。

## 抓崩溃现场

```text
_x32_抓崩溃现场v2.py --attach --secs N    # 附加 + 轮询；崩溃即抓 EIP/全寄存器/反汇编/调用栈/异常码
_解析崩溃转储.py --latest                 # 离线解析 _崩溃转储\*.dmp（不碰游戏）
```

**禁止**在没有调试器监测时把"闪退/卡住"当成可归因结论（只看"进程没了"只有结果，没有原因）；
**禁止**为此另写崩溃抓捕脚本（库内已有）。

## 收尾（固定顺序，反了会留入口断点）

1. `breakpoint_delete_all` → 2. `debug_stop`。
2. ⚠ 附加会让被调试进程退出后**变僵尸**（`HasExited=True` 但仍占进程表）
   ⇒ **写 `Ekd5.exe` 前必须先关 x32dbg**，否则 `_dsh写锁.py` 会以"游戏正在运行"拒绝写入。

## 已知适配坑（本 bundle 实测）

| 现象 | 处置 |
|---|---|
| `script_execute` 报 `Method not allowed` | 用 `script_execute_batch`，或把逻辑写进 Python 侧 |
| `memory_read` 对新分配页报 `-32010` | 约 1.5s 缓存延迟，**不是权限问题**，重试即可 |
| 搜狗输入法（`SogouTSF.ime`）导致频繁暂停 | 配 `_x32保活.py` |
| 前台被抢、点击无效 | 用 `AttachThreadInput` 强置前，**不要** `SetForegroundWindow` 硬来 |
| 断点把游戏整体挂住（`Responding=False`） | `breakpoint_delete_all` + 循环 `debug_run` 到 `running`；高频地址禁挂普通断点 |

## 证据记录（每次动态观察至少留）

目标进程/模块身份与调试器架构；断点的模块/RVA/类型/条件/命中次数；触发步骤、线程、停点指令、
寄存器、调用栈、关键内存读回；观察到的分支、后续消费者与画面/业务结果；
**证据层级**（静态定位 / 运行时命中 / 内存读回 / 受控路径结果 / 游戏内验收）；未覆盖路径与复测条件。

## 常见误区

| 误区 | 修正方法 |
|---|---|
| 拿旧构建绝对地址直接用 | 核对当前模块基址、RVA、字节与指令边界 |
| 动作刚发出就设断点，把命中当成最终选择/结算 | 断点放到实际选择/写入/消费位置，逐阶段记录后再继续 |
| 条件断点计数增加 = 条件已满足 | 查清原生条件行为、适配器返回值、命中计数与暂停状态（见上"陷阱"） |
| 把一个寄存器值称为字段含义或最终结果 | 追写入、变换、分支与消费；必要时对比成功/失败路径 |
| 内存值对但界面不对就认定计算错 | 同时查"值属于哪个对象""界面读哪个对象""后续刷新是否执行" |
| 把运行时写入当持久补丁 | 分开保存：进程内读回 / 磁盘文件读回 / 重启后结果 |
