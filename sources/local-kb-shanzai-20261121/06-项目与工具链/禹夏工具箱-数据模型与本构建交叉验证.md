# 禹夏引擎工具箱 ⇄ 本构建 交叉验证（特技编辑器数据模型）

> 来源：用户 2026-10-16 提供的三张截图（**禹夏引擎工具箱 ver0.1 → 特技编辑器**，引擎指向本工作区 `Ekd5.exe`）。
> 本页把它的数据模型与本构建（SHA **`0046459D53F2565D060D4FFB4A1F87FC1897B91AAE63D990E66D60EEF901C845`**）逐条对账。
> 关联页：`03-机制详解/特技后缀类型码-f列-后缀表与分派.md`（f 列语义）、`03-机制详解/特技定义表与空位搬移.md`（名表基址/空位）。

## 结论速览

1. **它的"桩起始点"= 实现该特技的函数入口**（不是"查询桩"本身）；**它的"装备特技号"= 该函数同时查询的装备特效号** ⇒ 两者可用本构建字节直接复核 ✓。
2. **已逐条复核 5 组，全部一致**（见 §2）；它标注的"**常规参数化桩**"在字节层面也成立（函数内**没有**内联的特技查询桩）。
3. **它的"后缀号"列与我们的 f 列实证完全对上**（`0x04 (N%)` ⟷ f=0x04 = `%d%%`；`0x05 (N)` ⟷ f=0x05 = `%d`；`0x00` ⟷ 空白）。
4. **它的「主引擎参考后缀表」`0x00`–`0x05` 与本构建完全一致**（`0x00` 原生/无后缀、`0x01 +N`、`0x02 +N%`、`0x03 -N%`、`0x04 N%`、`0x05 N`），
   **从 `0x06` 起错位**（它 `0x06 属性关系`、`0x13 N次`；本构建 **`0x06` = `%d次`**）⇒ **两套编号不可混用**（它自己的界面也写"以当前引擎为准"）。
5. **特技说明文本**：它的编辑器显示"**Imsg 偏移 `0x14FF0`**"、"**有效字节 109/199**"、"修改后需重启游戏" ⇒ 说明文本在 `Imsg.e5`，**每槽约 199 字节**（其口径，待复核）。

## 一、它的数据模型（编辑器列）

| 列 | 含义（交叉验证后的理解） |
|---|---|
| 编号 | 特技号（= 名表行号），双击可改 |
| 名字 | 名表 `0x9E800 + 号×16` 的 12B GBK |
| **装备特技号** | 该实现函数里另外查询的**装备特效号**（例：覆海之龙 `0x43`、真元流转 `0x1B`、破妄归真 `0x25`） |
| **桩起始点** | **实现函数入口 VA**（有的特技是"单一桩"，有的是"复合特技"⇒ 多个入口） |
| 后缀号 | = 本库的 **f 列**（名表偏移 15） |
| 复合特技 | 是/否（是否由多个入口共同实现） |
| 状态 | `常规单一桩` / `常规参数化桩`（后者：号由参数传入，函数内无内联查询桩） |
| 风险 | `低风险` / `不支持修改` |
| 操作 | 双击编号/名称可改；**"屏蔽特技"按钮腾出特技号**；"编辑特技说明"改 `Imsg` 文本 |

## 二、逐条复核（本构建现读字节）

| 编号 | 它的 装备特技号 | 它的 桩起始点 | 本构建现读 | 判定 |
|---|---|---|---|---|
| `0x00` 覆海之龙 | `0x43` | `0x4210F4` | `push ebp / mov ebp,esp / push 0 / push 0 / **push 0x43**` | **✓ 一致** |
| `0x01` 真元流转 | `0x1B` | `0x421106` | 同形，`**push 0x1B**` | **✓ 一致** |
| `0x02` 破妄归真 | `0x25` | `0x43C72C` | 函数内出现查询 **`0x25`** | **✓ 一致** |
| `0x0C` 随机破坏能力 | — | `0x472D5C` | 函数内查询号 = **`0x0C`** | **✓ 一致** |
| `0x03`/`0x06`/`0x0D`/`0x12`/`0x15` | — | `0x43CDDD` / `0x40399F` / `0x4039F6` | 前 48 字节内**无** `push imm + call 0x4101D9/0x42518F` | **✓ 与它标注的"常规参数化桩"吻合** |

> 方法：在给定 VA 处反汇编 48 字节，搜 `push imm` 紧跟 `call 0x4101D9` / `call 0x42518F`（本库的"特技查询桩"形态）。

## 三、对我们（搬回工程）的直接价值

1. 它给出了我们**没有的**一张表：**特技号 → 实现函数入口**（含"复合"标记）⇒ 可用它**定位被 NOP 的段属于哪个特技**（比逐个反推快得多）。
2. 它给出了 **装备特技号** 这一维度（同一函数同时查"个人号 + 装备号"）。
3. "**屏蔽特技** = 腾出特技号"与我们的"搬回/退役"是同一类操作的两个方向 ⇒ 互通。

## 五、★ 交叉验证升级：**本构建「特技号 → 桩入口」全表已产出**（2026-10-16 补）

> 用户口径：「**需要啊**」（同意我把全表扫出来，与它的"桩起始点"列逐条比对）。

### 5.1 产物（工具：`大鲸鱼产生专用\_特技叠加检测.py --map`）

| 文件 | 规模 | 列 |
|---|---|---|
| `大鲸鱼产生专用\_特技桩全表.tsv` / `.json` | **134 行 / 127 个号**（入口去重 128） | `号 / 十进制 / 形式 / 桩入口 / 调用点 / 宝物号 / 叠加方式 / 效果值方式` |

**★ 本构建有"两族桩形式"**（这是第一版扫描漏掉 `0x00`/`0x01` 的原因）：
- **`call 0x4101D9`**（直接查）—— 97 个号；
- **`call 0x42518F`**（先经 `0x40B922` 判存在、再转发 `0x4101D9`；即"叠加/条件式取值器"）—— 补上 30 个号。

**参数约定（本次实证）**：紧邻 `call` 往前最多 4 个 `push imm32`，顺序 =
`效果值方式 / 叠加方式 / 宝物号 / 人物·兵种号` ⇒ **第 3 个 push = 宝物（装备）特效号，第 4 个 = 特技号** ✓
（这正是用户工具箱"装备特技号"列与"编号"列的含义。）
