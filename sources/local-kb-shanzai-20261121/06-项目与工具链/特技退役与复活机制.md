# 特技退役与复活机制

## 结论速览

- 用户需求（2026-10-14）：**有些特技不需要了，要完全删除（从代码到名表变成空位），
  但又怕以后还要用 ⇒ 把代码存成注入文档备用。**
- 本机制已实现并**自检通过**：`清空 359 字节 → 复活 359 字节 → SHA 与基准完全一致`。
- 三个工具：
  | 工具 | 作用 |
  |---|---|
  | `_特技登记表.py` | 扫全部补丁 txt，建立「特技 ↔ 地址 ↔ 字节」总账 |
  | `_特技退役-提取.py` | 把某特技的完整实现提取成**可复活档案** |
  | `_特技退役-复活.py` | 从档案把特技原样写回（**走 `safe_write_exe`**，遵守 W1~W5） |
  | `_特技退役-自检.py` | 内存内验证「清空 → 复活」闭环（不碰真 EXE） |
- **特技 = 三类东西**：个人特技名表行 + 代码包（钩子/代码洞/查表）+ 剧本·数据引用（EXE 外）。

## 适用版本

- 复刻版6.6山贼 `Ekd5.exe`（当前 SHA 见 `_改动总账.md`）。
- **多节映射注意**：`.code` VA `0x401000`/Raw `0x400`、`.api` VA `0x4BE000`/Raw `0x90200`、
  `.text3` VA `0x4CE000`/Raw `0x9F800` —— **不能对全 exe 用单一偏移公式**，必须按节表反查。

## 已确认事实

### 1. 个人特技名表结构（重要纠正）

- 基址 **VA `0x4CC600`**（文件偏移 `0x9E800`）。
  ⚠️ **2026-10-15 更正**：旧口径 `0x4CC800` 偏了 `0x200`（＝32 行）。**可复现判据**（现读）：
  `(0x4CD550 − 0x4CC600)/16 = 245 = 0xF5`「※削减全能力」、`(0x4CD560 − 0x4CC600)/16 = 246 = 0xF6`「※物理易伤」
  —— 与现役补丁体内 `push 0xF6 / call 0x4101D9` **一一对应**。
  本页下方"255 行 / 到 `0x4CD7F0`"是按**旧基址**推出来的，**行数与末地址待复核**（不要直接引用）。
- 每行 16 字节：**名字（GBK，约 12B，补 `0`）+ 若干 `00` + 显示 flag**。
- 行号由地址反推：`行号 = (VA − 0x4CC600) / 16`，**行号 = 特技号**。
  - 例：`0x4CD4D0` ⇒ `(0x4CD4D0 − 0x4CC600)/16 = 0xED = 237 行`（旧口径的 `0xCD = 205` 是**错基址的产物**）。
  - ⚠️ 旧口径因此把"异常追袭占 `0xED` 行"判成错的 —— **更正后 `0xED` 反而是对的**（237 = `0xED`）；
    当时真正被混掉的是"**行号**"与"该行**末字节曾是 `0xED`**"这两件事。

### 2. 特技的三类组成

| 组成 | 位置口径 | 退役处理 |
|---|---|---|
| 个人特技名表行 | VA **`0x4CC600`** + 特技号*16 | 名字清 0 |
| 代码包 | 钩子点（改原函数入口）+ 代码洞（实现）+ 可选查表 | 代码区填 `0x90` |
| 剧本/数据引用 | `.eex` 剧本指令、`Data.e5` 字段 | **不在 EXE 内**，档案仅登记提醒 |

### 3. 实测样本：异常追袭（4 处）

| VA | 长度 | 归属 | 退役前字节（档案内容） |
|---|---|---|---|
| `0x4363B0` | 8 | `.code` 钩子（引擎伤害修正函数入口） | `E9 4B DC 09 00 90 90 90` |
| `0x4D4000` | 89 | `.text3` 代码洞 | `50 53 56 57 9C 8B 74 24 1C …` |
| `0x4D4200` | 256 | `.text3` 状态位查表 | `00 02 02 02 01 03 03 03 …` |
| `0x4CD4D0` | 16 | `.api` 个人特技名表第 205 行 | `D2 EC B3 A3 D7 B7 CF AE … 05` |

### 4. 自检结果（闭环）

```
[0] 合成基准（= max(当前 EXE, 档案)）：补齐 17 字节  -> SHA 5A59CCCF5DC827B75EEBCEE6FC92E10EF3E6DBAAF94AC6EA3F142AEF1C2957EF
[1] 清空特技：改动 359 字节                        -> SHA A9865786B25664A22E4684D3D06A740878C2C058EAE34DE7635275117957EF63
[2] 用档案复活：改动 359 字节                      -> SHA 5A59CCCF5DC827B75EEBCEE6FC92E10EF3E6DBAAF94AC6EA3F142AEF1C2957EF
[3] 断言「复活后 == 基准」：**逐字节一致 —— 闭环通过**
```


## 风险与边界

- **提取来源可能不全**：档案靠「补丁文本 + 登记表 + 快照」三源合并；
  若某特技的实现分散在多份补丁而文件名不含同名关键字，可能漏抓。
  提取后务必看 `README.md` 的条目数是否合理。
- **多补丁共用地址**：不同特技可能改同一处（例如都挂 `0x432950`），
  退役一个会连带影响另一个 ⇒ 退役前先查 `特技登记表.md` 是否有地址重叠。
- **半状态是常态**：2026-10-14 实测当前 EXE 里异常追袭处于
  「钩子已撤、代码洞还在」的中间态 ⇒ 退役/复活工具必须能处理非全有/全无的情况
  （本工具已按逐处独立判断实现）。
- **`Errno 22` 坑**：把 EXE 复制到新目录后立刻整文件覆写会偶发 `OSError: [Errno 22]`
  （安全软件扫描新可执行文件时短暂持锁）。**闭环验证不必落地文件**，改内存内比对即可。
- 复活必须遵守写锁规则 W1~W5（唯一入口 `safe_write_exe`）。
- 档案**不含剧本/数据表引用**；退役后若剧本仍在调用该特技号，行为需另行确认。

### 3. ★ 两条重要约束（退役前必看）

**约束 A：同一机制可能拆成多份补丁，按文件名聚类会把一个特技算成两个**

实测：补丁 `【6.6山贼】火地形-与纵火同源(3回合消失).txt` 改的是
`0x432FCD`(128B) 与 `0x44C7FE`(13B) —— 这两处**正是纵火链**。
而"纵火"这个名字只被 `纵火-恶劣天气可用`(改 `0x46FD51` 2B) 占用。

⇒ 登记表按**补丁文件名**推断特技名，会把"火地形"与"纵火"当成两个特技，
   实际它们是**同一条机制的两次改动**。退役任何一个都要把对方一起考虑。

**约束 B：多个特技共用同一钩子点**

上表 8 组共享说明：注入区（`0x432xxx`）与部分 `0x4Cxxxx` 名表位置是**多特技共用**的。
退役前必须查 `特技重叠分析.md`，否则会连带改变别的特技行为。

### 4. 名称匹配修正

`_特技退役-提取.py` 原来的匹配是 `key in nm or key in fn or nm in key`，
导致「★无情铁手」把「无情铁手」的全部 10 份补丁都抓进来（反之亦然），
产出**等价档案**。现改为三级优先：

1. 去装饰符（`★☆空格`）后**精确相等**
2. 否则**文件名包含关键名**（关键名长度 ≥ 3）
3. 再否则才子串匹配

验证：`修罗之怒` 现在精确匹配 1 份补丁（此前也是 1 份，但同名特技不再互相污染）。

### 5. 建议的退役顺序（重叠组）

- 先退**独占地址多**的特技，最后处理共享地址的（或干脆不单独退）。
- 对共用 `0x4322D3`（HP辅助说明显示 / HP辅助拆分 / 搬回特技）这组：
  三者的显示逻辑共用同一格式化函数，**要么一起保留，要么一起退役**。
