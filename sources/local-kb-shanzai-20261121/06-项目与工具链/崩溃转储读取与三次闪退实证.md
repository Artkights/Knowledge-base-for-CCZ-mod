# 崩溃转储读取与三次闪退实证（Ekd5 6.6 山贼）

> 本文记录**只读**手段：开本地全转储 → 解析 minidump → 读异常码/出错地址/寄存器/栈 → 反查字节。
> 结论用于定位闪退真因；**写入 EXE 一律走 `大鲸鱼产生专用\_dsh写锁.py`**（见 `00-总览与规范/Ekd5写入串行化规则.md`）。

## 结论速览

- 靠"调试器断点停在哪个地址"判崩溃点会**误判**（实测把断点停点 `0x4D4022` 记成了崩溃点）。
  **只有 minidump 的 ExceptionStream 才是真凭据**。
- 2026-10-14 打开 `Ekd5.exe` 本地全转储后，抓到 **3 次闪退 ×2（成对：一个 0xC000041D 包装 + 一个原始 0xC0000005）**：

| 时刻 | 线程 | 原始异常 | 出错地址 | 当时状态 |
|---|---|---|---|---|
| 02:46:47 | 12076 | 写 `0x6` | `Ekd5.exe+0x3045F`（VA `0x43045F`） | envsave v1 生效中、异常追袭仍在 |
| 03:07:18 | 10964 | 写 `0x3D888DB0` | `comctl32.dll+0x38D46` | 异常追袭已回滚 |
| 03:25:53 | 15364 | 读 `0x72CCE080` | `comctl32.dll+0x38D0E` | 同上 |

- **02:46 那次已定性**：dump 里 `EIP` 处的机器码是 **`80 70 04 01` = `xor byte ptr [eax+4], 1`**，
  且 `Eax = 0x00000002` ⇒ 写 `0x6` ✓ 与异常参数一致。该 4 字节在**当前 EXE 文件里只出现一次**，
  位于 VA `0x41A192`，前面紧跟 `0B 05 A0 0F 50 00`（`or eax, dword [0x500FA0]`）
  ⇒ **它读的是"环境设定块指针" `[0x500FA0]`，而该指针当时是 0** ⇒ 取 `[0+4]` 写标志位就炸。
- 栈上返回地址全是 `user32.dll` 消息分发 + `Ekd5.exe+0x1BB85` / `+0x1BAD7`（窗口过程/对话框过程）
  ⇒ 崩溃发生在**窗口回调里**，这正是外层异常码为 `0xC000041D`（callback 逃逸）的原因。
- 时间线自洽：`envsave` v1 于 **02:31:27** 落盘 → 02:46 崩；**03:00:29** EXE 再变（`BE86A649…`，
  VA `0x43045F` 变成 `C6 05 A4 0F 50 00 01` 即 `mov byte [0x500FA4],1` 一串标志初始化 + `mov eax,0x500FA0`）
  ⇒ envsave v1 的指针未初始化问题在 v2 被消掉，但 03:07 / 03:25 换到 `comctl32` 崩，说明**还有第二个点**。

### 2.5 后两次（comctl32）寄存器签名一致，但**上下文不是出错现场**

两次 `--detail` 结果几乎完全相同：

```
异常(原始)   写 0x3D888DB0 @ comctl32+0x38D46   /   读 0x72CCE080 @ comctl32+0x38D0E
寄存器       Eax=00000000 Ebx=00000000 Ecx=0000102B(→00001073) Edx=00000001 Esi=00000003 Edi=00000003
dump 内 Eip  0x77484C6C (ntdll.dll)，其前后字节 = C2 14 00 90 B8 5C 00 00 00 BA 60 85 4A 77 FF D2
栈            KERNELBASE / kernel32 / ntdll / user32 的异常与错误报告路径（无 Ekd5.exe 帧）
```

- ⇒ 这两次的 **CONTEXT 是 WER 接管后的状态**，不是崩溃指令现场（与 02:46 那次不同：那次的 `Eip` 正好等于
  `ExceptionAddress`）⇒ **以 `ExceptionStream.ExceptionAddress` 为准**，别用 `Eip` 反推指令。
- `Ecx` 两次都像 **HWND**（`0x102B`→`0x1073` 递增），`Esi=Edi=3`、`Eax=Ebx=0`、`Edx=1`
  —— 可作为"同一 bug 的两次复现"的指纹；下一步要把 `comctl32+0x38D0E`/`+0x38D46` 映射到具体 API
  （无符号时可用 x32dbg 附加后 `disassembly_at 0x744A8D0E`，或按导出表反推邻近函数）。

## 已确认事实

### 1. 怎么开、怎么读

```powershell
# 开（全转储，落盘到 大鲸鱼产生专用\_崩溃转储）
$k='HKL[本地盘]\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\Ekd5.exe'
New-Item $k -Force | Out-Null
New-ItemProperty $k DumpFolder '<游戏根>\大鲸鱼产生专用\_崩溃转储' -PropertyType ExpandString -Force
New-ItemProperty $k DumpType 2 -PropertyType DWord -Force      # 2 = 全转储
New-ItemProperty $k DumpCount 10 -PropertyType DWord -Force
# 关：Remove-Item $k -Recurse -Force
```
```bat
大鲸鱼产生专用\_pyrun.cmd 大鲸鱼产生专用\_read_crash_dump.py               :: 最新一个
大鲸鱼产生专用\_pyrun.cmd 大鲸鱼产生专用\_read_crash_dump.py --all         :: 全部
大鲸鱼产生专用\_pyrun.cmd 大鲸鱼产生专用\_read_crash_dump.py 6988 --detail :: 指定 + 寄存器/栈
```

### 2. minidump 结构偏移（自己解析，不依赖 WinDbg）

| 流 | 关键字段 |
|---|---|
| Header | `MDMP` + `NumberOfStreams`@+8, `StreamDirectoryRva`@+12 |
| ExceptionStream(6) | `ThreadId`@+0；`ExceptionCode`@+8；`ExceptionAddress`@+24(u64)；`NumberParameters`@+32；`ExceptionInformation[15]`@+40(u64×15) |
| ModuleListStream(4) | 每项 `MINIDUMP_MODULE` = **108 字节**：`BaseOfImage`@+0(u64)、`SizeOfImage`@+8、**`ModuleNameRva`@+20** |
| ThreadListStream(3) | 每项 `MINIDUMP_THREAD` = **48 字节**：`ThreadId`@+0、`Stack`@+24、**`ThreadContext`(DataSize@+40, Rva@+44)** |
| x86 CONTEXT | `Edi`@0x9C `Esi`@0xA0 `Ebx`@0xA4 `Edx`@0xA8 `Ecx`@0xAC `Eax`@0xB0 `Ebp`@0xB4 `Eip`@0xB8 `EFlags`@0xC0 `Esp`@0xC4 |
| Memory64ListStream(9) | `NumberOfMemoryRanges`@+0(u64)、`BaseRva`@+8(u64)，随后每段 16 字节 (start u64, size u64)，数据按序连续存放 |

- 关键手法：**从 dump 里读 EIP 处的机器码**，而不要相信磁盘上 EXE 的同地址字节
  —— 打了补丁/回滚后两者会不一致（本次就撞上：磁盘上是 `C6 05 A4 0F 50 00 01`，dump 里是 `80 70 04 01`）。
- 成对转储：`0xC000041D`（`STATUS_FATAL_USER_CALLBACK_EXCEPTION`，回调里异常逃逸）是**包装**，
  同目录下同名（不带 `(1)`）的那个才带**原始** `0xC0000005` 与访问类型/目标地址。

### 3. VA ↔ 文件偏移（6.6 山贼，6 节）

```
.code   VA 0x401000  Raw 0x000400   Size 0x085000
.text1  VA 0x486000  Raw 0x085200
.text2  VA 0x48B000  Raw 0x089A00
.api    VA 0x4BE000  Raw 0x090200
.text3  VA 0x4CE000  Raw 0x09F800
.rsrc   VA 0x532000  Raw 0x103800
⇒ file = Raw + (VA - ImageBase - SectionVA)
```

## 实现·使用方法

1. 复现闪退（游戏侧正常操作即可）→ 转储自动落盘（每次 250~290 MB，注意占用）。
2. `_read_crash_dump.py --all` 先看**异常码/出错地址/模块**三件套，挑出**原始** `0xC0000005` 那一个。
3. 对目标加 `--detail`：拿到 `Eax/Ebx/…/Eip/Esp` 与 EIP 前后 16 字节、栈上落在模块内的返回地址。
4. 用 `Eax` 等寄存器 + 出错指令**反推地址**（本次：`xor byte [eax+4],1` 且 `eax=2` ⇒ 目标 `0x6` ✓）。
5. 反查该字节序列在文件中的位置（正则扫描全文件），再看它周围的原生代码，判断"它在操作哪个全局"。
6. 需要看函数上下文时，把 **VA** 交给 `_dsh反汇编工作台.py da <VA> <长度>`（注意它读的是**磁盘当前** EXE）。

## 风险与边界

- 转储是**全内存**，包含游戏内存数据；归档/分享前注意体积与隐私。
- 磁盘 EXE 与崩溃时 EXE 可能不同（补丁/回滚）⇒ 一律以 dump 内字节为准；必要时从 dump 里**整段提取**代码页比对。
- `0xC000041D` 只说明"异常从回调里逃出来"，**不能**据此认定错误在 user32/comctl32；
  真凶要看原始 `0xC0000005` 的出错指令。
- 用 `_read_crash_dump.py` 解析 250 MB 文件约需数秒~十几秒，`--all` 会逐个加载（峰值内存约 1 个转储大小）。
