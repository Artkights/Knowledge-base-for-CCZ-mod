## 已确认事实

### 1. 数据模型（来自 `ui\skill_editor` 常量，与工具界面列一一对应）

| 列 | 含义 |
|---|---|
| `num` | 特技号 0~255（**编号不允许修改**，只能改名/迁移/屏蔽） |
| `name` | 名表里的名字 |
| `equip` | **装备特技号**（显式 `0x00` 与"无装备字段"**严格区分**；0 是有效值，不能按假值处理） |
| `stub_start` | 桩函数起始 VA（多个去重显示，无法确认时标"未知"） |
| `suffix` | **UE 后缀号**（说明文本里的 `%N` 占位样式） |
| `composite` | 是否复合特技 |
| `status` | `empty` 占位符 / `uncertain`（名表有名字但**桩引用为 0**）/ `normal` / `sentinel` |
| `risk` | `low` / `locked`（可改名，迁移与屏蔽由调用方拦）/ `high` / `forbidden`（**255 屏蔽哨兵号**，禁止任何操作） |

- 风险合并规则：**`forbidden > high > locked > low`**（取两者较高者）。
- 弹窗分流：`low`→可关闭的一般警示；`high`→**不可关闭**的高风险弹窗。

### 2. 特技号引用（桩）判定规则 ★核心

- **引用位置**：特技号只出现在**桩函数的 `push` 立即数**里 ——「4 个 push 中**第 3 个=装备号**、**第 4 个=个人号**」；
  兼容 `6A imm8`（2 字节）/ `68 imm32`（5 字节）；**定位失败就跳过，绝不误写**。
- **内联桩判定（其文档称 Ruling 5）**：只有「`call` 前紧邻**恰好 1 个** `push imm`」才算内联桩；
  **含 ≥2 个 push 的异常桩不是内联桩**（例：6-push 桩的真实号在 `68 imm32`，前面的 `6A xx` 是**标志**）。
- **参数化桩**（个人号运行时计算，**禁止迁移改号**）：
  - `call 0x600xxx` 调度区：在**调度函数**里数 `cmp al` 分支（各桩 5/6/7 个不等）；
    **调度器有间隙** —— 其文档举例 `0x6000C2` 覆盖 `0x06~0x0B + 0x0D~0x10`、**跳过 `0x0C`** ⇒ 必须用 **cmp 分支精确值集**，不得当连续区间。
  - `直调 0x42518F / 0x4101D9`：在**桩函数自身**里找 `cmp al, N`（N=循环次数）⇒ 覆盖 `base ~ base+N`。
  - 桩内形态只认：`mov eax,[ebp+8]` → `add eax/al, imm` → `inc/dec eax` → `push eax`；
    **明确不做通用寄存器数据流分析**，无法确认就返回 None（= 宁可不改）。
  - 参数化桩的**装备号是整组共享**的（一组只改那一个 push）。
- **屏蔽哨兵**：`equip` 渠道 → 装备号 push 改 **`0x00`**（SENTINEL_EQUIP）；
  `per` 渠道 → 个人号 push 改 **`0xFF`**（SENTINEL_PER）并把名表 src 置占位符
  ⇒ 与库内「`0xFF` = 空/永久」的口径**互证** ✓
- **禁止自动迁移的情形**：效果代码里 `cmp al, imm8` **分派表**引用语义复杂、误改风险高 ⇒ 只迁移 `stub_equip` / `stub_per`。

### 4. 工程做法（可直接借）

- **写引擎 = 可逐条撤回的操作历史**：写操作返回结构含
  `('ok','warnings','undo','changed','version_match','imsg_changed','imsg_undo')`
  ⇒ 每次写都带 **undo 记录 + 引擎版本匹配校验**（界面显示 `6.6引擎 1.0.6.6`）。
  比库内现行"备份 + 审计行"更强的一点：**逐条撤回 + 版本不符就拒写**。
- **风险分级驱动交互**：先"风险检测（只提示）"再"执行注入"，高风险弹窗不可关闭。
- **注入器面板**：选引擎 + 选补丁 → 检测 → 注入（其路线是补丁注入，我们走直接写 EXE + `_dsh写锁.py`）。
- **特技说明编辑**：按**特技号**定位 `Imsg.e5` 里的说明槽（界面显示 `Imsg 偏移 0x14FF0`、**有效字节 109/199**、
  "保留固定槽位字节保护"、`IMSG_SKILL_DESC_PAYLOAD_SIZE`）⇒ 说明槽是**固定长度**的（≈200 字节），改完需重启游戏生效。
  ⚠ 库内既有口径是"特技文字在 **Amsg.e5**（角色N 第一特技=特性N）" ⇒ **两者可能是不同表**
  （Amsg=名字/角色表，Imsg=特技说明），**待核验后再合并口径**。

## 深挖第二轮（2026-10-16）：桩扫描规则 + 代码洞桩签名 + 本样本实测对照

### 1. 三种特技号引用形态（其 `core\stub_scan` / `core\stub_formats`）

| 形态 | 判据 | 号在哪 |
|---|---|---|
| **标准桩 / 多推桩 / 包装桩 / 参数化桩** | `call` 前紧邻 push 序列；**装备号总在第 3 个立即数 push** | push 立即数 |
| **mov-al 桩** | `mov al,技能号; mov cl,装备号; push 0; push 1; push ecx; push eax; call 内联核心`（例：其引擎策略增伤 `0x43C263`） | **`mov al` 立即数**里，**不在 push** |
| **参数化桩** | 桩内 `mov eax,[ebp+8]`→`add al/eax,imm`→`inc/dec eax`→`push eax`（不做通用数据流分析） | 运行时算 |

- **代码洞桩**（code-cave stub）：不靠函数序言回溯，而是用**完整字节签名**定位：
  `signature` = `call` 前的完整已知字节；`trailing_signature` = `call` 后的操作；`push_offsets` = 各 `push imm` 的 opcode 位置
  ⇒ 既能避免把数据里的任意 `E8` 误认成桩，也能给出**不依赖反汇编回溯**的精确地址。
  其两条实例签名：`6A 00 6A 01 6A 00 68 BE 00 00 00`（技能号 190）、
  `8B 4D FC 6A 00 6A 01 6A 00 68 F5 00 00 00`（技能号 245）。
- **扫描工程细节（重要）**：`call` 前要在 **`max_back=0x800`** 字节内找最近的 `55 8B EC`/`55 89 E5`（prologue）；
  其注释举例"策略增伤 `0x43C263` 距 prologue **582 字节**，`0x200` 会漏，**线性反汇编错位会导致漏扫**"。

### 三、★ 「arg 参数桩」机制（回答"参数化桩的特技号从哪来"）

禹夏 `arg_stub.pyc` 自述原文：

> **第5类桩识别：配置循环桩（arg 参数桩 + 调用方循环区间）**
> - **arg 参数桩**：内部 `push 0; push 1; push eq-imm; push [ebp+8]; call 内联核心`，
>   **个人号由调用者经 `[ebp+8]` 参数传入**（如检查助手 `0x449034`）。
> - **调用者循环**：`push imm32(起始DWORD); counter清零; cmp counter, N; push 起始+counter; call arg桩`
>   → **覆盖 = 起始 ~ 起始+N-1**。
>
> 只读分析模块，不修改引擎。

⇒ 这解释了本样本的 `0x40399F`（`cmp al,6` + `add eax,8`）与 `0x4039F6`（`cmp al,4` + `add eax,0x0F`）：
**桩本身不 push 特技号**，而是把「特技号 = 调用者传入的个人号」再交给 `call 0x436334`（第四条判定入口）；
**桩内 `al` 是循环变量**，故 `al+N` 推区间只是近似，**真值须由调用者的循环区间决定**。
⇒ 这也说明：把参数化桩覆盖的特技号补进映射表时，**应扫"调用者循环"而不是猜 `al+N`**。

## 深挖第四轮 + 对照印证（2026-10-16）：用禹夏的"算术语义表"补我们扫描器的断链

### 1. 从 `core\stub_scan` / `core\risk` / `core\skill_blocks` 掏到的规则

- **允许跨越的算术语义表**（其常量）：`mov / add / sub / inc / dec / xor / lea / shl / shr / imul / and / or / neg / cdq / movzx / movsx`
  —— 用途：回溯 `call` 前的 push 序列时，**允许跨过"参数计算"类指令**。
- **mov-al 桩形态**：`mov al,技能号; mov cl,装备号; push 0; push 1; push ecx; push eax; call 内联核心`
  判定规则：`call` 前 **0x10 字节内必须有 `push eax`**（该 call 是 eax 传参）。
- **三处调度区（其引擎坐标）**：`0x600000~0x600BC0 标准调度`、`0x600BC0~0x601700 扩展调度`、
  **`0x4D4000~0x4D4400 溅射调度`**；其核心入口候选元组 = `0x42518E, 0x42518F, 0x43C7D4, 0x410159, 0x4078DA, 0x412C5E`。
- **`core\risk` 的设计**：风险等级 `safe / review / blocked`（**始终是建议、不硬阻断**），
  字段 `addr / category / size_needed / cave_avail / capacity_ok / severity / idempotent / overlap`
  ⇒ **会检查代码洞容量**（cave_avail / capacity_ok）与幂等、重叠。
- **`core\skill_blocks` 的设计**：屏蔽个人特技时把「原名字 + 原字节(undo) + 装备引用地址」快照进 `.skill_blocks.json`；
  重新启用分「原地恢复」与「重新赋号」两种语义（后者把个人 push `FF→target`、装备 push `num→target`）。

### 2. ★ 对照印证：本样本 41 个"未解析调用点"的根因

现场字节（本样本现读）：

```
0x414D98: 55 8B EC │ 6A 00 │ 6A 03 │ 6A 7D │ 04 8F │ 50 │ E8 … │ 5D C3
          序言      push 0  push 3  push 号  add al,imm  push eax  call   收尾
```

- 我们的 `back_args` 要求 push **紧邻连续** ⇒ 被 `04 8F`（`add al, 0x8F`）**断链**，只回收到 1 条 `push eax`
  ⇒ 该 call 落入 "unresolved"，对应特技号永远显示「—」。
- 而禹夏的算术语义表**正是为这种情况准备的**：允许跨过参数计算指令继续往前找 push。

### 3. 改法（已实施并实测）

- `_增强面板数据.py` 新增 **`back_args_fwd()`**：从 `call` 前最多 96 字节**线性反汇编**到 call，
  允许跨越上表那些算术指令；为对齐稳健，**尝试多个起点**、取"指令精确铺到 call 且 push 最多"的解码；
  遇 `call/ret/jmp` 视为跨函数边界即丢弃。`scan_all()` 优先用它，拿不到再退回旧 `back_args`。
- 同时放宽归属：**第 3 个立即数 push（装备号）在 0x00~0xFF 时即归入该号**并标 `dyn=True`
  （第 4 参为 reg/mem 或不存在时）——这正是禹夏口径「参数化桩的装备号仍位于第三个立即数 push」。

## 自审补正（2026-10-16，用户口径「你再看看？」）

对上一轮"反汇编式回溯"改动做了独立复核，**发现 2 个问题、修掉 1 个、澄清 1 个**：

### 问题 1（已修）：窗口/步长导致**假 `dyn`**

- 实例：`号 0x22` 的 call `0x43BDF3`，真实字节 = `6A 00 6A 00 6A 20 6A 22 8B 4D 08 E8 …`
  ⇒ **4 个 push 全是立即数**（技能号 = 第 4 个 = `0x22`），但旧实现起点**步长 -2**，错过了正确对齐，
  只捡到 3 个 push ⇒ 被误判成 `dyn=True`，并把 `item` 记成 `0x20` ✗（技能号凑巧没错，字段错）。
- **修法**：起点**逐字节**试（步长 1）；评分改为
  **①优先"解码起点正好是桩序言 `55 8B EC`/`55 89 E5"**（照禹夏的 prologue 回溯口径）→ ②push 更多 → ③窗口更短。
- 复核：`0x22` 已移出 `dyn` 列表 ✓；剩下 `dyn=True` 的经字节逐个确认**都是真参数化**，例如
  - `0x66` @`0x43D031`：`55 8B EC 6A 00 6A 03 6A 66 04 89 50 E8 …`（第 4 参 = `add al,0x89` 后 `push eax`）
  - `0x76` @`0x41CDFF`：`… 6A 76 8B 45 08 83 C0 5B 48 50 E8 …`（`mov eax,[ebp+8]; add eax,0x5B; dec eax; push eax`）
    ⇒ **正是禹夏文档写的 `mov eax,[ebp+8]` + `add` 形态** ✓
  - `0x7B` @`0x42115B`：`… 6A 7B 04 83 50 E8 …`

### 问题 2（澄清，不改代码）：多解**不影响技能号**

- 现象：枚举全部起点后，"能精确铺到 call"的解常不止一个（唯一解 42 / 多解 129）。
- **决定性复核**：对每个已归属调用点，枚举 96→2 全部起点、收集各自的"结论（技能号, dyn）"：
  **技能号在所有解下完全一致**（样本：号 `0x00` 的解给出 `(0,False)` 与 `(0,True)` —— 号都是 **0** ✓；
  `0x01`→1、`0x02`→2、`0x0C`→12、`0x11`→17、`0x12`→18 同理）。
- ⇒ 多解只影响"是否读到第 4 个立即数"（即 `dyn` 标志），**不影响技能号**；
  扫描器采用"序言优先"评分取到的是真解 ✓。**`dyn` 标志仅供内部参考，不作为面板显示依据**（面板不显示它）。

### 结论（本改动的可信度）

- 「未解析 41→24、解出号 164→171、无桩号 97→90」**这三个数字成立**，且技能号维度经独立枚举验证**稳定** ✓
- 新增的工具级结论：**桩判定评分 =（序言优先, push 数, 窗口长度）**；起点必须逐字节试，步长 2 会漏对齐。
