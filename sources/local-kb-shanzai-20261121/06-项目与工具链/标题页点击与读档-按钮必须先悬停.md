# 标题页点击与读档：按钮必须"先悬停再点击"（2026-10-15 定案）

> **触发**：用户口径「每一次自动读取识别读档…而且也没有强制按第一个读档去读，你在干什么呀？」
> 本页把「标题页为什么总点不中」这件事一次说清，避免下次再绕。

## 结论速览

1. **★ 自绘按钮必须先 hover 再点击**：`SetCursorPos` 之后**只等 0.2 秒就点击 ⇒ 一律无效**；
   等 **0.5~0.6 秒**让游戏收到 hover 再点击 ⇒ **立刻弹出**「读取进度」。
   这是本会话反复"没点中"的**唯一根因**。
2. **坐标要按客户区比例算，不能硬编码**：本机客户区实测出现过 **960x728 / 800x550 / 640x440** 三种
   （DPI 与窗口状态不同）。基准（960x728）下「烽烟再起」= (686,220)，
   比例 `686/960 = 0.7146`、`220/728 = 0.3022` ⇒ 800x550 时 = **(571,166)**、640x440 时 = **(457,132)**。
   实测两组比例**完全一致**（`686/960 = 541/640`），证明比例法可用。
3. **⚠ 但比例法在"菜单布局真的变了"时会点错项**：本会话点 (571,166) 弹出的是 **「结束游戏」**，
   说明当时标题页的菜单项位置/数量与基准不同 ⇒ **盲点有风险，可能误关游戏**。
   ⇒ 每次点击后必须**验证弹出的是不是预期对话框**；不确定就重新测量。
4. **R1 已有硬断言**：`_自动读档进战场.py` 会检查确认框 `Static` 文本必须以 `进度No.001` 开头，
   不匹配就**点「否」退出**（第 606 行附近）⇒ 读档合规性有保障，不需要另写。
5. **权威读档入口是 `_自动读档进战场.py --go-safe`**（由 `_42结束回合.load_001()` 调用）。
   **不要再新写读档脚本**（工作区已有 50+ 个）。

## 已确认事实

### 点击协议
* 标题页「烽烟再起」是**自绘**、无控件可抓；但 `读取进度` 与 `读取` 确认框都是**标准 `#32770`**，
  内部 `SysListView32` / `Button` 有真实控件矩形 ⇒ **对话框部分可以用控件矩形算坐标**。
* `click_screen()` 原先只有 `time.sleep(0.2)`（`_自动读档进战场.py`），已改为 **`hover=0.55`**。
* 物理点击（`SetCursorPos` + `mouse_event` 左右键）是**唯一可靠**方式；
  `PostMessage`/`SendMessage` 的鼠标消息对标题页**无效**（本会话实测 down/up/dblck 全无效）。

### 读档后的流程
* 读档成功 ⇒ 先进入**出战准备界面**（「氪金系统／桃园三结义／刘备军主营」，右下有「→／取消／保存」），
  **不是**直接进战场 ⇒ 判据要用**战场宽 `[0x4B422C] > 0`**，不能只看"对话框消失"。

## 证据来源
* 实测：`SetCursorPos(1125,421)` → 等 0.5s → 左右键 ⇒ 弹出 `#32770 '读取进度'`（本会话，SHA `F2179C1F…` 时期）。
* 实测：同样坐标只等 0.2s ⇒ 连续重试全部"没生效"。
* 实测：客户区三种尺寸下 `686/960`、`220/728` 比例一致。
* 实测：点 (571,166) 在该次布局下弹出 **「结束游戏」**（反例，说明必须验证弹出内容）。
