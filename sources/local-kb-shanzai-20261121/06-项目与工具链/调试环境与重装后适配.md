## 实现·使用方法

1. **先确认调试器活着**：`_x32.cmd state`。返回 `stopped` 表示没有会话（正常）；返回 `paused` 表示会话已就绪，可直接反汇编。
2. **要读/要写内存**：会话必须是 `paused`；`running` 状态下 `memory_read` 报 `-32001 Debugger is not paused`。
3. **要抓实机战斗数据**：管理员启动游戏 → 进战场 → `debug_attach_pid`（**别**用 `debug_init` 跑游戏）。
4. **改完文件要复读**：任何"写入 → 回读"都要像能力自检那样留证据（原值/新值/还原值三点）。
5. **每次收尾**：跑 `_x32_收尾清理.py --stop`，确认断点为 0、测试进程退出。

## 风险与边界

- **坑①（最隐蔽）**：PowerShell 5.1 + GBK 代码页读**无 BOM** 的 UTF-8 `.ps1` 会按 GBK 解码，中文字符串产生"字符串缺少终止符"等语法错误，看起来像脚本写错了，其实是编码。**所有含中文的 .ps1 必须存成带 BOM 的 UTF-8**。
- **坑②**：`.cmd`/`.bat` 里的中文注释在 936 代码页下会被拆行当成命令执行（实测报 `'mcp（HTTP' is not recognized`）。**批处理只写 ASCII 注释**。
- **坑③**：`Add-MpPreference` 在 360 接管 Defender 后必失败（`0x800106ba`），不要把"加 Defender 排除"写进任何自动化步骤。
- **坑④**：`memory_allocate` 得到的新页，**写入后立刻 `memory_read` 会报 `-32010 Memory not readable`，等待约 1.5 秒后可读**。`memory_get_info` 报告该页为 `MEM_COMMIT / PAGE_READWRITE`（OS 侧确实可读）⇒ 这是 **x64dbg 页缓存/MCP 侧**的现象，不是 360 拦截、也不是真的读不到。**读写改游戏自身模块（`0x400000`–`0x4xxxxx`）不受影响**，故对打补丁/断点无实际障碍。
- **坑⑤**：`debug_get_state` 与 `debug_init` 之间存在竞态，刚 init 完查可能仍是 `stopped`；必须轮询（本页脚本统一用 `wait_paused()`）。
- **坑⑥（bat 传中文名的坑，最费时间）**：`.bat` 里 `call _pyrun.cmd _x32_加载Ekd5.py` 这种**把中文脚本名写进 bat** 的写法会失败，python 收到的是 `_x32_\ufffd\ufffd\ufffd\ufffdEkd5.py`（文件名被替换字符污染，报 `No such file or directory`）。同一个命令在 pwsh 里 `cmd /c call ...` 却正常 ⇒ 属 bat 上下文特有。**处置**：`_生成-ASCII包装器.py` 生成 `run_load.py` / `run_verify.py` / `run_caps.py` / `run_cleanup.py`，bat 只调这四个 ASCII 名。
- **坑⑦（`chcp 65001` 是负优化）**：为了"让 UTF-8 的 bat 能显示中文"而加 `chcp 65001`，结果 cmd 把 **GBK 编码的 bat** 里的中文文件名参数按 UTF-8 解 ⇒ 反而坏掉。**正确组合是：bat 存 GBK + CRLF，且不要 chcp**（本机控制台本来就是 936）。
- **坑⑧（输出编码双向）**：python 输出被 DSH/PowerShell 管道采集时按 GBK 解码会中文乱码；而控制台里按 UTF-8 输出又会乱码。**处置**：`_dsh编码引导.py` 按"是否 `isatty()`"分流——重定向时强制 UTF-8、真实终端保持系统编码，并统一加 `errors="replace"` 兜底，保证任何字符都不会让脚本崩。读输出前在 pwsh 里设 `[Console]::OutputEncoding = [Text.Encoding]::UTF8`。
- `script_execute` 在本插件里**始终**返回 `Method not allowed`；要恢复运行请用 `debug_run`，不要在脚本里依赖 `script_execute`。
- `memory_read` 单次上限 **768 字节**（旧记录：896 返回空），大块读取要分段。
  ⚠️ 本条的**原始实验记录已找不到**（全库只有转述）⇒ 属待复测项，见 `待验证清单.md` 同轮条目。
- 本页的"能力矩阵"是**在 360 主动防御开启状态下**取得的；若日后 360 版本升级或改策略，需重跑 `_x32_能力自检.py` 复核。

## ★ 控制台/脚本输出编码口径（2026-10-24 固化，工具侧唯一合规写法）

**判据（不是"乱码"，是崩）**：本机 `python` 默认 `sys.stdout.encoding = gbk`、`utf8_mode = 0`。
脚本只要打印 GBK 编不出来的字符（`⇒ ✓ ✗ ⚠ ★ ✅ ❌ ⇄ ↔ − ² ✔ ✘ 📖` 等），
在真实控制台或被管道采集时 **直接抛 `UnicodeEncodeError` 异常退出**：

    _知识库体检.py:386 print(text)
    UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'

⇒ 症状常被误读成"工具坏了/这页体检跑不出来"，实际只是**一个字符**让进程死掉。

**唯一合规处置**：用库内 `_dsh编码引导.py:22 init_stdio()`（重定向→UTF-8、真终端→系统编码，
一律 `errors="replace"` 兜底，永不因打印崩掉）。惯用插入块（`_静置体检.py:64-70` 是样板）：

    sys.path.insert(0, HERE)
    try:
        from _dsh编码引导 import init_stdio
        init_stdio()
    except Exception:
        pass

**禁止的"绕过"**（都已实测是负优化，见本页坑⑥⑦）：
`PYTHONIOENCODING=utf-8` 临时救场、`PYTHONUTF8=1`（会把 cmd 传来的 GBK 中文文件名解坏）、
`chcp 65001`（cmd 解析阶段已按 936 读 bat，切码页反而更坏）。这些只让**当前那次调用**好看，
下一个会话照样崩 ⇒ 必须落到脚本里。

**批量补齐与复查工具**：`大鲸鱼产生专用\_补编码引导.py`（分级判据用 `tokenize`，不靠猜）

| 级 | 判据 | 会不会崩 | 动作 |
|---|---|---|---|
| A | 代码体（注释与模块 docstring 之外）含非 GBK 字符 | 打印出来就崩 | 补引导 |
| B | 只有注释 / 模块 docstring 含非 GBK 字符 | 不崩 | 只登记 |

    python _补编码引导.py                  # dry-run 清单
    python _补编码引导.py --apply          # 补 A 级（逐份 py_compile，失败则一个字节都不写）
    python _补编码引导.py --revert         # 按插入块原文精确删除 = 字节级回滚

默认**自动排除** `_冻结证据_20261024\静置清单.md` 里出现过的 `.py`（SHA 被取证清单锁着，不许动）。

### 2026-10-26 04:17 坑⑪：同一个文件里多处就地编辑 ⇒ 「先构造后写盘」仍会**互相覆盖**（对本页坑⑩ 的**自我更正**）

**症状（本轮真实发生，非推演）**：给 `03-机制详解\AI价值体系-公式与地址表-6.6适配.md` 一次补 3 处编辑，

**根因（模式级，不是打字级）**：坑⑩ 定的写法是
「先把新内容整体构造完并断言 `count(old)==1`，再重读比对前像，最后才 `wb` 写盘」——
它是按**一条编辑**描述的。多条编辑时我照抄成了

```
for path, old, new in EDITS:
    raw = read(path)            # 每次都从"原始前像"读
    blob = text.replace(old, new).encode()
    built.append((path, raw, blob))
guard: read(path) == raw        # 写前检查：此时文件还是原始内容 ⇒ 通过
for path, raw, blob in built: write(path, blob)   # ★ 三次 wb，后一次把前一次抹掉
```

⇒ 同一文件的 N 个 `blob` 都是 **`raw + 单条编辑`** 的兄弟版本，**互相不包含**；顺序写盘的结果
= **最后一条编辑独占文件**。更糟的是两道安全机制都**报绿**：
① 每处 `count(old)==1` 断言各自成立（针对同一前像）；
② "写前重读等于前像"的并发守卫在写**之前**统一跑完，**看不到自己即将造成的覆盖**。

**正确形态（已落地，按文件累积）**：

```
files = {}                       # path -> [原始 raw, 当前 text]
for path, old, new in EDITS:
    if path not in files: files[path] = [read(path), decode(read(path))]
    assert files[path][1].count(old) == 1     # 在"已应用前序编辑"的文本上断言
    files[path][1] = files[path][1].replace(old, new)
# 收尾：每个文件只写一次；写后复读并逐条断言"新内容在场"
```

三条硬性要点：**一个文件一次写**；断言跑在**累积文本**上而不是原始文本上；
写盘后必须**按内容**校验（`新串 in 复读`），不能只看"写后 SHA 变了、字节数涨了"。

**为什么字节数会骗人**：本轮 3 处编辑各写一次，最终 `196511 → 196818 B`（涨了 307 B），
看起来像"三条都进去了"；实际只进了一条（第三条本来就最长）。⇒ **字节增量不能当编辑条数的证据**。

**与坑⑩ 的关系（自我更正，不删原条目）**：坑⑩ 治的是
