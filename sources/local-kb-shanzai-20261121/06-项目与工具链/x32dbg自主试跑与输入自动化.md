## 结论速览

- **能用 x32dbg 自己把游戏跑起来并推进到战场**，不必依赖人工启动：
  `debug_init` 加载 `Ekd5.exe` -> `debug_run` -> 窗口出现 -> 继续 `debug_run` 直到进战场。
  实测：战场宽 `0x4B422C = 6676`、59 个单位存活、我方 5 人（data 0/1/2/22/30）全部可读。
- **三个必须处理的坑**（不处理就会误判成"游戏没反应/补丁失效"）：
  1. **搜狗输入法 `SogouTSF.ime` 会频繁让调试器暂停** —— `stop_reason=breakpoint_or_exception`，
     EIP 落在 `sogoutsf.ime` / 其它系统 DLL。游戏被暂停时**完全不响应输入**。
     处置：`_x32保活.py` 轮询 `debug_get_state`，一 paused 就 `debug_run`。
  2. **前台窗口会被抢** —— `GetForegroundWindow()` 有时返回 `0x0`，此时 `keybd_event`/`mouse_event` 全部无效。
     处置：`AttachThreadInput` + `ShowWindow(SW_RESTORE)` + `SetForegroundWindow` + `SetFocus`（见 `_强激活并按.py`）。
  3. **点击坐标必须换算** —— 截图是**整个窗口**（含工具栏 122px），客户区原点 ≠ 窗口原点。
     换算：`客户区坐标 = 截图坐标 − (ClientToScreen(0,0) − GetWindowRect().left/top)`。
- **判断"输入是否生效"不要用画面 hash**：菜单有 hover 高亮，hash 会在两个值之间抖动，
  看着"变了"其实游戏状态没变。正确判据是**内存**（`0x4B422C` 战场宽、单位表 HP、`ctx`）。
  ⚠️ **但这只用于判断"输入有没有生效"，不能单独用于判断"在不在战场"** —— 见下方"风险与边界"的战场判据。

## 适用版本

- 主机：Windows；x32dbg + `x32dbg-mcp` 插件（`127.0.0.1:3000/mcp`）。
- 样本：`Ekd5.exe`（v5，SHA256 `12C088F9898AFD4A46F1438916ED7FA9D68B08F6F7899E1488CECD884FADE189`）。
- 关键全局：战场宽 `0x4B422C`、加速 `0x4B3D20`、战斗上下文 `0x4927F0`（常量，勿解引用）、
  单位表 `0x4A7B20 + slot*0x30`（HP 在 `+0x10`、data 号在 `+0x00`）。

```bat

```

### 3. 输入自动化的正确姿势

- 坐标换算（`_点菜单.py` 已实现）：
  ```
  off = ClientToScreen(hwnd, (0,0)) − GetWindowRect(hwnd).topleft
  客户区坐标 = 截图坐标 − off
  屏幕坐标   = ClientToScreen(0,0) + 客户区坐标
  ```
- 置前（`_强激活并按.py`）：`AttachThreadInput(fg, me, true)` → `ShowWindow(SW_RESTORE)`
  → `SetForegroundWindow` → `SetActiveWindow` → `SetFocus` → `AttachThreadInput(..., false)`。
- 记录人工点击（`_记录我的点击.py`）：轮询 `GetAsyncKeyState(VK_LBUTTON)`，记录
  屏幕坐标 / 客户区坐标 / 窗口尺寸 / 前台 hwnd / 内存状态（战场宽、存活数、ctx），
  写 `_我点击的坐标.txt`。**这是获取未知界面坐标最快的方法**。

## 风险与边界

- **`mouse_event` 走系统级输入**：会真的移动你的鼠标，请在自动化期间不要抢鼠标。
- 搜狗输入法只要在系统里就有可能持续干扰；彻底解法是切到英文或停用其 TSF，
  但**改动用户输入法属于系统设置变更，需用户同意**，本工作不擅自改。
- `debug_init` 由 x32dbg 创建进程后，**关掉 x32dbg 会一起结束游戏**；
  若想"正常玩 + 事后附加"，应当先普通启动游戏，再 `debug_attach_pid`。
- 战场判据**不要用窗口尺寸**：标题页实测 `808x611`、战场 `1208x971`，
  而知识库另有"标题页 646x489"的口径（可能是不同分辨率），尺寸不可靠。
  可靠判据是 `0x4B422C > 0` 或单位表 HP>0 的个数。
  ⚠️ **口径补强（2026-10-14 全库审计）**：**只看内存会被上一局残留骗到** ——
  实测读档失败后标题页仍保留"我 5 / 敌 42"的单位表数据，战斗结束后单位数组**也不会清零**。
  现行唯一判据是**三者同时成立**：
  `SmallMap` 控件可见 **且** 主窗口宽 > 900 **且** `0x4B422C`（战场宽）> 0。
  详见 `03-机制详解/自动战斗-识别与驱动.md` 与纠错台账同轮条目。
