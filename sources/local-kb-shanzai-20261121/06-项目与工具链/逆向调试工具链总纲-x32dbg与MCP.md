## 结论速览

- **两类问题必须分开看，这是绝大多数"反复出现的异常"的真正来源**：
  1. **工具层**：MCP 通道、脚本调用方式、会话状态机 —— 本页第 2、3 节给契约与故障矩阵。
  2. **知识层**：同一个坑在多个文档各写一遍、且深浅不一 —— 本页第 6 节给唯一归属表。
- **`MCP 进程活着 ≠ 调试会话存在`**。实测（2026-10-14 17:5x）：`x32dbg.exe` 在跑、3000 端口在 Listen、
  HTTP 直接 POST 返回 `{"state":"stopped"}`，而同期脚本却全线报 `空响应` ⇒ **必须先判状态，再发业务调用**。
- **最高频的三个真实故障**（都会以"调用异常"的形式表现出来，但根因完全不同）：
  | 表象 | 根因 | 处置 |
  |---|---|---|
  | 所有 `debug_*` 报 `空响应` | MCP 在、**调试会话已结束**（游戏闪退 / 已 `debug_stop`） | 先 `_x32.cmd state`；`stopped` 就重新 attach，**不要重试业务调用** |
  | 脚本越跑越卡、游戏点不动 | **命中断点把目标进程整个挂起**（软件断点） | 命中即记录、**立即 `debug_run` 放行**；用 `大鲸鱼自动战斗.py --go --breakpoint`（观测挂在推进循环上）/ `_等命中读数.py` / `_x32栈漂移探针.py` |
  | 反复 `脚本 No such file` / 中文乱码 | bat 上下文的中文文件名 + 代码页（GBK/UTF-8） | 走 ASCII 包装器 `run_*.py`；bat 只写 ASCII 注释 |

### 2. MCP 调用契约（源码级已确认）

证据：`大鲸鱼产生专用\_x32dbg.py`（桥客户端）、`_x32_抓崩溃现场v3.py:79,113`（源码注释即踩坑记录）。

| 契约 | 内容 | 违反后果 |
|---|---|---|
| **C1 握手只做一次** | `initialize` + `notifications/initialized` **每个进程只调用一次**；v3 用 `_INITED[0]` 守住 | 重复握手 ⇒ `空响应`（已实测踩坑） |
| **C2 不自写 HTTP** | 必须 `import _x32dbg` 复用已验证的桥 | 自写 URL/头 ⇒ `空响应`（已实测踩坑） |
| **C3 参数走文件** | `call <tool> <args.json>`，避开 PowerShell 引号 | 引号被吞 ⇒ 参数错、报"调用异常" |
| **C4 单目标** | 同一时刻只能对一个目标；`debug_attach_pid` 到新目标**会结束旧会话** | 以为"两个都在调"，实际前一个已经没了 |
| **C5 没有 detach** | **没有 detach 工具**；`debug_stop` 会关掉目标 | 想"断开但保留游戏"做不到，只能收尾重启 |
| **C6 状态前置** | 读/写内存、断点等要求会话 `paused` | `running` 下 `memory_read` 报 `-32001` |
| **C7 空响应不重试** | `空响应` 是**终态信号**（会话没了），不是瞬时抖动 | 反复重试 ⇒ 浪费整轮时间、并掩盖真相 |

### 3. 故障矩阵（唯一判定表）

| 返回 | 真实含义 | 是否重试 | 正确下一步 |
|---|---|---|---|
| `{"state":"stopped"}` | MCP 在、**无调试会话** | 否 | `debug_init`（离线）或 先启动游戏再 `debug_attach_pid` |
| `{"state":"paused"}` | 会话就绪、可读可写 | — | 正常执行 |
| `{"state":"running"}` | 目标在跑 | 否 | 需要读值就先设断点或暂停 |
| `空响应` | **会话已结束**（游戏闪退/已 stop）；也可能 C1/C2 被违反 | **否** | 先 `state`；`stopped` 就重新 attach，**并怀疑游戏已闪退**（查进程 + dump） |
| `-32001 Debugger is not paused` | 状态没到 `paused` | 是（轮询到 paused） | 轮询 `debug_get_state` |
| `-32010 Memory not readable` | **新分配页的页缓存延迟**（约 1.5 秒），不是权限问题 | 是（等 1.5s） | 等待后重读；模块内内存（`0x400000`–`0x4xxxxx`）不受影响 |
| `Method not allowed: script.execute` | `script_execute` 被插件禁用 | 否 | 改用 `debug_run`；批量用 `script_execute_batch`（未验证） |
| `No such file or directory` + 文件名带 `\ufffd` | bat 中文名污染 | 否 | 改用 ASCII 包装器 |
| HTTP 层连不上 | x32dbg 没开 / 端口被占 | 是 | 起 `x32dbg.exe`（管理员） |

### 4. 会话纪律（代价是真实事故）

1. **禁止无条件 `debug_run` 循环**：本引擎用异常做流程控制，放行未处理异常 = **终结进程**（已造成一次事故）。
   放行前必须读 `stop_reason`，用 `context_get_basic` / `stack_get_trace` 区分首次异常与未处理异常。
2. **命中即记录、立即放行**：抓现场的脚本"命中后不放行"会让游戏长时间挂起，
   表现是"游戏卡住不动、推进脚本狂点全打空"（用户已两次提醒）。
3. **一次不超过几个关键断点**，跑完立刻清点。
4. **收尾顺序固定**：`breakpoint_delete_all` → `debug_stop`（顺序反了会留入口断点）。
   工具：`run_cleanup.py --stop`。
5. **先进战场再 attach**；不要让调试器当启动器（除非明确要离线跑）。
6. **断点命中 ≠ 真的发生了一次攻击**：`0x405DE1` 的上层 `0x4064F1` 有 11 个调用者（预估/AI/预览/结算），
   要证明"真的打了"必须同时核对上下文变化与 HP 下降。详见 `03-机制详解/伤害路径判别-物理与策略.md`。
7. **输入法干扰**：搜狗 `SogouTSF.ime` 会让调试器频繁暂停 ⇒ 配 `_x32保活.py`；
   前台被抢用 `AttachThreadInput` 强置前，**不要**用 `SetForegroundWindow` 硬来。

### 4.1 ★★★ 启动次序：x32dbg 必须在游戏之前（2026-11-01 实机 4 组对照）

> 与本节第 5 条「先进战场再 attach」**不冲突**：那条讲的是 `debug_attach_pid` 的时机；
> 这条讲的是 **`x32dbg.exe` 进程本身何时启动**。两者是不同的动作。

| 组 | 做法 | 结果 |
|---|---|---|
| ① | 只起游戏，**不起 x32dbg** | 20 / 40 / 60 秒均存活 |
| ② | **先起 x32dbg，再起游戏** | 15 / 30 / 45 秒存活 ⇒ 这是安全顺序 |
| ③ | 游戏已在跑，**再启动 `x32dbg.exe`**（前台 / 最小化各一次） | **两次均在 20 秒内游戏进程消失** |
| ④ | 组②下 `debug_attach_pid` | 附加成功（state=running），随后 x32 进程被回收、**游戏一并消失**（与本页 C5 / `debug_stop` 终结目标同源） |

- **可证伪判据**：`Get-Process -Name ekd5` 在起 x32dbg 后 20 秒仍返回 PID ⇒ 存活；返回空 ⇒ 已消失。
- **固定做法**：① 先起 x32dbg（或在长驻终端里保活）→ ② 再起 `Ekd5.exe` → ③ 等 15s 确认 `Responding=True` → ④ 才 `debug_attach_pid`。
- **未解**：组③的机制**未查明**（未取证是谁杀的进程，只有"进程消失"这一现象 + 2/2 复现）。
  因此**不要**据此推断"x32dbg 会杀游戏"以外的任何原因；需要机制时另做取证。
- **Popen 连带回收（同窗口实测）**：本会话每条 Shell 命令结束会拆终端 ⇒ `Popen(x32dbg.exe)` 起的调试器
  被连带回收，`3000` 端口随之消失。对策：把启动放进 `run_in_background=true` 的长驻作业（起进程 + 长时间 `sleep` 保活终端），
  另发命令走桥。桥侧就绪判据 = `_x32dbg.py state` 能返回带 `state` 的 JSON（不是端口能连上就算）。

### 5. 环境坑（编码/权限）

| 编号 | 坑 | 处置 |
|---|---|---|
| 坑① | PowerShell 5.1 在 936 代码页下按 GBK 读**无 BOM** 的 UTF-8 `.ps1` | 含中文的 `.ps1` **必须带 BOM** |
| 坑② | `.cmd`/`.bat` 里中文注释在 936 下被拆行当命令 | 批处理**只写 ASCII 注释** |
| 坑③ | 360 接管 Defender 后 `Add-MpPreference` 必失败（`0x800106ba`） | 不要把"加 Defender 排除"写进自动化 |
| 坑④ | `.cmd` 必须存 **GBK + CRLF 且不要 `chcp`** | `chcp 65001` 是负优化 |
| 坑⑤ | Python 输出编码双向 | 用 `_dsh编码引导.py`（按 `isatty()` 分流 + `errors="replace"`） |
| 坑⑥ | 调试器与游戏**必须同为管理员**，否则 attach 被完整性级别拦 | `_以管理员启动游戏.cmd` / `_以管理员启动调试器.cmd` |
| 坑⑦ | 工具脚本必须**归档**才进知识库视野 | 跑 `python 大鲸鱼产生专用\_归档工具源码.py apply` |
| 坑⑧ | **知识库 md 必须带 BOM**；而 `edit` 类工具改完会**掉 BOM** | 每轮改完复检 BOM 并补齐（本会话实测 9 个文件被改掉） |
| 坑⑨ | **attach 后会停在系统 DLL，看似"卡住"**（`stop_reason=breakpoint_or_exception` 落在 `win32u/ntdll/windowmanagementapi`） | 这是**假暂停**：`debug_run` 放行即可恢复；**别当成游戏卡死或补丁失效** |

## ⛔ 故障模式：x32dbg 状态机错乱（2026-10-14 实战事故，务必识别）

### 症状（四条同时出现即可判定）

| # | 症状 | 判据 |
|---|---|---|
| 1 | **EIP 停在数据段** | 例如 `0x48E8B6`，附近是 GBK 字符串（`"MP MAX"`/`"保存"`/`"读取"`）⇒ 正常程序不会执行数据 |
| 2 | **`debug_run` 报 `success:true` 但 `state` 仍 `paused`** | 放行指令被吞 |
| 3 | **断点列表为空，却 `stop_reason=breakpoint_or_exception`** | 不是断点，是异常/状态错乱 |
| 4 | **单步陷入固定小循环** | 实测 9 条一循环：`0x48E8B6 → 0x77186C80/6C87/6C97/6C98/6C9C/6C9F/6CA0/6CA1 → 回到 0x48E8B6` |

### 已排除的原因

- **不是软件断点 `0xCC` 残留**：复读 `0x405E9A` = `89 02`（干净）；
  `.text` 段 1485 个 `0xCC` 是**编译器对齐填充**，正常。
- **不是本工作区工具留的坑**：`breakpoint_list` 为 0。

### 正确处置（**不要硬撑**）

| 步骤 | 做法 | 说明 |
|---|---|---|
| 1 | 先试 `register_set eip=0x405DE1` | 可把 EIP 拉回代码段（实测能短暂推进到 `0x426A0B`） |
| 2 | 若 EIP **又弹回数据段** ⇒ 判定错乱 | 实测弹回 `0x48E8BD`，连续 5 次同址 |
| 3 | **立刻 `debug_stop` 结束会话** | 不要再反复 `debug_run`（越拖越乱） |
| 4 | 重启游戏 + 重新 attach | `_以管理员启动游戏.cmd` |

**教训**：`debug_run` 连续 3 次无效就应当判定调试器异常并收工，
**不要为了"再试一次"反复放行**——本次因此浪费约 10 分钟并最终仍需重启。
`debug_stop` 会终止被调试进程（实测游戏进程消失），**动手前先确认存档时间**。

### 预防

- 出现**被调试程序闪退/异常**（如本项目 v6/v7 补丁闪退）后，
  **先 `breakpoint_delete_all` + 结束会话再重启游戏**，不要在同一会话里继续挂断点；
- 长时间反复 `debug_run` 是危险信号，应改用**只读采样**或**重新 attach**。

## ★ 2026-10-19 共享速查（跨 AI）+ 并发占用规则

> 本节给 **DSH 与 Codex 共用**：两人都能驱动同一个物理调试器，所以除了技术事实，还必须约定**谁在用**。
> 上级权威仍是本页第 1~3 节（入口 / 契约 / 故障矩阵）；本节只补**实践级硬事实**与**并发约定**。

### 1. ★★ 跨 AI 并发占用（最容易互相打脸的一条）

- **两个 AI 用的是同一个 x32dbg 进程 + 同一套桥脚本**（`大鲸鱼产生专用\_x32dbg.py` / `_x32.cmd`）。
  **Codex 侧没有单独的 x32 MCP 注册**（`~/.codex/config.toml` 里只有 `kb` 与 `node_repl`）⇒ 它走的是同一套 Python 桥。
- **`debug_attach_pid` 到新目标会结束旧会话**（本页 C4），**且没有 detach**（C5）
  ⇒ **谁先 attach，谁就独占**；另一方此时 attach / `debug_stop`，会把对方正在跑的取证直接打断，
  而对方只会看到 `空响应` / `stopped`，**很容易误判成「游戏崩了」**。
- **动手前先取证再决定碰不碰**：
  ```bat
  大鲸鱼产生专用\_x32.cmd state        :: 有会话吗、stopped / paused / running
  Get-Process x32dbg                    :: 谁起的、起了多久
  台账末尾 10 行 + 交接.md               :: 另一方是否正声明占用
  ```
- **约定**：① 占用方**必须在台账写一行**「我正占用 x32dbg 做 X，预计到 Y」；
  ② 非占用方**只用**只读采样（`_减伤实机采样.py` / `_42结束回合.py --probe`）或离线工作台（`_dsh反汇编工作台.py`）；
  ③ 收尾固定 `breakpoint_delete_all` → `debug_stop`，并在台账写「已释放」。

### 2. 十条实践级硬事实（都会以「调用异常」的形式反咬）

| # | 事实 | 处置 |
|---|---|---|
| 1 | **日志断点 `breakpoint_set_log`**：命中**不暂停**、`hit_count` 照常累加 | 只想统计「执行了没有／几次」时**首选它**，别用会挂起进程的普通断点 |
| 2 | **原生条件断点在命中时先递增计数、之后才求值 condition** | `hit_count>0` 只证明「执行到该地址」，**不证明条件成立**（AGENTS.md §12）|
| 3 | **搜狗输入法造成「假暂停」**：抓到 `EIP=0x5676CC90`（`sogoutsf.ime+0xACC90`）**不是崩溃** | 改用日志断点，或并行跑 `_x32保活.py` 自动放行 |
| 4 | `script_execute` 在本 bundle **不可用**（`-32003 Method not allowed`）| 用 `script_execute_batch`，或把逻辑写进 Python 侧 |
| 5 | **后台启动调试器会失败**（`run_in_background` 起不来 x32dbg）| **必须前台**跑 `_42起桥并附加.py` |
| 6 | `memory_read` 对**新分配页**有约 **1.5 秒缓存**（`-32010`）| 不是权限问题，**重试即可** |
| 7 | **`debug_stop` 后目标常留「未响应」态** | 需要干净初始态时**杀进程重启**，别在脏态上继续判定 |
| 8 | **被附加过的进程退出后会变僵尸**（`HasExited=True` 仍占进程表）| 写 `Ekd5.exe` 前**先关 x32dbg**，否则 `_dsh写锁.py` 会以「游戏在运行」拒绝 |
| 9 | **`_x32保活.py` 有 40 次上限**；`state=paused` 但 `Responding=True` **不等于卡死** | 别把「看起来暂停」当死机 |
| 10 | **死规则：先放行再叫人** | 要用户动手前，循环 `debug_run` 到 `running` 且 `Responding=True`，**打印凭据**再叫人（AGENTS §7）|

### 3. ★ 一个容易被当成「规则打架」的口径（裁决如下）

AGENTS §6 要求「跑多回合战斗／观察闪退**必须**已附加调试器」，而 §3.6 坑① 又要求「判**补丁是否崩**必须**无调试器**跑」。
**两者不矛盾，用途不同**：

| 目的 | 必须的姿势 | 理由 |
|---|---|---|

| **判定**：这个补丁**活不活**、行为对不对 | **无调试器**跑 | 附加／暂停／`debug_stop` 会污染存活判定（曾把「自己杀进程」误报成崩溃）|

## ★ AGENTS.md §6 强制规则（2026-10-21 迁入）

- **任何会跑多回合战斗 / 观察闪退 / 取证时序的测试，必须在 x32dbg 已附加的状态下进行。** 只看"进程没了"只能得到结果；要得到原因必须有停下时的寄存器与调用栈。
- **选型定案：只用 x32dbg，且不再讨论/对比其它调试器。** 本样本 `Ekd5.exe` 是 32 位 PE32 / x86；工作区已有 x32dbg MCP 桥（端口 3000）。
- **标准动作**：`_x32_抓崩溃现场v2.py --attach --secs N`（附加 + 轮询，崩溃即抓 EIP/全寄存器/反汇编/调用栈/异常码）；`大鲸鱼自动战斗.py --go --breakpoint`（观测挂在推进循环上 + 收尾自动删自设点；全清用 `--cleanup-bps`。旧 `_x32断点探针.py` 已退役）；`_先放行再叫人.py`（设断点后循环放行到 running）。
- **禁止**：在没有调试器监测的情况下把"闪退/卡住"当成可归因的结论；也禁止为此另写新的崩溃抓捕脚本（库内已有 `_x32_抓崩溃*.py` + `大鲸鱼自动战斗.py --breakpoint`（旧 `_x32断点探针.py` 已退役））。
- **收尾固定**：`breakpoint_delete_all` → `debug_stop`。
- ⚠ 附加会让被调试进程在退出后变僵尸（`HasExited=True` 但仍占进程表）⇒ 写 `Ekd5.exe` 前必须先关 x32dbg，否则 `_dsh写锁.py` 会以"游戏正在运行"拒绝写入。
- 本页上文"抓崩溃优先 minidump"是早期工具排序；**强制规则以本节为准**，minidump 只作补充证据。

## ★ 2026-10-25 补充：同名僵尸 `Ekd5` 会连带打坏「找 pid / Responding」

- **现象**：`tasklist` 见到 12 个 `Ekd5.exe`（11 个 20 K 僵尸 + 1 个 41 MB 活进程）。
  `pid_of()` 取第一条 ⇒ 返回僵尸：`OpenProcess` 成功、`ReadProcessMemory` 全失败、
  `GetLastError()=0`、`Mem.rd` 全 `None`；`responding()` 因 PowerShell 对同名数组做成员枚举，
  恒返回 `None`，`state=running` 也确认不了「可操作」。
- **已修（`_ccz公共.py`，2026-10-25）**：
  ① 新增 `pid_readable(pid)`（读 `0x400000` 两字节，僵尸必失败）；
  ② `pid_of_game()` 先剔除不可读进程再比窗口面积（顺带修「**最小化**时 rect=`(-32000,-32000)` ⇒
     面积全 0 ⇒ 回落 `pids[0]`（僵尸）」）；
  ③ `responding()` 改为 `Get-Process -Id <pid_of_game()>`，不再按映像名取数组。
- **判定口径**：新脚本一律 `pid_of_game()`。若 `Mem.rd` 全 `None` 而 `OpenProcess` 成功，
  **先怀疑僵尸**，不要归因于「游戏没进战场」。
- 僵尸仍会挡住 `_dsh写锁.py`（见上文第 8 条）⇒ 写 `Ekd5.exe` 前照旧先关 x32dbg。
