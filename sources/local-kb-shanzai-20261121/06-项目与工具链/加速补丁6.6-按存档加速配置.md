## 结论速览

- **用户报的“保存配置不管用、读档后回到初始”不是保存失败**：`保存配置` 确实写进了 `patch\xiaoan66\pl_06.ini`，但 `LoadSettings()` 结尾**故意把超级加速与阶段加速强制关掉**（`Proxy.cpp` 的 `gSettings.superEnabled = false; gSettings.phaseEnabled = false;`，`ConfigTests.cpp` 里还有一条断言 `skip modes forced off on restart`）。所以哪怕值存住了，**下次启动也一定回到“关”**，看起来就像没保存。

## 已确认事实

### 1. 现有配置流（改动前）

| 环节 | 位置 | 行为 |
|---|---|---|
| 配置文件 | `Proxy.cpp`（`gConfigPath`，由 `Initialize` 拼成） | `<游戏目录>\patch\xiaoan66\pl_06.ini`，**74 行十进制数**，每行一个字段 |
| 读取 | `Proxy.cpp` `LoadSettings()` | 逐行 `ParseLine` 校验；超范围回落默认；**结尾强制 `superEnabled=false; phaseEnabled=false`** |
| 保存 | `Proxy.cpp` `SaveSettings()` | 把 `gSettings` 摊成 74 行 → 写 `.tmp` → `MoveFileExW` 原子替换 |
| 入口 | 菜单 `kSave`（`Proxy.cpp`）、对话框 `IDC_SAVE`（`Ui.cpp`） | 都调 `SaveSettings()`，失败弹“配置保存失败/无法保存加速配置” |
| 字段序 | `gConfigLines[0..73]` | `0`=超级开关、`1..5`=超级五个子项、`6`=阶段开关、`7..9`=阶段三选项、`10`=滚轮微调开关、`11..13`=三阶段值、`14`=滚轮步长、`15`=齿轮开关、`16`=齿轮倍率、`35`=Ctrl→Shift、`65..69`=五个热键 |

### 2. 为什么必须用“读档”当触发点

- 补丁**已经**在游戏的 `CreateFileA` 导入表里挂了钩子（`PatchedCreateFileA` → `ObserveGuideScenarioPathA`，服务“简易攻略”）。存档同样是普通文件打开，**复用这个钩子即可识别“读了哪个存档”**，不需要反汇编引擎的存/读档函数。
- 存档文件名即天然主键：`<游戏目录>\SV\SV003.E5S`（工作区实测存在 `SV\SV000.E5S … SV900.E5S`），取 basename 并大写 → `SV003.E5S`。

## 风险与边界

- **未编译、未实机验证**：本轮无 shell / 无 MSVC，以上全部是源码级实现 + 自检；首次构建失败时优先看 `/WX` 警告。
- **读档菜单的“读档头”**：若引擎在打开菜单时逐个读存档文件，本实现会在“安静 300ms 后”按**最后一个**被打开的名字套用一次；用户真正点选读档时该文件会再被打开一次，最终状态仍是所选存档（中间可能有一次短暂切换）。若实测不能接受，可改成“读档后再校验一次”或加 `ReadFile` 钩子按读取长度过滤。
- **并发窗口**：`ObserveSaveName` 与 `ApplyPendingSaveProfile` 之间用 SRWLOCK 保护名字与时间戳；极端情况下（应用与新一轮打开重叠）可能漏掉一次切换，下一次打开会自愈。
- **只识别扩展名 `.E5S`**：若某个派生版用别的扩展名（或存档放在别处），需要同步调整 `SaveNameFromPath*`。
- **行为变更（必须有意识）**：改动前“每次启动/读档后超级与阶段一律关”；改动后**读档会恢复你保存过的开关状态**（该存档有独立段就用独立段，没有就用全局保存值）。想彻底关掉，就在配置页取消勾选后点`保存配置`（全局变成关），之后未单独配置的存档读档时也是关。
- 本次落地时实测：游戏目录**已装过 2026-10-13 的旧构建**（`Koeicda.dll` 743424 字节、`GearNtKe.dll` 112640 字节、`patch\xiaoan66\install.ini` + `pl_06.ini`），且验证时 `Ekd5.exe` 正在运行 ⇒ **安装前必须关游戏**，否则 DLL 被占用。

### 4. 新行为（切换语义，用户口径：选一个就一直按它走，直到再按一次停止或切到别的模式）

```cpp
void SwitchAccelerationMode(bool super) {   // 热键与菜单共用
    bool& target = super ? gSettings.superEnabled : gSettings.phaseEnabled;
    bool& other  = super ? gSettings.phaseEnabled : gSettings.superEnabled;
    if (target) target = false;             // 同一模式再按一次 = 停止
    else { other = false; target = true; }  // 打开目标并自动关掉另一个 = 切换
}
```

- 文案：按 Z ⇒ 超级开、阶段关；再按 Z ⇒ 全关；按 X ⇒ 阶段开、超级关；再按 X ⇒ 全关。
- `ConfigTests` 新增 5 条断言（开/切换/切回/同模式停止/阶段同理）⇒ 本版 **35 项 0 failures**。
- 引擎侧不变：设置一旦应用就是**静态代码补丁**，回合推进不会重置（"后续回合都按这个"由设计保证）。

### ⚠️ 5. 实机暴露的真问题：自动存档把用户刚按的 Z 翻回去（2026-10-15，已修）

**现象（用户口径）**："当回合可以 Z 加速，下回合恢复 X 了"。

**证据（`_看加速状态变化.py` 后台逐帧记录 + 存档 mtime）**：

```
01:23:20.828 超级=开 阶段=关   ← 用户按 Z，切换语义生效 ✓
01:23:22.030 超级=关 阶段=开   ← 约 1.2 秒后自己翻回阶段
01:23:23.232 超级=开 阶段=关
01:23:29.240 超级=关 阶段=关   ← 再按 Z = 停止 ✓（语义本身没问题）
… 反复来回，同期 SV000.E5S 的 mtime 一直在刷新（= 自动存档）
```

### 1. ★★ 核心公式（`GearNtKe.cpp:42-97`）

```c
int    ClampSpeed(int value)      { return value < -128 ? -128 : (value > 128 ? 128 : value); }
double SpeedMultiplier(int value) { return pow(2.0, ClampSpeed(value) / 10.0); }        // ★ 倍率 = 2^(v/10)
UINT   ScaleInterval(UINT interval, double speed) {                                     // ★ SetTimer 间隔
    double scaled = interval / speed;
    if (scaled < 1.0) return 1;
    if (scaled >= 2147483647.0) return 0x7fffffffU;
    return static_cast<UINT>(scaled);
}
```

- **倍率 = `2^(v/10)`**，`v` 夹紧 **`[-128, +128]`**：`v=10`⇒**2×**、`v=20`⇒**4×**、`v=0`⇒**1×**、`v=-10`⇒**0.5×**
  （`GearTests.cpp:142-147` 断言：`SpeedMultiplier(0)==1.0 / (10)==2.0 / (20)==4.0 / (-10)==0.5`；`SetSpeed(±100000)` ⇒ `GetSpeed()==±128`）
- **`SetTimer`/`timeSetEvent` 的间隔 = 原间隔 ÷ 倍率**（下限 1、上限 `0x7FFFFFFF`）——即"**倍速 → SetTimer 参数**"的换算就是这一行 `interval / speed`。

### 2. 六个被拦截的时间 API 与虚拟时钟（`GearNtKe.cpp:133-201, 292-296`）

| 原 API | 替换实现 | 语义 |
|---|---|---|
| `GetTickCount` | `AcceleratedTick` | `虚拟tick += 真实间隔 × 倍率` |
| `timeGetTime` | `AcceleratedTime` | 独立"多媒体纪元"，同样按倍率推进 |
| `QueryPerformanceCounter` | `AcceleratedCounter` | `虚拟计数 += 真实间隔 × 倍率 × (1000/frequency)`（`counterMilliseconds = 1000.0/frequency`） |
| `GetMessageTime` | `AcceleratedMessageTime` | `虚拟tick + (真实消息时间 − 真实tick) × 倍率`（**与 tick 共享纪元**） |
| **`SetTimer`** | `AcceleratedTimer` | `realTimer(hwnd, id, ScaleInterval(interval, 倍率), cb)` |
| `timeSetEvent` | `AcceleratedEvent` | `realEvent(ScaleInterval(delay, 倍率), …)` |

- **`rawSpeed == 0` 时全部走原生路径**（不做缩放）；`UnIntercept` = 卸载这六个钩子；`GetSpeed` = 返回 `rawSpeed`。
- 初始化（`Initialize`，`InitOnceExecuteOnce` 懒加载）：`GetModuleHandleW/LoadLibraryW` 取 **`kernel32.dll / user32.dll / winmm.dll`**，
  再 `GetProcAddress` 解析 **`GetTickCount / timeGetTime / QueryPerformanceCounter / GetMessageTime / SetTimer / timeSetEvent`** 并存进全局（`realTimer` = 原版 `SetTimer` ⇒ 这就是导出 **`OldSetTimer`** 的来源）。
- **`DllMain` 只调 `DisableThreadLibraryCalls`**（二进制反汇编 `0x640027A0` 与源码一致）⇒ 钩子**不在 DllMain 安装**。

## 2026-10-29 11:58 纠正：外置加速不作为战场逻辑闸门

用户纠正「加速不影响战场」后，按本页源码/二进制结论复核：外置加速补丁由 `GearNtKe.dll/Koeicda.dll` 提供，主要钩 `GetTickCount/timeGetTime/QueryPerformanceCounter/GetMessageTime/SetTimer/timeSetEvent`，并通过 `0x500AD8`（速度字）、`0x4B3D18`（阶段）、`0x500ADB/0x500E0C`（原生超级状态/忙锁）控制时序。它没有直接改写物理/策略上下文、单位 HP/MP 或伤害槽，因此不应把加速状态当作战场逻辑成立条件；测试仍以正式战场、`4018=1`、前后 probe 为硬判据，加速只作为时序背景记录。

结论：后续 P0-2/P0-1 测试不因 `0x4B3D20=0` 自动停测，也不再向该地址补写 `3`；如需研究外置加速本身，另读 `0x500AD8/0x4B3D18/0x500ADB/0x500E0C` 与 DLL 配置，不把它们混入战场伤害判据。证据等级：L1-S（源码/二进制页）+ L1-T（入口代码与离线夹具）。
