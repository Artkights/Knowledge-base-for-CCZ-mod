## 二、昨天为什么搞不定（6 次失败的真实分布）

| 版本 | 挂点 | 位置性质 | 结果 |
|---|---|---|---|
| v6 / v6b / v6c / v6d | `0x405DE1` 内两处 | 伤害公式函数体内 | **每个轮次必崩** ❌ |
| v7 | `0x4E6052`（MOD 易伤函数内）| 别的函数，稳定 | 推进 4 轮次存活，但**分支命中 0 次** ⇒ **无效果** ❌ |
| v8 | `0x43BF1C`（公式出口）| **`0x43BC5A` 函数体内** | 表现不稳 ❌ |
| v9 | `0x43BF0E` | **同上函数体内** | 表现不稳 ❌ |
| v10 | `0x43BE2E`（公式中段）| **同上函数体内** | **无调试器下推进 1 回合即进程终止** ❌ |

### 失败的根因（当时就已定案，只是没人能绕开）
> **只要在物理伤害公式 `0x43BC5A` 的函数体内做 inline hook，游戏推进回合就会终止。**

原因：该函数**被多条路径共用**，且内部有 **6 条 `jmp` 旁路共享寄存器/栈不变量**：
`0x43BD06→0x43D3B5`、`0x43BDC7→0x43F1E8`、`0x43BE7C→0x43EAC3`、`0x43BEA0→0x4E3124`、`0x43BEE8→0x43EA4F`、`0x43BF0E→0x43BC2F`
⇒ 在函数体内动 5 字节，会破坏未被覆盖的那些路径。

**⇒ 昨天全部 6 次尝试，本质上都在"函数体内找位置" —— 层面选错了。**

## 三、今天突破的三个关键

### ① 换层面：从「函数体内」改到「链式修正的编排点」
现读发现物理伤害的收尾是一条**整齐的链**，每个特技一环：
```
0x43BC5A …（物理伤害公式）… 0x43BDC7  jmp 0x43F1E8
0x43F1E8 …（特技修正链：push 攻击者[ebp-0x2C] / 目标[ebp+8] / 伤害[ebp-4] → call → mov [ebp-4],eax）…
0x43F27F  jmp 0x43BDCC      ← ★ 链尾（本补丁的挂点）
0x43BDCC …（NOP）… 0x43BF06 call … 0x43BF15 cmp/封顶 … 0x43BF1C 返回
```
**`0x43F27F` 的两个硬性质（现读确认）**：
- **xref 0 处引用** ⇒ 只能从链上**顺序走到**（唯一入口）
- 它跳的 `0x43BDCC` **也只被它自己引用** ⇒ **无绕过路径**（覆盖率 100%）

### ② 用「同长度替换」，不动指令边界
`0x43F27F` 原本就是 `E9 48 CB FF FF`（`jmp`，5 字节）⇒ 换成 `E9 F7 8B 01 00`（仍 5 字节）
⇒ 这是 §3.6 判据里**最安全的形态**（只改操作数/操作码，不移动边界、不复用寄存器契约）

### ③ 守住寄存器契约（这条最容易漏）
链返回后 `0x43BF15 cmp eax, ecx` **仍在用 eax/ecx** ⇒ 注入体必须**显式保存恢复**：
```asm
push eax / push ecx / push edx
... 业务 ...
pop edx / pop ecx / pop eax
```
（历史上 v10 第一版就漏了 `PUSH EAX`，覆盖了前一条 `CALL` 的返回值）

## 四、技术细节（可复现）

### 注入体（38 字节 / 17 条指令）
```asm
0x457E7B  50              push eax
0x457E7C  51              push ecx
0x457E7D  52              push edx
0x457E7E  8B 4D 08        mov  ecx, [ebp+8]      ; 目标（实测：永远是挨打方）
0x457E81  8A 41 1E        mov  al,  [ecx+0x1E]   ; 异常状态字节
0x457E84  A8 C0           test al, 0xC0          ; 中毒位
0x457E86  74 11           jz   0x457E99
0x457E88  8B 45 FC        mov  eax, [ebp-4]      ; 伤害
0x457E8B  6B C0 78        imul eax, eax, 120     ; ×1.2
0x457E8E  99              cdq
0x457E8F  B9 64 00 00 00  mov  ecx, 100
0x457E94  F7 F9           idiv ecx               ; 正数截断 ⇒ 向下取整
0x457E96  89 45 FC        mov  [ebp-4], eax
0x457E99  5A 59 58        pop edx / ecx / eax
0x457E9C  E9 2B 3F FE FF  jmp  0x43BDCC
```

## 五、今天验证的过程（也是可复用的取证法）

1. **频率测量**：挂 `0x43F27F` 断点，**空闲 20 秒命中 0 次** ⇒ 判定低频、可安全挂点（上次栽在"高频断点把游戏卡死"）
2. **参数归属**：命中时读 `[ebp-4]/[ebp+8]/[ebp-0x2C]`，靠"同两单位角色对调（一次攻击、一次反击）"确认 **`[ebp+8]` 永远是挨打方**
3. **状态字节**：改用**纯内存快照**（`_单位状态快照.py`，不挂断点、不暂停游戏）⇒ 全表 `+0x1E` 只有 `0x00`×245 与 `0xC0`×5，与用户"447 中毒"相互印证
4. **实机**：写盘后由用户实测确认可用

## 六、可复用的四条结论

1. **不要在"数据流函数体内"改，改在"链式修正的编排点"** —— 这是本次最大的方法论收获
   （物理链的编排点 = `0x43F1E8..0x43F27F`；以后想"对每次物理伤害追加一步修正"，都优先考虑这里）
2. **`0x43F27F` = 已验证可用的"链尾挂点"**（0 引用、无绕过、同长度 5 字节）
3. **`0x457E7B` 起洞区已占用 38 字节**（后续从其后算起；写前必过 `_注入地址占用登记.py --check`）
4. **查桩/查 id 必须同时扫 `6A xx`（imm8）与 `68 xx 00 00 00`（imm32）** —— `0xB1` 就是漏扫 imm32 被误判"无桩"
