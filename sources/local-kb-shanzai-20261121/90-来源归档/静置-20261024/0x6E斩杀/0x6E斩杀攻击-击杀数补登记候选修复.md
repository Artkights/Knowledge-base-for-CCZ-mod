### 一、`0x40CFF6`（斩杀函数）完整语义（143 B 已逐条反汇编）

```
0x40CFF6  push ebp / mov ebp,esp / push 0 / sub esp,8
0x40CFFE  call 0x45D2DA          ; ★ 特技桩：push 0,0,29,110(0x6E) → call 0x4101D9
0x40D003  test eax,eax / je 0x40D081   ; 没有 0x6E 特技 ⇒ 直接返回 0
0x40D008  ecx = [ebp+0xC]        ; 入参 = 物理伤害上下文 ctx（伤害数组在 ctx+0x84 ⇒ 与 0x4037DD 同一下标口径）
0x40D00B  ecx = [ecx+0x0C]       ; ctx+0x0C = 攻击者战场单位记录
0x40D00E  call 0x40658F          ; 单位记录 → 人物记录（ECX 进 / ECX 出）
0x40D013  eax = movzx word [ecx+0x35]   ; ★★ 读的是【攻击者杀敌数】！
0x40D017  push 50
0x40D019  call 0x40BAD4          ; 0x40BAD4 = `xor edx,edx; idiv [esp+4]; ret 4` ⇒ eax = 杀敌数 / 50
0x40D01E  eax += [ebp-0x10]      ; 阈值 = 父栈槽 + 杀敌数/50
0x40D021  push eax
0x40D022  loop:  cl = [ctx+0x10+i] ; 目标列表，0xFF 结尾
0x40D031  eax = [ctx+0x84+4i]    ; 该目标伤害槽
0x40D03C  [ebp-0xC] = eax        ; 累计伤害
0x40D03F  call 0x4061F9          ; 取目标单位记录
0x40D047  call 0x40658F          ; → 目标人物记录
0x40D04C  call 0x407263          ; （目标相关数值，非 0x426BA0 —— 旧推断有误）
0x40D055  call 0x425AD9          ; 百分比：eax = [ebp+0xC]*[ebp+8]/100（既有结论）
0x40D05A  [ebp-0xC] += eax       ; 累计再加
0x40D060  call 0x41B500          ; 目标 HP
0x40D065  cmp [ebp-0xC], eax / jb 0x40D079   ; 累计 < HP ⇒ 不斩
0x40D077  mov [ctx+0x84+4i], eax ; ★ 斩杀 = 把伤害槽写成 HP（= 恰好致死）
0x40D079  inc [ebp-4] / jmp 0x40D022
```

**两个由此得出的硬事实**：
1. **杀敌数 `+0x35` 参与斩杀阈值计算**（`杀敌数/50` 累加到阈值）⇒ 杀敌数不是纯战绩字段，改写它会**反过来影响后续斩杀判定**。
2. 斩杀函数的唯一调用者是 `0x452911`（`0x452907` 桩内，`push 0` + `ecx=[ecx+0xC]`），而 `0x452907` 的唯一调用者是 `0x45280A`（`call 0x405DE1` 之后的特技链）。

### 二、★★ 原生死者结算**已经**登记杀敌数（这才是关键）

`0x426BA0`（`cmp byte [0x505FDC],0 / jne skip / inc word [eax+0x35]`）
⇒ **注意门控方向：`[0x505FDC] == 0` 才 +1，非 0 则跳过**（页首第 2 条把方向写反了）。

- 唯一直调点：`0x4290F2`（全 `.code` E8 扫描确认 1 处）。
- `0x4290F2` 位于 `0x4290C8` 函数内，该函数做：`cmp [ecx+0x24],cl / jae` → `or byte [ecx+0x24],0x80` → `cmp [ebp-8],0 / je` →
  `ecx=[ebp-4]` → `call 0x40658F` → `mov eax,ecx` → `call 0x426BA0` ⇒ **典型"死亡结算 + 杀敌数 +1"**。
- `0x4290C8` 的调用者只有 2 处：**`0x4037F0`** 与 `0x420F7C`。
- `0x4037F0` 上下文（伤害结算主循环）：
  ```
  0x4037D2 call 0x41B500                     ; 目标 HP
  0x4037DD cmp [ctx+0x84+4i], eax            ; 伤害槽 vs HP   ← 与斩杀写入同一数组
  0x4037E4 jb  0x403839                      ; 伤害 < HP ⇒ 未死，跳过
  0x4037ED mov ecx,[ctx+0x0C]                ; 攻击者单位记录
  0x4037F0 call 0x4290C8                     ; ★ 判死成立 ⇒ 死亡结算 ⇒ 内部 0x426BA0 给攻击者 +1
  ```

### 三、⇒ 结论（可证伪）

斩杀把伤害槽写成 **HP** ⇒ 结算时 `cmp 伤害槽, HP` **必然不 jb** ⇒ **必然走 `0x4037F0 → 0x4290C8 → 0x426BA0` ⇒ 攻击者杀敌数已经 +1**。

因此 Codex 的 v1/v2 补丁（在 `0x40D077` 处再调一次 `0x40658F → 0x426BA0`）是**重复登记**：

| 情形 | 应有 | 装 v1/v2 后 |
|---|---|---|
| 斩杀 1 个目标 | +1（结算给的） | **+2** |
| 斩杀 N 个目标 | +N | **+2N** |
| 斩杀被免死/未判死的目标 | +0 | **+1（错加）** |

⇒ **"优化"的正确方向不是改补丁，而是不装**（原引擎已正确）。
若实测确实是 **+1**（而不是 +2），则说明该次并未走 `0x4037F0` 结算，必须用 x32dbg 在 `0x4290F2` 与 `0x40D077` 各下 1 个断点，比 `hit_count` 才能定论（**未做**）。

> 背景：用户要求把补丁装上实测（对照"原生 +1 vs 补丁 +2"）。装配过程中发现 v2 不可用。

### 一、v2 的 bug（字节级）

v2 段（33B）在 v1 段前面插入了 9 字节门控指令：

```
89 01                      mov [ecx],eax
FF 45 FC                   inc dword [ebp-4]
80 3D 3C C6 4A 00 03       cmp byte [0x4AC63C],3     ← 新增 7B
75 12                      jne 0x40D0B0 (ret)        ← 新增 2B
8B 55 0C / 8B 4A 0C        mov edx,[ebp+0xC] / mov ecx,[edx+0xC]
E8 EF 94 FF FF             call → 实际 0x406598   ❌ 应为 0x40658F
8B C1                      mov eax,ecx
E8 F9 9A 01 00             call → 实际 0x426BA9   ❌ 应为 0x426BA0
C3                         ret
```

**根因**：`rel32` 是相对**下一条指令**的。插入 9 字节后两个 `call` 的地址都后移 9，
但 rel 值照抄了 v1 ⇒ 目标**整体 +9**：一个跳进 `0x40658F+9` 的指令中间，另一个跳到 `0x426BA0+9`（已过 `ret`）。
⇒ 这就是"门控版"行为不可预期的来源之一（与"重复计数"是两个独立缺陷）。

**修正**：两个 rel32 各 **−9**

| | v2（错） | v3（对） | 验算 |
|---|---|---|---|
| call1 | `E8 EF 94 FF FF`（−27409）→ 0x406598 | `E8 E6 94 FF FF`（−27418） | 下条 0x40D0A9 − 0x6B1A = **0x40658F** ✅ |
| call2 | `E8 F9 9A 01 00`（+105209）→ 0x426BA9 | `E8 F0 9A 01 00`（+105200） | 下条 0x40D0B0 + 0x19AF0 = **0x426BA0** ✅ |
| jne | `75 12` → 0x40D0B0 | 不变 | 0x40D09C+2+0x12 = **0x40D0B0**（ret）✅ |

## ★★★ 2026-10-18 10:05 实机闪退定因：**门控变量选错了**（`0x4AC63C` 不是"战斗态"）

用户实测（v1 + 门控 v3 已装，SHA `EA1E2960`）：**「待斩杀攻击时候，发出攻击闪退」** ⇒ 已立即回退到 `81989C9F`。

### 一、崩点：`0x40658F` 是"取单位号再查表"，传错指针必崩

```asm
0x40658F  push ebp / mov ebp,esp
0x406592  push [ecx]           ; ★ 把 ECX 指向的第一个 dword 当【单位号】
0x406594  call 0x4061E4        ; 0x4061E4(单位号) → 人物记录（ECX 返回）
0x406599  pop ebp / ret
```

辅助段做的是 `mov ecx,[ctx+0xC]` 再 `call 0x40658F`。**只要 `[ctx+0xC]` 不是有效战场单位记录**，
`push [ecx]` 就会读到垃圾"单位号" ⇒ `0x4061E4` 用它索引人物记录表 ⇒ 越界 ⇒ 闪退。
"待斩杀攻击（进入目标选择/预览）→ 发出攻击 → 闪退"正落在这个语境上：`0x40CFF6` 在预览路径同样被调用，
此时上下文不是真实战斗结算的 ctx。

### 二、门控为什么没挡住：`0x4AC63C` 的语义被误用

Codex 的 v2/v3 用 `cmp byte [0x4AC63C], 3` 当"真实战斗态门控"。**库内 2026-10-17 已定案它不是状态码**：

- `0x4AC63C` 是「**主值 + 余量**」双字节计数对的主值（余量在 `0x4AC63D`）；
- `0x416A75`：置 `2` → 处理 → `inc` 成 `3` → 返回（⇒ 2=处理中、3=处理完）；
- `0x416A9B`：`[0x4AC63D] >= 40 且 != 114` 时 `inc [0x4AC63C]` + `sub [0x4AC63D],40`（逢 40 进 1）；
- `0x40B922` = `byte[0x4AC63C]==3` 的谓词，真正的用途是**渠道选择**：`==3` 走 `0x4101D9`（真判定），否则走 `0x41301E`。

⇒ **`== 3` 与"是不是战斗态"无关**，用它当门控 ⇒ 预览语境照样可能放行 ⇒ 必崩。
**要判断"是否真实结算语境"，必须先找 `0x452907`/`0x45280A` 的调用者语境（未做），不能拿 `0x4AC63C` 凑。**

### 三、结论：这条路彻底放弃

1. 功能本身**多余**：原引擎死亡结算 `0x4037F0→0x4290C8→0x4290F2→0x426BA0` 已给攻击者 `+0x35` +1（用户实测回退后 +1）。
2. 两次实现都被实机否决：v1/v2（含 rel32 错）、v3（rel32 修对但**门控变量错**）⇒ 全部**不可用**。
3. 已回退：`EA1E2960 → 81989C9F`（备份 `bak_auto_20261018_095723`），复读两段一致。
4. 若将来出现"某击杀场景杀敌数确实没加"的反例，正确入口是**结算侧**：
   查 `0x4290C8` 的两个调用者（`0x4037F0` / `0x420F7C`）中哪一个被绕过，**不要**再回到 `0x40D077` 里补登记。

### 四、可复用的规范教训（两条，都是花钱换的）

1. **插指令必须重算 rel32**（v2 教训）：插入 N 字节后，其后所有 `call/jmp` 的相对偏移要各减 N；写后要**逐条复算目标地址**，

2. **用全局量当门控前必须核对该全局的真实语义**（v2/v3 教训）：本库已有多页说明 `0x4AC63C` 是计数对主值 + 渠道判定，

### 一、真正的原因（字节级）

```asm
0x426BA0  55 8B EC                        push ebp / mov ebp,esp
0x426BA3  80 3D DC 5F 50 00 00            cmp  byte [0x505FDC], 0
```

## ★★★★ 2026-10-18 11:51 撤掉斩杀补登记 —— 一次修掉「人头 +2」和「预览闪退」

> 用户实测：「斩杀获得的人头是 +2（正常攻击 +1），预览斩杀（即将攻击）又闪退」

### 一、两个现象是同一个根

**现象 1：斩杀人头 +2**

```
0x426BAA = 90 90（门控已解除）  ⇒ 死亡结算 0x4290C8 → 0x4290F2 → 0x426BA0 给 +1
0x40D077 = E8 09 00 00 00      ⇒ 斩杀函数内又 +1
⇒ 两条都走到 = +2
```

当初加「斩杀补登记」是因为 **门控还没解除时** 斩杀真的 +0（10:58 的实测）；
门控一解除（`0x426BAA` = `90 90`），原生结算就覆盖了斩杀 ⇒ 补登记变成**重复计数**。
⇒ **补登记已经过时，撤掉即可。**

**现象 2：预览斩杀闪退**

`0x40CFF6`（斩杀函数）在**预览语境**也会被调用。补登记的辅助段做了指针范围校验：

```asm
0x40D08D  mov ecx,[edx+0xC]        ; [ctx+0xC]
0x40D090  cmp ecx,0x4A7B20
0x40D096  jb  skip
0x40D098  cmp ecx,0x4AAB20
0x40D09E  jae skip
0x40D0A0  call 0x40658F            ; ← 这里崩
```

**范围校验只保证"指针落在战场单位表区间内"，不保证"指向的那条记录是有效单位"。**
预览语境下 `[ctx+0xC]` 可能恰好落在区间里，但记录内容不是有效单位（单位号可能是 `0xFFFF` 或垃圾）。
`0x40658F` 的实现是 `push [ecx]; call 0x4061E4(单位号)` ⇒ 用垃圾单位号索引人物表 ⇒ **越界闪退**。
（这与 10:00 那次「初版无校验必崩」是同一处崩点，只是那次连范围都不校验。）

### 二、修法（撤掉补登记，保留门控解除）

| 段 | VA | 原（补登记） | 现（还原） |
|---|---|---|---|
| 入口 | `0x40D077` | `E8 09 00 00 00` | **`89 01 FF 45 FC`**（原生 mov [ecx],eax + inc [ebp-4]） |
| 辅助段 | `0x40D085` | 40 字节洞 | **90 × 40** |

**保留不动**：
- `0x426BAA` = `90 90`（门控解除）⇒ 普通击杀与斩杀击杀都由死亡结算 +1
- `0x40D017` = `6A 64`（斩杀阈值分母 100）

### 五、教训（第三次同类）

**"某个功能原来不加，我补了一次 +1" 这种补丁，必须绑定"当时的前提"**（门控未解除）。
一旦前提被别的补丁改掉（解除门控），补登记就自动变成重复计数。
⇒ 以后凡是"补漏"型补丁，**落地时就该在补丁头写明它依赖的前提**，并在前提变化时立刻复查。
（本案例的补丁头其实写了"原引擎已 +1"的错误结论，反而误导了后续判断。）
