# 外部补丁对比：「6.6X策略特效-注入」初版 vs 修复版（跳转错在哪）

> 样本：`Ekd5.exe` SHA `2AC91CB8F1B26866…`（**这两个补丁都还没打进本样本**，现读该区仍是 `90`）
> 材料：`[本地盘]\qq\qq群\6.6X爱要不要系列（策略特效） - 注入.txt`（**初版**）
> 　　　`[本地盘]\qq\qq群\6.6X爱要不要系列（策略特效） - 注入（修复跳转错误导致乱码）.txt`（**修复版**）
> 方法：逐字节 diff → 定位差异 VA → 反汇编两版 → **机检"跳转落点是否为合法指令边界"**

## 结论速览

1. **两份补丁只差 2 个字节**（同尺寸 4370 B、26 段、合计 925 B），
   且**都在同一个 723 字节大段 `-0041B22D` 内**：
   | # | VA | 初版 | **修复版** | 性质 |
   |---|---|---|---|---|
   | 1 | **`0x41B41E`** | `0D` | **`0E`** | **`jae` 的 rel8 位移**（`0x41B41D` 处 `73 xx`）|
   | 2 | **`0x41B4F5`** | `00` | **`E7`** | 某桩的 `push` 立即数（`68 xx xx xx xx`）|
2. **★ 跳转错误的机理（这就是"乱码"的根因）**：
   ```asm
   0041B41A  39 42 10   cmp [edx+0x10], eax
   0041B41D  73 0E      jae 0x41B42D     ← 修复版：落在 mov eax,[ebp-4] 的【指令首字节】
   0041B41F  53         push ebx
   0041B420  FF 75 FC   push [ebp-4]
   0041B423  E8 B1 A6 00 00   call 0x425AD9     ← 5 字节
   0041B428  01 45 FC   add [ebp-4], eax
   0041B42B  EB 18      jmp 0x41B445
   0041B42D  8B 45 FC   mov eax,[ebp-4]   ★ 正确落点（指令边界）
   ```
   **初版写 `73 0D` ⇒ 跳 `0x41B42C` = 落在 `0x41B423` 那条 5 字节 `call` 的【最后一个字节】上**
   ⇒ CPU 从字节中间开始解码 ⇒ 后续指令全错位、控制流乱飞 ⇒ **表现为乱码/崩溃**。
   **⇒ 正确写法必须落在 `0x41B42D`，即 rel8 = `0x0E`。**
3. **★ 机检结论（客观、可复现）**：对两版各自的代码段做"跳转落点合法性"检查 ——
   * **修复版：非法落点 = 0** ✅（三个段全部合法）
   * **初版：非法落点 = 1** ❌（唯一那一处就是 `0041B41D jae 0x41b42c`）
4. **第 2 处差异（`0x41B4F5`）不是跳转，是"桩查的特技号漏填"**：
   ```asm
   0041B4E8  55 8B EC      push ebp / mov ebp,esp
   0041B4EB  6A 00         push 0
   0041B4ED  6A 01         push 1
   0041B4EF  68 00 00 00 00   push 0      ← 初版
   0041B4F4  68 E7 00 00 00   push 0xE7   ← 修复版
   0041B4F9  E8 DB 4C FF FF   call 0x4101D9   （特技查询）
   0041B4FE  5D C3         pop ebp / ret
   ```
   **`0xE7` 在个人特技表 = 「火战精通」**（相邻：`0xE6 山林精通`、`0xE8 刀剑震鸣`、`0xE9 满弓取敌`）
   ⇒ 修复版把"这个桩要查哪个特技"补上了。**两版都是 5 字节（`68` 形态），所以尺寸不变。**

## 已确认事实：本补丁的形态

* **它是"注入"形态**：把 3 个代码块写进 `.code` 的 `90` 填充区
  （`0x452CFE` 33 B / `0x40CDCA` 126 B / **`0x41B22D` 723 B**），再靠若干 1 字节段在别处挂钩。
* **`0x41B22D` 大段里是一整排"桩函数"**，形态统一：
  `55 8B EC | 6A 00 | 6A 01 | 68 xx xx xx xx | 68 <特技号> | E8 → 0x4101D9 | 5D C3`（23 字节/个）。
* 实测其中两个桩：
  * `0x41B4D0`：`push 0 / push 1 / push 0 / push 0`（该桩的号是 `0`）
  * `0x41B4E8`：`push 0 / push 1 / push 0 / push **0xE7**`（修复版）
  ⇒ **特技号在"紧邻 `call` 的那个 `push`"里**。

**★ 本页最有复用价值的判据（建议进方法论）**：
**拿到注入型补丁后，先做一次"跳转落点合法性"机检** ——
把补丁代码段**线性反汇编**，凡段内跳转目标**不落在任一指令起始地址**上，就是**必然乱码/崩溃**。
该检查**不需要实机、不需要样本归一**，几秒钟出结论，能提前抓掉这类致命错。

## 风险与边界

* 我**只比出这 2 处差异**；修复版是否**还有别的错误**未验证（本页不担保"修复版一定可用"）。

### 三、★ 风险提示（我发现的、修复版没改的）

**其余 6 个桩的"号"仍是 `push 0`（= 特技 `0x00 覆海之龙`）** ⇒ 有两种可能，**必须由作者确认**：
* **（a）漏填** —— 若这排桩本意是"分别查 `0xE4 陆战精通` / `0xE5 水战精通` / `0xE6 山林精通` / …"，
  那**另外 6 个桩的号也需要填**（与 `0xE7` 同一类错，只是没被这次修复覆盖）；
* **（b）有意为之** —— 若这些桩的号**运行时由寄存器/其它途径提供**、`push 0` 只是占位，则无需改。

**⇒ 我据此判定："修复版"只修了 1 处编号，同一排里还有 5~6 处同类形态未复核**。
**给作者的建议**：把这排桩逐个用"该桩本应服务哪个特技"对齐名表（`0xE4~0xE9` 段）。

### 四、判据（新增，可复用）

**同一注入块里出现"一整排同形态子桩"时，必须逐个核对"每个子桩填的号"，不能只检查被点名的那一处。**
机器做法：`_复核策略特效桩号3.py` 用反汇编器枚举段内全部 `push…push…call 0x4101D9` 序列，
把**最后一个 `push`** 当"号"打印出来 ⇒ 一眼看出哪些是 `0`。
