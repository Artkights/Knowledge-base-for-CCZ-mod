## 一、一句话根因

**转移量被原样写进承接者的伤害槽（`ctx+0x108+4×列表位置`），引擎在 `0x4229FC` 做 `HP = HP - 伤害` 时没有任何下限保护 ⇒ 转移量 > 承接者 HP 时 HP 变成负数；而顶层唯一"按 HP 判死"的 `0x40502B` 要求 HP **严格等于 0**（`test eax,eax / jne`）⇒ 负 HP 永不判死 ⇒ 单位留在场上，随后被六档位刷新路径 `0x45AB05 → 0x40DA4A`（`[0x505F30]==0` 模式）抬成 `1`、或按无符号读成巨大值 ⇒ 用户看到的就是「原地满血复活」。**

⇒ **"概率"不是随机，是条件**：只有 `转移量 > 承接者当前 HP` 的那几次会复活；`转移量 == HP`（刚好打死）时 HP 恰好归 0，原生判死正常生效。

## 二、两处漏钳口（现行 v23/v15 洞体，源码级）

`_生成-转移策略-0x6F-v5.py` 的分派段（v15/v23 洞体同源）：

| 分支 | 触发条件 | 伤害槽写法 | 钳制 | 后果 |
|---|---|---|---|---|
| `.orig`（`v5.py` 分派 `.st`）| 承接者**就是原目标** | `min(累计伤害, HP)` | ✅ 有 | HP 恰好归 0 ⇒ 原生判死生效 |
| `.found` 且 `位置 ≥ 原目标数`（`jmp .float` 那条）| 承接者**已被本洞追加过**、本次再命中 | 直接写累计 total | ❌ **无** | 多目标累计 ⇒ HP 变负 ⇒ 复活 |
| `.append`（`v5.py: mov eax,[edi+0x14] / mov [esi+ecx*4+0x108],eax`）| 承接者**不在**目标列表，新追加一项 | 写**完整转移量** | ❌ **无** | HP 变负 ⇒ 复活 |

⇒ 三个分支里**只有一个钳了**，另外两个没钳 —— 这就是"改了十几个版本还是偶发复活"的原因。

**关键历史纠误**：`更新记录.md:17046` 记的因果是 —— v6 为了防止复活把追加槽钳到 **`HP-1`**（代价：飘字显示 `HP-1`，用户不接受）；v7 为了「飘字 = 完整转移量」改成**写完整 xfer** ⇒ 复活回归。**这两件事其实不冲突**：
- **伤害槽**该钳到 **`min(xfer, HP)`**（不是 `HP-1`）⇒ HP 恰好 0 ⇒ 引擎判死；
- **飘字数字**由 `0x44FB73(slot, 值, 0x12, 0x18)` 单独排（v8 已实装）⇒ 想显示完整 xfer 就传完整 xfer。
⇒ v6→v7 那次取舍是把"钳制"和"飘字显示"错误地绑在了一起。

### 2.2 ★ 挂点 `0x42365C` 的真实身份 = 伤害写入器收尾（不是结算器）

### 2.3 ★ 常规分支在 `0x422999` 钳位 —— 「负 HP」根因对常规策略不成立

`0x42296A~0x42299E`（常规类型）：

```

0x422982  sub  eax,[ebp-0x14]               ; HP-dmg
0x422985  push eax
```

⇒ `0x4229F5 eax = HP - dmg ∈ [0, HP]`，`0x4229FC call 0x43F6DB` **写不出负 HP**。
⇒ 旧结论「`.append` / `.found` 未钳位 ⇒ 负 HP ⇒ 满血」**对常规类型策略不成立**：钳位在引擎侧（`0x422999`），不在补丁侧。v7 当初加的「完整转移量 vs 钳到 HP-1」权衡是**假绑定**。

### 2.4 `0x43F6DB` 无符号上钳（机制保留，前提收紧）

```
ecx = unit; push [unit]; 0x4061E4 → 0x407263 → eax = maxHP
ecx = [ebp+8] = newHP
cmp ecx,maxHP / jbe 0x43F706   ; 写 newHP
else 0x43F6FB..0x43F701        ; mov [unit+0x10], maxHP
```

`jbe` 是**无符号** ⇒ 任何负值（`0xFFFFxxxx`）必然走 else ⇒ **写满血**。机制成立，但**必须真有人传负值进来**。

### 2.5 ★ 唯一能传负值的分支：策略效果类型 `0x18`

`[ebp-0x34]` 不是未初始化局部，而是 **`byte [0x4D1570 + 策略号]`**：

```

0x4226B7  mov al,[eax+0x4D1570]   ; 效果类型
0x4226BD  push eax                ; → [ebp-0x34]
```

`0x42291D` 处四路分流：

| 类型 | 行为 |
|---|---|
| `0x20` | 不扣血（`0x42292E/0x422938` → `0x422A3A`） |

### 2.6 `0x42554F` = 逐目标循环**之前**的排序，不是结算

`0x4226C1 call 0x42554F(ctx)`。以 `0x403360(unit)` 为键做冒泡，逐对用 `xchg` **同步**交换：

- 列表 `ctx+pos+0xC` ↔ `ctx+pos+0xD`

⇒ 追加项会被排序吸收，但**字段同步交换**，不产生「列表位置 ↔ 伤害槽」错位。

## 3.40 ★ 语义与门控纠正：`0x6F` 是特技号，不是策略号（2026-10-28，用户驳回 §3.9/§3.13 的门控方案）

> **本节优先于 §3.9「精确门控候选」与 §3.13「精简适配 v1 候选」的门控结论**：
> 那两节写的「`0x45802A:84→85`（JE→JNE）+ `0x458400=0x6F`」**作废，不要再照做**。

### 3.40.1 用户口述的语义（原话）

> 「当持有特技者被策略攻击时，敌军的使用策略范围内，如果存在他们的单位转移到附近血量最低的敌军单位上。
> 怎么就变成了持 0x6F 特技的单位施放策略 0x6F 才应转移。」

⇒ 正确语义：**持特技 `0x6F` 的单位「被」策略命中** ⇒ 把打给它的那份伤害，转给**施法者阵营**里 HP 最低的另一个单位
（候选范围 = 该策略的作用范围）；它自己不再是施法者。

### 3.40.2 两个编号体系（门控错位的根因）

| 量 | 是什么 | 查询入口 |
|---|---|---|
| `ctx[0]`（`0x423594` 的 `[ebp-4]` 首字节）| **策略 Data 号** | `0x484002`（`imul ecx,0x61; add ecx,0x4A3E77` ⇒ 61H 策略记录）|
| `0x6F` | **个人特技号** | `0x42518F`：`ecx` = 单位指针；4 个栈参数 `[ebp+8]/[ebp+0xC]/[ebp+0x10]/[ebp+0x14]`（callee `ret 0x10`）；`eax` = 特效值（0 = 不生效）|

**`0x42518F` 参数签名（2026-10-28 现读全函数，仅 `0x2B` 字节）**

```c
int 0x42518F(int ecx_unit, int arg1, int arg2, int arg3, int arg4);   /* cdecl, ret 0x10 */
```
- `ecx` = 单位指针（`0x4061F9` 的返回值）；函数内 `push ecx` 存到 `[ebp-4]`，下游再 `mov ecx,[ebp-4]` 取回。
- **`0x42518F` 自身不读任何栈参数**，只把它们原样 `push` 给 `0x40B922`；而 `0x40B922`（`0x40B922..0x40B934`，共 `0x15` 字节）
  也**一个都不读** —— 只 `call 0x40B913` → `cmp al,3` → `sete cl`。
  ⇒ 库内"`0x40B922` 的实参语义尚未认领"（`可搬回清单-初版对照.md:405`）的真因是：**它根本不读参数**。
- 真正的语义在下游两个实现里（cdecl 不调 esp，它们的 `[ebp+8..0x14]` 恰好落在同一位）：

| 位 | 语义（现读证据） | v27 传值 |
|---|---|---|
| `[ebp+8]` arg1 | **特效/特技号**；`0x41301E` 里 `0x413028 and dword [ebp+8],0xFF` ⇒ **必须 ≤ 0xFF** | `[0x458400]` = `0x6F` ✅ |
| `[ebp+0xC]` arg2 | 渠道/来源号，作 `0x43C794` 第 3 实参 | `0x23`（**语义未认领**）|
| `[ebp+0x10]` arg3 | 渠道**类型码**（不是指针）：`0x413009` 首条 `cmp ecx,2` | `1` ✅ |
| `[ebp+0x14]` arg4 | 附加标志，作 `0x43C794` 第 4 实参 | `0` |

- 既有实例：`0x45D513` = `(0xFE, 0x59, 0, 0)`；`0x42E599` = `(0xF6, 0, 1, 0)`；`0x43C7EB` = 叠加式取值。
- ⚠ **两个静态风险（首次实机必看，均未验证）**：
  1. 真分支 `0x4101D9` 开头 `0x4101F1 mov ecx,[edx]` **解引用 edx**，而 `0x42518F` 不设 edx ⇒ edx 由调用者（本洞）继承、值未定义；
     只在 `0x40B913` 返回 `al==3` 时进这条（否则走 `0x41301E`，该分支不用 edx）。
  2. `arg2 = 0x23` 语义未认领；若 `0x43C794` 拿它当表索引，可能越界。

§3.9 把 `0x458400` 当"策略号白名单"，用 `cmp al,[0x458400]` + `JNE` 做精确门控 ⇒ 等于要求"**施放的策略号** == 0x6F"，
而策略表 `0x6F` 行的效果类型是 `0x27`，与"**被攻击方**是否持特技 0x6F"毫无关系 ⇒ **门控挂错了对象，不是参数值写错**。

### 3.40.3 v27 的正确门控（现行在装）

- **门控对象 = 受击方**：洞内对 `ctx+0xD+i` 的每个已命中目标 `call 0x4061F9`（slot→单位）后
  `push dword [0x458400] / call 0x42518F`，返回 `eax=v`；`v<=0` ⇒ 该目标不转移。
- **`0x458400` 的语义随之改变**：v24/v26 里它是"策略号（排除/白名单）"，v27 里它是**特技号参数**
  （`push dword [0x458400]` 的第 4 个实参）。§3.9「0x458400 参数范围」整节按旧语义写（"0x6F 是策略号""0xFF=不启用"）⇒ **作废**。
- **不需要"策略号门控"**：v27 用 `0x42518F` 查**精确特技值** —— 没这条特技的单位查出来就是 0
  ⇒ 天然隔离，不必再叠"`ctx[0]==X`"这类判据。
  ⚠ **`0x4D1570` 的索引是「策略号」，不是特技号**（2026-10-28 现读纠正 §3.15 与 §3.40 初稿）：
  `0x425698 movzx eax, byte [ecx]`（`ecx` = `ctx`）→ `0x4256A4 mov al, byte [eax+0x4D1570]` → `0x4256AA jmp 0x4E4700`（类型码分发）。
  所以 `0x4D1570[0x6F] = 0x27` 的意思是"**策略** 0x6F 的效果类型是 0x27"，
  `0x66/0x67/…/0x7A` 这 12 个也是**策略号**，与本特技号 `0x6F` 是两套编号 —— 不要再混称"12 个特技号"。
- **阵营门控**（用户要求「敌军范围内…他们的单位」）：`0x406710(ecx=单位)` ⇒ `al` = 阵营组
  （`movzx eax,[ecx+5]` 查表 `0x40672D`，**只改 eax**）。洞内在循环外算一次**施法者阵营**（`[esi+8]` = 施法者记录），
  循环内对每个候选比对，不同阵营直接跳过 ⇒ 伤害只在**施法者自己阵营**内转移，不会转给玩家队伍。
- 另加三条必备过滤：跳过**当前受击目标本身**、跳过**施法者自己**、跳过 **HP<=0** 的候选。

## 3.41 「落雷（策略 0x18）不触发转移」在 v27 已不存在（2026-10-28 静态复查）

> 现读样本 SHA256 = `7E61EA1BFA5B0755996699C807AB908DBFB364CAD376E080B8381E91077DE7F0`（v27 在装）。
> 证据类型 = 文件字节复读 + 离线反汇编；**无运行时结论**。

### 3.41.1 字节事实

- `0x458400 = 6F`（`db 0x458400 2` → `6F 90`）—— 是**特技号**参数，不是策略号。
- 全洞唯一引用：`0x45806B FF 35 00 84 45 00` = `push dword [0x458400]`，作为 `0x42518F` 的第 4 个栈参数。
- **洞体内没有任何策略号比较**（`0x458000..0x45816C` 逐条反汇编：`cmp` 只有 `cmp eax,[edi]`/`cmp cl,0xFF`/`cmp ecx,[esi+8]`/`cmp al,[edi+0x20]`/`cmp ecx,[edi+0x1C]`/`cmp byte [edi+0x18],0xFF`/`cmp cl,0xFA`）。
  ⇒ 旧 v24 的 `cmp al,[0x458400]` + `JE 退出`（`0x458021/0x458023/0x458029`）**已被整段删除**。

### 3.41.2 结论

1. **参数层面：没有了。** 现在无法通过 `0x458400` 让"某个策略号"豁免转移 —— 该字节只表示"查哪一条特技"。
2. **语义层面：本来就不该有。** 旧豁免来自"施法者侧"语义（自己放落雷时不要转移）；v27 是**受击方**语义，
   敌军用落雷打中我军持 `0x6F` 者时，伤害转给敌军 HP 最低者 —— 正是用户口径要的行为。
3. **若仍要恢复豁免**（例如只想让部分策略触发）：用空闲字节 `0x458401` 作"排除策略号"，
   洞内在目标循环入口加 3 条（`movzx eax,[esi]` / `cmp al,[0x458401]` / `je L_NEXT`，约 10 B）；
   洞可用区 `0x458000..0x4582FF`（0x300 = 768 B）已用 `0x16D`，余量 `0x193` 足够；**不动**现有特技号门控。

### 3.41.3 静态不能定论的一点（别当成已知）

落雷是否真的会走到 `0x423594`（洞所在函数），**静态无法确认**：

- `0x4D1570[0x18] = 0x00`（现读 `db 0x4D1570 0x20` 第 0x18 字节 = `00`）⇒ 策略 0x18 的类型码 = 0；
- 类型码分发在 `0x4256A4 → 0x4256AA jmp 0x4E4700` → `0x4E472A FF 24 85 C3 59 4E 00` = `jmp dword [eax*4 + 0x4E59C3]`；
