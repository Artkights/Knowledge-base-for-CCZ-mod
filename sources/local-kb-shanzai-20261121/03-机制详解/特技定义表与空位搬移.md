# 特技定义表机制 与「搬回初版特技」记录

## 结论速览

- 已推翻旧口径：`0x4061E4` **不是**特技定义表定位，而是人物记录定位（`16 位ID × 0x48 + [0x4CEA00]`）；`0x42AC58(id)` 的含义是「该人物/单位是否存在」（`[ecx+0x2A]` 自增后 `0xFF → 0x00` = 不存在），特技号取自记录里的 `[ecx+0x28]`。
- 特技效果落地 = 每技能一个查询桩（`call 0x4101D9`，参1 压特技号）+ 一个效果块；`0x441D87` 是链式数值修正器（攻击方 `0xF2` 经 `0x425AD9` 按百分比扣减 → 防守方 `0xF6` 加回），加新特技 = 新加一个桩 + 在链里加一块。
- `0x4101D9` 契约（写桩前必读）：参1（栈顶那个 push、`[ebp+8]`）= 特技号，参2/参3/参4 是渠道·范围开关，标准桩照抄 `push 1 / push 1 / push 0 / <特技号>`；返回值可能为 `0xFF`（查不到/失败）；stdcall，被调用者清 16 字节栈；**每次调用前必须重设 `ECX` = 单位指针**，两个桩连查不重建 ECX → 点击敌人（伤害预览走该链）闪退。
- 只有被引擎查询过的特技号才生效：当前 exe 共查询 105 个；名称表空位 `0xF4`、`0xF9` 都**不在**查询列表 → 放上去不生效（初版那两格是「物理致死/策略致死」秒杀类，刻意回避）；初版有查询、当前没有的 37 个槽位 = 被删掉的处理，可作搬回候选；页内「未决问题」仍开放：引擎按特技号还是按 `0x48` 记录内容决定行为未知，`Effect.e5` 条目结构未解析。
- 三个特技的最终落地（已实机验证通过 2026-10-12，SHA256 `92C9FA4041736775B43FF53259ADF8B8BAC86D58C6FC624EC1170C80E48291F8`）：`0xFC` ※削弱攻击 = `0x441D39` 改 `jmp 0x432500` 扩桩（先查 `0xF2`，没有就查 `0xFC`）；`0xF7` ※削弱策伤 = 原生内联效果块 `0x445FDE`，原位未动；`0xFD` ※减少移动力 = 抄回 `0x42E589` 的 55 字节（仅改 +0x1A 处 `68 F6 00 00 00` → `68 FD 00 00 00`，指令等长、相对跳转与调用无需重算）。
- 说明栏与弯路：说明分派母函数入口是 `0x452C81`（`ret 0xC`，`[ebp+0x10]` = flag 原始值），`0x42834D` 不是入口（被 `0x452CC2 → 0x428350` 跳过，改它无效）；原生专用分支判的是 `flag == 0x10`（设成 `0x11` 会落到 `AL>=0x0F` 的空串分支）；分派只收 flag + 特效值、不收特技号 → 同 flag 的技能无法区分；`0x8F` 的 flag 与 `0xF3` 撞车后已改到 `0x14`（代码洞判断同步改为 `cmp eax,0x14`，文件偏移 `0x4322D8`）。

## 零、⚠️ 更正：上一版把 0x4061E4 认错了

**上一版结论（错误）**：以为 `0x4061E4` 是「特技定义表定位」。

**实际**：`0x4061E4` 取的是 **16 位 ID × 0x48 + [0x4CEA00]** —— 那是**人物记录**定位
（`[0x4CEA00]` 是人物表指针），不是特技表。

`0x42AC58(id)` 的真实含义是「**这个人物/单位存在吗**」：

```
0x42AC58(id):  push id / call 0x4061E4  → ECX = id × 0x48 + [0x4CEA00]（人物记录）
               call 0x411DA5            → AL  = [ECX + 0x2A]
               inc  al                  ← 0xFF → 0x00（= 不存在）
```

> 情报窗口那段循环 `for i in 0..0x3FF: if 0x42AC58(i)` 是在**遍历单位**，
> 不是遍历特技。特技号来自记录里的 `[ecx+0x28]`。

## 一、特技效果是怎么落地的（本条才是关键）

### 结构：一技能一个「查询桩」+ 一技能一个「效果块」

**查询桩**（每个 21 字节左右，形式统一）：

```asm
0x441D39: push ebp / mov ebp,esp
          push 0            ; 参4
          push 1            ; 参3
          push 0            ; 参2
          push 0F2h         ; ★ 参1 = 特技号
          call 0x4101D9     ; 通用特技查询（返回该单位此特技的特效值）
          mov esp,ebp / pop ebp / ret
```

- 当前 exe 里这种纯桩共 **70 个**；加上带 `add al,imm` 的写法，引擎共查询过 **105 个特技号**。
- 初版查询过 **136 个** —— 差额就是被删掉的处理。

**效果块**（每个桩只有 1 个调用者，就是它的效果落地处）：

```asm
0x441D87: push ebp / mov ebp,esp
   ; ── 攻击方(参3 [ebp+0x10])的特技 0xF2 ──
0x441D8D: call 0x45D513          ; 有效性/状态检查
0x441D9D: call 0x441D39          ; 查 0xF2 特效值
0x441DA6: cmp eax,0x64 / jae     ; >=100 直接返回 1
0x441DB4: call 0x425AD9          ; percent_calc(原值, 百分比)
0x441DB9: sub [ebp+8], eax       ; ★ 扣减
   ; ── 防守方(参2 [ebp+0xC])的特技 0xF6 ──
0x441DD5: call 0x441D53          ; 查 0xF6 特效值
0x441DE7: add eax, [ebp+8]       ; ★ 加回
   ; ── 参2 的特技 0xFF ...（继续链）──
```

**结论**：这是一条**链式数值修正器**——每个特技占一块，按顺序对同一个数值做
「扣减 / 加回」。**加新特技 = 新加一个查询桩 + 在链里加一块**，技术路径完全明确。

### 各槽位的效果落地面貌（实测）

| 特技号 | 桩入口 | 效果块 | 作用 |
|---|---|---|---|
| `0xF2` | `0x441D39` | `0x441D9D` | **按特效值百分比扣减值**（初版名为「削弱攻击」）|
| `0xF6` | `0x441D53` | `0x441DD5` | **按百分比加回值**（当前名为「※物理易伤」）|
| `0xF7` | （在 `0x445FF9` 内联）| `0x445FDE` | **按百分比扣减**（「※削弱策伤」）|
| `0xFF` | `0x441D6D` | `0x441DF0` | 继续链 |

### 表的建立（启动时）

```
0x4815F6: push 4                     ; PAGE_READWRITE
0x4815F8: push 0x1000                ; MEM_COMMIT
0x4815FD: push 0x20000               ; ★ 表缓冲 131072 字节
0x481602: push [0x4CEA00]            ; 表基址
0x481608: call [0x4861E8]            ; 分配
0x481619: call 0x42B88B
0x481623: push 0x48B000              ; ★ C++ 静态初始化函数指针表起点
0x48161E: push 0x48B0BC              ;   终点（共 47 个入口）

```

- `0x481720(a, b)` = 遍历 `[a, b)` 里的 4 字节函数指针并逐个 `call`（C++ 静态构造器机制）。

- **推论：`0x48` 记录表是在启动时由某个初始化函数从数据文件填充的**，不是静态数组。

## 七、引擎级移植技法（实战验证）

> 目标：让一个「名字放进空位」的特技真正被引擎调用。
> 核心要求是**引擎必须查得到这个特技号**。当前 exe 只查询 105 个号，
> 名称表里的空位（`0xF4`、`0xF9`）都不在其中。

### 技法 A：扩展已有查询桩（适用于"链式修正器"里的技能）

**范例：把「※削弱攻击」搬到 `0xFC`**

`0xF2` 的桩 `0x441D39`（26 字节）只被 `0x441D9D` 调用一处，且
`0x441D87` 那条链按「攻击方 0xF2 → 扣减 / 防守方 0xF6 → 加回」工作。
**不动链子**，只把桩改成"先查 0xF2，没有就查 0xFC"：

```
0x441D39 (26B) → E9 C2 07 FF FF + 21×NOP        ; jmp 0x432500
0x432500 (43B) → 新桩：
    push ebp / mov ebp,esp
    push 0 / push 1 / push 0 / push 0F2h / call 0x4101D9
    test eax,eax / jne done
    push 0 / push 1 / push 0 / push 0FCh / call 0x4101D9
  done:
    mov esp,ebp / pop ebp / ret
```

- **优点**：对现有 `0xF2`（策略盾反）零影响 —— 不冲突。
- **适用**：技能的效果块在**共享链**里、只靠「查询桩」取值的场合。

### 技法 B：抄回被 NOP 掉的内联块（适用于"直接内联"的技能）

**范例：把「※减少移动力」搬到 `0xFD`**

初版里 `0xF6`（减少移动力）**不走通用桩**，而是在移动力计算函数内部
内联了一段 55 字节代码；当前 exe 把这段整段 NOP 了。

```
0x42E589 (55B, 当前全是 90) ← 抄回初版原字节，只改 1 个字节：
    偏移 +0x1A 的  68 F6 00 00 00  →  68 FD 00 00 00
```

- 因为**指令长度完全一致**，块内所有相对跳转（`EB xx`）与相对调用
  （`E8 xx xx xx xx`）地址都不变，**无需重算**。
- **适用**：初版有、当前被 NOP 掉的专用处理块。

### 找"被删掉"的位置：两版字节对比

初版与当前 exe 的节区布局、名称表偏移（`0x9E800`）完全一致，
可以直接按**同一 VA** 比较：

```

00413028  81 65 08 FF 00 00 00   and dword [ebp+8], 0xFF   ; ★ 就把它当特技号取低 8 位
```

**由此得到三条必须遵守的规则**：

| # | 规则 | 违反后果 |
|---|---|---|
| 1 | **参1（栈上第一个 push）= 特技号**；`参2/参3/参4` 是渠道/范围等开关 | 查错特技（静默错误，最难查） |
| 2 | **返回值可能是 `0xFF`**（查不到/失败） | 直接当百分比用 ⇒ 系数算成负数或巨大值 |
| 3 | **每次调用前必须重设 `ECX`**（单位指针）；返回后 ECX 已被破坏 | 传垃圾指针 ⇒ **点击敌人（伤害预览跑这条链）时闪退** |

**标准桩写法（照抄，以查 `0x24` 为例）**：

```asm
    push ebp
    mov  ebp, esp
    push 1                  ; 参4
    push 1                  ; 参3
    push 0                  ; 参2
    push 0x24               ; ★ 参1 = 特技号
    call 0x4101d9           ; stdcall，被调用者清 16 字节栈
    pop  ebp
    ret
```

> ⚠️ **旧口径校正**：本页早先的示意写成 `push 0 / push 1 / push 0 / push 0F2h`（四参顺序另有含义）。
> 实测 `0x422e56`（查 `0x70`）与 `0x405dcf`（查 `0x24`）都是 **`push 1 / push 1 / push 0 / <特技号>`**。
> 记法：**特技号永远是最上面那个 push（= `[ebp+8]`）**，其余三个是开关，照抄现成桩最稳。

#### ⚠️⚠️ 血泪教训：每次 `call 0x4101D9` 之前都必须重设 `ECX`（单位指针）

- `0x4101D9` 把 **ECX 作为入参**（单位指针），返回后 **ECX 已被破坏**。
- 证据一：修正链 `0x441D87` 每次调桩前都 `mov ecx,[ebp+0x10]` / `mov ecx,[ebp+0xC]`。
- 证据二：初版搬回的移动力块里，每次调用前都 `mov ecx,[ebp+0x18]`。
- **现象**：曾写过一个"先查 A、没有就查 B"的扩展桩，两次调用之间没重建 ECX
  → 第二次查询传进垃圾指针 → **点击敌人（伤害预览跑这条链）时闪退**。
- **修法**：第二次查询前插入
  ```
  mov eax, [ebp]          ; 调用者(链函数)的 EBP
  mov ecx, [eax+0x10]     ; ECX = 链函数的 [ebp+0x10] = 单位指针
  ```
- **EDX 无需重建**：修正链连续调三个桩都不重设 EDX，说明 `0x4101D9` 不破坏 EDX。

**`0x4101D9` 是 `stdcall`（被调用者清栈 16 字节）**，证据：

```asm
0x40BF99: push 0 / push 0 / push 1Ch / push 72h
0x40BFA4: call 0x4101D9
0x40BFA9: pop ebp
0x40BFAA: ret                 ; ← 调用方完全没清栈
```

- 因此新桩（`0x432500`）里**连续两次** `call 0x4101D9` 不会造成栈错位 ✅
- 原桩末尾的 `mov esp,ebp` 只是防御性还原，保留即可 ✅

**`0x42518F`** 是「双渠道判定」包装器：内部按情况转 `0x4101D9` 或 `0x41301E`，
同样由被调用者清栈；搬回的移动力块字节与初版一致，调用约定天然正确 ✅

## 八、走过的弯路（别再踩）

1. **`0x42834D` 不是说明函数入口**，只是分支链中间一段，且被 `0x452CC2 → 0x428350` 跳过；直接改它无效。

6. 把入口整条换成 `jmp 代码洞` 后，**所有 flag 都能在洞里分流**，不必为了加功能去改 flag 值。
