## 三、★ 三渠道叠加：为什么需要方案C

### 3.1 特效表「4+2」布局（本工程首次解出）

```
行(16 字节) = 4 × [UInt16 人物token][BYTE 特效值]   ← 4 人物槽
            + 2 × [BYTE 兵种号][BYTE 特效值]        ← 2 兵种槽
```
**证据**：兵种号字段实测取值只有 `1~79` 与 `255`，共 61 种，**255 出现 390/512**（空槽）；
与知识库清理口径「`兵种=255`、`特效值=0`」吻合。
**`0x51` 行本来就有兵种配置：兵种 73 → 特效值 16。**

### 3.2 三条渠道会「相加」

`0x4101D9` 的四个栈参数（见《特效号定位与安全读写-命名空间》）：

| 参 | 含义 |
|---|---|
| 参1（栈顶） | **人物/兵种特效号**（两者**共用名称空间**） |
| 参2 | **宝物特效号**（独立名称空间；`0` = 禁用该渠道） |
| 参3 | **叠加方式**：`0`=相加 `1`=取大 `3`=按位或 |
| 参4 | 效果值方式 |

- 宝物特效值存在**物品行 `+0x16`**（`Data.e5+0x818C` 起 104 行、`Star.e5+0` 起 151 行，行长 `0x19`），
  实测取值 1~87 —— 也是 **1 字节**。
- 修罗之怒原版桩 `push 0 / push 0 / push 0x6D / push 0x51` ⇒ **参3 = 0 = 相加**。
- ⇒ 人物槽（最多 4）+ 兵种槽（最多 2）+ 宝物，**全部按整数相加**，加在"编码后的字节"上。

### 3.3 相加为什么会失效（三种坏法）

| 情形 | 填写 | 相加 | 旧方案解读 | 后果 |
|---|---|---|---|---|
| 两渠道都设「攻30%」 | 121+121 | 242 | **防+60%** | 加错能力 |
| 两渠道都设「攻防30%」 | 123+123 | 246 | **防+61%** | 加错能力 |
| 人物攻63% + 兵种攻防1% | 253+7 | 260→低字节 4 | **无能力+1%** | 整槽失效 |
| 255 + 1 | 255+1 | 256→0 | **完全失效** | 技能消失 |
| 三渠道 攻30+防30+纯20 | 121+122+80 | 323→67 | **攻防+16%** | 百分比从 80% 掉到 16% |

**根因**（知识库早记过的"死结"）：一个字节里掩码要"**或**"、百分比要"**加**"，
而引擎只提供一种合并方式 ⇒ 简单改参3 解决不了。

### 3.4 方案C：逐来源累加（解法）

沿用本工程已验证的**气贯长虹（MP辅助）模式**：在合并核心挂钩子 + 全局标志切模式，
逐来源把值拆成 `(掩码, 百分比)`，做 **`掩码 |=`、`百分比 +=`**。

| 地址 | 改动 |
|---|---|
| `0x432656` | `75 0A` → `75 6F`：把"非 flag1"分支改指 `0x4326C7` |
| `0x4326C7` | 跳板 `E9 <rel32>` → `0x4D4600`（原本是空闲区） |
| `0x4D4600` | **caveM（74 字节）**：flag=3 → 槽A 模式；flag=4 → 槽B 模式；其他 → `jmp 0x432662`（原 MP 模式，行为不变） |
| `0x4326E9` / `0x4326EA` | **g_mask（1B）/ g_pct（2B）** —— 实测这两处**引用数 0**、文件内为 `00`，**无需写入** |

- 全局区实测：flag@`0x4326E0`、8 个能力累加器@`0x4326E1..E8`、**`+9..+11` 空闲**。
- 合并核心 `0x432640` 原逻辑：flag=0 → `0x43269C`（模式 0 加 / 1 取大 / 3 或）；
  flag=1 → HP 模式；否则 → MP 模式。收尾 epilogue 在 `0x4326C0`。

### 3.5 效果对比

| 配置 | 旧「相加」 | **方案C** |
|---|---|---|
| `[121,122]` 攻30+防30 | 攻防+60%（碰巧对） | 攻防 +60% ✅ |
| `[121,122,80]` **三渠道** | **攻防+16%** ❌ | **攻防 +80%** ✅ |
| `[255,1]` | **0（失效）** ❌ | **攻防 +63%** ✅ |
| `[255,255]` 槽B | 溢出 ❌ | 精敏士 +62% ✅ |

**必须保留**：`0x45B6DA` = `E9 49 4A 00 00 5D C2 08 00`（钩点1 尾部跳转，改动不得触及）。

### ★ 两个踩过的坑

1. **`0x4101D9` 会解引用 EDX**（`mov ecx,[edx]`，用于人物 token 判定）。
   原版靠调用链给有效指针；代码洞用 `div`/`shl` 会把 EDX 搞脏 ⇒
   必须 `push edx` 保存、每次调用前 `mov edx,[esp]` 恢复，否则踩空指针。
2. **原版 `0x45B69C` 的 `je 0x45B6DA`**：槽A 特效值为 0 时会**绕过整个钩子**，
   导致槽B 永不执行 ⇒ 钩点必须放在它**之前**（最终定在 `0x45B68A`）。

## 八、★ 事故与教训（务必记住）

**2026-10-14 05:45 我把 `Ekd5.exe` 截断成了 0 字节。**

- 起因：写 `Ekd5.exe` 一直报 `OSError: [Errno 22]`，我做诊断时写了
  `open(path, 'wb')` 去"测试可写性" —— **`'wb'` 一打开就截断文件**，我随即 close，文件内容全没了。
- 恢复：`_dsh写锁.safe_write_exe` 在失败前已自动存了备份
  （`Ekd5备份\补丁前备份\Ekd5.exe.bak_before_xiuluo2skill_20261014_054510`，1153024 字节），
  用 `_紧急恢复Ekd5.py` 逐字节还原，SHA 与截断前一致 ✅。
- **教训**：
  1. **绝不**用 `open(p,'wb')` / `'w'` 去"测试可写性" —— 要用 `'r+b'` 或
     `os.open(p, os.O_WRONLY)`（**不带 `O_TRUNC`**）。
  2. 真正的锁冲突表现为 `CreateFileW(GENERIC_WRITE)` 返回 **error 32（共享冲突）**，
     Python 侧可能是 `EACCES(13)` 或 `EINVAL(22)`；别把它当"权限/路径"问题。
  3. 任何写 `Ekd5.exe` 前先 `tasklist` 确认没有 `Ekd5.exe` 进程；
     杀进程后句柄还要等 1~2 秒才释放。
