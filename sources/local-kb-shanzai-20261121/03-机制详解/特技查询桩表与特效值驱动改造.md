## 结论速览

1. **引擎里有 82 个「特技查询点」，其中 62 个是独立桩函数**，形态统一：

## 四、改造模板（**已实测两次的 22 字节洞体**）

```asm
; 挂钩点（5 字节）：E8 <rel32 洞>          ← 覆盖原指令；覆盖掉的字节必须在洞尾补回
; 洞体（22 字节）：
8B 4D FC              mov  ecx, [ebp-4]        ; ecx = 上下文/单位
E8 <rel32 桩>          call <桩>                ; al = 该特技的字段值（0x36 号 = 特效值）
38 45 F8              cmp  byte [ebp-8], al    ; 与"已攻击次数"计数器比较
0F 83 <rel32 出口>     jae  <出口>              ; 达到 ⇒ 跳出
E9 <rel32 回跳>        jmp  <回跳>              ; 否则回原流程
```

### 122.2 ⚠⚠ 三处口径修正（**重要**）

| # | 我先前的说法 | 实际（依 `特技定义表与空位搬移.md:7` 的库内契约 + 本次实测）|
|---|---|---|
| **1** | 「4 个 push = 参1/参2/**桩内号**/名表id」 | **push 顺序 = 参4 / 参3 / 参2 / 参1**；**`[ebp+8]` = 参1 = 特技号**（= 我说的"名表id" ✓ 对）；**我称的"桩内号"其实是「参2」** |
| **2** | 「`桩内号` 是字段选择器 ⇒ 可以做全局字段表」 | **⚠ 错** —— 库内口径：**参2/参3/参4 是「渠道·范围开关」**；实测 34 个取值里 29 个只被 1 个特技使用 ⇒ **它更像"每特技专属的渠道组合"**，**不是全局字段枚举** |
| **3** | 「`0x36` = 特效值」 | **⚠ 不准** —— `0x36` 是**酣战/引导这两个特技用的参2 值**；它们确实返回"特效值"，但**不能推广为"0x36 全局 = 特效值"** |

**★ 库内还给了写桩必守的契约（我先前不知道）**：
* `0x4101D9` **stdcall**，**被调用者清 16 字节栈**（`ret 0x10`）
* **返回值可能为 `0xFF`**（查不到/失败）
* **每次调用前必须重设 `ECX` = 单位指针** —— 两个桩连查不重建 `ECX` ⇒ **点击敌人（伤害预览走该链）闪退** ⚠（这条直接解释了 §118 那类崩因）

## 127.7 ★★★★★ **闭环确认（用户实测）**：个人特技表的 `byte1` **就是引擎读的特效值**

> 承接 §127；用户 2026-10-17 11:2x 实测反馈：**「是6次」**

### 证据链（三层互相独立）
| 层 | 内容 |
|---|---|
| **静态（EXE）** | v2 补丁洞体：`call 0x478E5D`（桩 `0x478E5D` → `0x4101D9`）取特效值 ⇒ `cmp [ebp-8], al` ⇒ 次数 = `al + 1` |
| **静态（DLL）** | `GetPersonEffect(unit, 特技号)` 读 `byte [unit*0x400 + i*4 + 0x10217E08]` 找槽，命中后把 **byte1/byte2/byte3** 三个出参返回（§127.2）|
| **运行时（读数）** | 单位 `[0]`（角色号 `0x0000`）的槽 = `17 05 00 FF` ⇒ **特技号 `0x17`（奋战攻击）、byte1 = `5`** |
| **游戏内（用户实测）** | **打 6 次** = `5 + 1` ✓ |

### ⇒ 结论（正式成立）
1. **「特效值」= 个人特技表每槽的 `byte1`**，与特技号（`byte0`）紧邻。
2. **改这 1 个字节即可改数值** ⇒ **不需要任何代码注入**（§3.6 判据①「只改立即数/操作数」的最安全形态；
   这里是"只改数据"，连指令都不碰）。
3. **v2 公式「次数 = 特效值 + 1」获得三次独立验证**：`3→4` · `4→5` · **`5→6`** ✓
4. **`byte2` / `byte3` 与次数无关**（实测 `b2=0`、`b3=FF`，各槽一致）⇒ 待定的只是它们的其他用途。

### ⇒ 由此打开的低风险路线（**优先级最高**）
| 目标 | 做法 | 风险 |
|---|---|---|
| **给任意单位调特效值** | 写 `个人表 + unit*0x400 + 槽*4 + 1` 一个字节 | **极低**（只改数据，不进指令流）|
| **给任意单位加特技** | 在空槽（`FF FF 00 FF` 处）写 `[号][值][0][FF]` | 低（需同时维护终止符位置）|
| **持久化** | 待查 `SaveVar`/`LoadVar` 是否覆盖该表（§127.5 P0）；否则用工具在每次进战场后重放 | 中 |
| **零代码（编辑器侧）** | 若外部修改器提供 `AddPersonEffect` 入口，则完全不用碰 EXE | 最低 |

### ⚠ 落地注意（写这类数据前必须做）
* **`byte0 == 0xFF` 是终止符**：往里加槽时必须**把新槽写在原终止槽位置**，并把终止符顺移一格；
  否则引擎遇旧终止符就停，新槽不生效。
* **槽上限 256**（`[0x101D3A44]` = `0x100`）⇒ 满了就必须复用/覆盖。
* **单位索引上限 `0x400`**（`GetPersonMes` 校验）⇒ 越界会读到别的单位数据。
* **写内存是临时改动**：退出游戏即恢复；**不要**在未查清持久化机制前把它当"改存档"用。
* **DLL 有 ASLR**（本机实测基址 `0x5B340000`，≠ `ImageBase 0x10000000`）
  ⇒ 任何按 DLL 地址的读写都必须先算基址：`基址 = dword[0x4F0008] - 0x1000BCA0`。

## 125.7 ★ 当前工作基底复核：角色战场编号/Data 编号与 `0x50E000` 运行时特效表的交互

> **样本绑定**：以下地址与调用关系均按当前工作基底 `Ekd5.exe` SHA256 `2B279F3F0A917B1BD6E6F812E473DFB4B06A4101F38903EE1092EF3BDB70652A`（1,148,928 B）复读。这里只做静态反汇编和交叉引用核查，没有启动游戏、没有附加 x32dbg、没有写入 `Ekd5.exe`、RS 或 SV。

### 125.7.1 `0x402CF9`：以角色记录 R 的三字节候选键查询 `0x50E000`

当前样本中，`0x402CF9` 的索引路径可以闭合为：

1. 调用者把索引乘以 `0x10`，加到调用者传入的表基址上；`0x413071` 的调用现场把 `EDX` 设为 `0x50E000`，因此该次查询实际落到 `0x50E000 + index*0x10`。
2. 函数循环 `i=0..2`，计算 `i*3`，读取 `[ECX+0x2E+i*3]`。在该调用链里 `ECX` 是由 DataID 反查得到的角色记录 R，所以候选键来源是 `R+0x2E`、`R+0x31`、`R+0x34` 三个三字节单元。
3. 函数随后按两个子记录/渠道比较表项键，并把命中的表项交给 `0x413009` 合并处理；表项的后续字节由消费者读取，不能仅凭表地址断言为“效果已经生效”。

这一步把“角色拥有的特技/效果键”和“运行时表项”连接起来，但仍不把角色的战场槽号直接等同于 DataID：战场槽号须先经 `0x4061F9` 得到 U，再由 `0x40658F` 得到 R，DataID 反查则由 `0x40BE7D` 完成。

### 125.7.2 `0x41301E`：当前样本的直接入口与编号交汇点

当前样本对 `0x402CF9` 的直接调用只有 `0x413071`（调用者函数 `0x41301E`）。该函数的静态顺序为：

- 先调用 `0x40BE7D`，把当前角色记录 R 转成 DataID；
- 再以 `[0x500C3B]` 和当前键调用 `0x4198BE`，进入个人特技/特效查询渠道；
- 调用 `0x43C794` 和 `0x413009` 做当前项的统一合并；
- 将 `EDX` 设为 `0x50E000`，再调用 `0x402CF9`，把角色记录 R 的三字节候选键与运行时数组交汇。

因此，当前样本能静态确认的编号关系是：

`战场槽号 -> 0x4061F9 -> U -> 0x40658F -> R -> 0x40BE7D -> DataID`，

而特效表查询在 R 的候选键与 DataID/个人特技查询结果都准备后进行；`0x50E000` 不是 Data 表本体，也不是把战场槽号直接当作特技号的证据。

### 125.7.3 `0x50E000` 的写入者与消费者

- `0x411CB2` 写入 `0x50E000 + index*0x10` 的 16 字节条目。静态分支显示有两个子索引（`0..1`），按模式选择条目起始处或 `+0x08` 的 8 字节子区；索引上限比较为 `0xFE`，所以当前实现至少按 255 个索引槽预留。
- `0x421E60` 以 16 字节步长读取条目，把条目首 WORD 通过 `0x4061E4` 映射到 Data 记录，并使用 `0x4CC600` 名称/文本表；这证明该区是运行时数组，且存在 Data 编号到显示/消费路径。
- `0x466F6C` 将表项拆成 8 字节输出记录，`0x4772D4` 按三字节键匹配并读取条目 `+0x03` 的长度/标志字段。两者都是消费/序列化路径，不能反推写入一定代表战斗效果已应用。

### 125.7.4 静态边界与下一步动态交接

**已闭合的静态事实**：当前 SHA 下，`0x50E000` 是运行时填充的 `index*0x10` 数组；`0x41301E` 把 R/DataID 查询与 `0x402CF9` 的三字节键查表串在同一条链上；`0x411CB2` 是已确认的写入口之一；`0x421E60`、`0x466F6C`、`0x4772D4` 是已确认的消费入口。

**仍需另一会话动态确认的项目（测试前必须保持 `4018=1`）**：

- 同一战斗帧中记录战场槽号、U 指针、R 指针、DataID，并确认 `0x41301E` 使用的 R 与目标角色一致；
- 命中 `0x41301E` / `0x402CF9` 时记录索引值、`R+0x2E/+0x31/+0x34` 三组候选键，以及 `0x50E000+index*0x10` 的 `+0/+2/+3/+8` 字段前后值；
- 区分 `0x411CB2` 的填充事件、`0x421E60/0x466F6C/0x4772D4` 的消费事件与最终 HP/MP/状态写回，避免把“表项存在”误判成“特技已生效”；
- 每个动作前后复读 `phase`、`enemy_alive`、`ours_ready` 与相关 HP/MP/集气值，形成可证伪的前后对照。


### 125.7.5 当前样本：0x50E000 的 16B 条目可再拆成两条 8B 通道

- `0x411CB2` 的写入形状可以具体化：先以 `index<=0xFE` 形成 `0x50E000+index*0x10`，再按子索引 `0/1` 取 `+0/+4`；另一模式把同一对子记录整体移到 `+0x08/+0x0C`，最后写入一个 DWORD。因而每个 16B 条目可静态拆成两条 8B 通道、每条含两个 4B 子记录；DWORD 的业务语义仍不命名。
- `0x421E60` 读取时用 `mode*8` 选择 `0x50E000` 的前半/后半通道，再按 `index*0x10` 和子索引 `0/1` 取 4B 子记录。非空子记录先比较 `byte[entry+2]`，再把 `WORD[entry]` 经 `0x4061E4` 映射到人物记录 R，并把 `byte[entry+3]` 与名字表/格式化链一起输出；模式 1 则改为在 `entry+0/+1/+2` 三个字节中匹配调用者键。
- `0x4772D4` 使用同样的 `index*0x10 + mode*8 + subindex*4` 布局：模式 0 先比较子记录首 WORD，再比较外部三字节键与 `entry+2`；非零模式统计匹配数。命中后取 `entry+3`，再调用 `0x41B707` 继续序列化/输出。因此它是查找/序列化消费者，不是 HP/MP 或特效最终写回点。
- `0x402CF9` 的调用者 `0x41301E` 先由 R→DataID，再把 `R+0x2E/+0x31/+0x34` 三个三字节单元送入查表；函数分别扫描前半和后半 8B 通道，并把命中结果交给 `0x413009` 合并。当前静态可确认的是“R 的装备/效果候选键 → 0x50E000 双通道子记录 → DataID/文本/输出链”，不能把 `entry+3` 直接命名成特效值或伤害值。

### 125.7.6 `0x50E000` 的原生填充来源：0x72 P1=10（当前样本静态）

- 当前样本原始字节表 `0x47D8DF` 中，索引 10 的表项位于 `0x47D907`，其 DWORD 为 `0x411C4A`；因此 `0x47D89E` 的 `P1=10` 分派会进入 `0x411C4A`。这不是按函数附近地址猜测，而是表项字节与分派器乘 4 规则的直接对应。
- `0x411C4A` 的函数体先经 `0x426E64` 解析输入，再按 `index<=0xFE`、子索引 `0/1` 和前/后 8B 通道写入 `0x50E000+index*0x10`；所以 `0x50E000` 的填充入口可以静态绑定到原生 `0x72 P1=10`，而不是只把它当成未知运行时缓存。
- 编辑器侧外部名单把 P1=10 标成“装备专属和套装”，这与 `R+0x2E/+0x31/+0x34` 三字节候选键及双通道条目形状相互吻合；但 6.6 当前样本尚未把该外部名称升级为完整产品语义，也没有证明写入后必然进入 HP/MP/状态 setter。

### 125.7.7 `0x426E64` 与 P1=10 的文本参数契约（当前样本静态）

- `0x426E64` 是单项字符串转数值解析器：连续十进制数字形成一个值；首位可带 `-`；首位可带 `*`，此时按 `dword[0x502000+n*4]` 取变量值；调用者使用返回的 `EDX` 作为 token 消耗长度，并自行加 1 跳过分隔符。它不是 `slot→U` 或 `DataID→R` 转换器。
- `0x411C4A` 对 P1=10 的 P2 采用两段格式：第一行解析为 `mode`，要求 `mode<2`；第二行解析 `5+mode` 个数。因此 `mode=0` 时有 5 个数，`mode=1` 时有 6 个数。
- 设第二行参数为 `v0,v1,...`：`v0<2`，写入地址选择子记录；`v1<=0xFE`，选择条目索引。最终地址可静态写成：`entry = 0x50E000 + v1*0x10 + mode*0x08 + v0*0x04`。
- `mode=0` 时 payload 由 `v2` 的低 16 位、`v3`、`v4` 组成 4B DWORD（对应 `entry+0/+1/+2/+3`）；`mode=1` 时 payload 由 `v2,v3,v4,v5` 四个低字节组成 4B DWORD。机器写点是 `0x411CD0: [entry]=payload`。
- 当前 RS 只读扫描复用 `大鲸鱼产生专用\_剧本体检.py` 的 `parse_eex/parse_command`：`0x72 P1=10` 共 609 条，去重后 228 种 P2 文本形状。样例：`0\n0,99,64,52,31` 对应 mode0、sub0、index99、payload(v2=64,v3=52,v4=31)；`1\n0,154,41,255,122,65` 对应 mode1、sub0、index154、payload=[41,255,122,65]；`1\n1,149,31,255,255,4` 对应 mode1、sub1、index149、payload=[31,255,255,4]。
- 因而“装备专属和套装”目前可以精确到一个原生双通道 16B 条目写入协议；`v0/v1` 的产品名称、payload 四字节的最终业务语义，以及后续 `0x413009`/HP/MP/状态是否消费，仍保持动态待验证。

### 125.7.8 `0x413009` 的结果合并边界（当前样本静态）

- `0x413009` 本体不读写 `0x50E000`，它只把父调用准备好的三项寄存器交给 `0x40BF2F`：`ECX=p2`、`EDX=旧累计值`、`EAX=当前新查询值`。当 `p2==2 且 EDX==0` 时，`0x413015` 先把当前 EAX 复制到旧值槽，再进入合并器。
- `0x40BF2F` 的当前样本规则是：`ECX=0` 做加法；`ECX=1` 取较大值；`ECX=3` 按位 OR；其它值在 `AL==7` 时保留当前 EAX，否则回退到旧 EDX。于是 `p2==2` 的首次查询（旧值为 0）可能表现为“命中但累计值看起来不变”，这不是 HP/MP setter。
- `0x402CF9` 的两段 `0x50E000` 查表结果会在父帧中交给 `0x413009`；因此当前静态链可以写成：`R+0x2E/+0x31/+0x34 → 0x402CF9 → 当前查询 EAX → 0x413009(p2,旧值) → 合并结果`。合并结果是否继续进入特技、状态或 HP/MP，必须沿更上层调用者继续追。

### 125.7.9 角色 Data/R 与两条特效查询渠道的交汇（当前样本静态）

- `0x41301E` 的输入先从 R 经 `0x40BE7D` 得 DataID，再把低字节特技号按 `p1*0x10` 进入 `0x4198BE`；`0x4198BE` 以 `[0x500C3B]=0x511000` 的 16B 行为参数，调用运行时 `[0x4F0008]`（当前 DLL 注册为 `ExtendData.dll!GetPersonEffect`），返回低字节后经 `0x42FBE1/0x413009` 合并。
- 随后同一个 `0x41301E` 又把 `EDX=0x50E000` 交给 `0x402CF9`，用 R+0x2E/+0x31/+0x34 的三字节候选键查第二张运行时表，再回到 `0x413009`。因此当前静态全链是：`slot→U→U[0]=DataID→R→(0x511000 行 + GetPersonEffect)→合并→(0x50E000 双通道查表)→合并`。
- `0x47B75B` 也会经过 `[0x4F0008]`，但它的调用约定和后续是资源/UI/记录路径，不能把所有 `[0x4F0008]` 命中统一命名为 HP 或伤害。真正的效果生效仍须继续看到特技/状态/HP/MP 的具体消费者。
