## 1. 结论速览

1. **特技桩的参数是四元组**：`push p1 / push p2 / push 类别 / push 名表id` ⇒ **"桩内号"是"类别"**（同一类别可用于不同名表 id，靠 `p1/p2` 区分）✓
2. **两个落点**：`0x4101D9`（**真判定**，138 行静态桩里占 **107**）｜`0x42518F`（**分流包装**，占 **31 行 / 去重 30 个特技**）✓
3. **分流规则**：主值 **`0x4AC63C` == 3** ⇒ 走 `0x4101D9`；**≠ 3** ⇒ 走 `0x41301E`（第二判定）→ `0x4198BE` → **`[0x4F0008]` = `ExtendData.dll!GetPersonEffect`**（MOD 自带 DLL）✓
4. **真判定链**：`0x4101D9` → `call 0x426A07` → `call 0x40658F`（由单位记录取 person）→ 返回 **`[person+4]` 低字节** → 调用者与 `0xFF` 比较判"是否命中"✓
5. **`0x40B922` = "主值 == 3 ?" 的布尔谓词**（`call 0x40B913 / cmp al,3 / sete`），**不是分流器**；落点 A/B 两条链都用它 ✓
6. ⇒ **实用含义**：那 30 个特技的判定**随语境（主值是否为 3）变化** ⇒ **"预览/战斗外"与"战斗中"可能走不同实现** ✓

## ⚠️ 08:5x 框架修正（用户口径 2026-10-17 09:2x）：「并不是每个特技都是伤害加成或五维加成的特技」

**用户原话**：「并不是每个特技都是伤害加成或者五维加成的特技吧。比如说你把二次行动加进来，他是类似回归、再行动的，
我觉得你应该先摸透这一些特技具体表现形式和作用」 ⇒ **本页此前的"分流族 ⇒ 预览可能不一致"框架是错的** ✓

### 为什么错（库内证据）
- `03-机制详解/二次行动.md:5-10` 速览写明：二次行动是**行为/状态机类**特技 ——
  判定入口桩 `421175`（`push 01/01/5A/38`）、**每回合只生效一次的载体是状态数组 `508B00[unit_id]`**、
  行动结束判定 `412D52`、恢复行动力 `406690`（位掩码 `06`）⇒ **它根本没有"收益数值"，也没有"预览值"** ✓
- 因此：**"分流族 43 个"只说明"它们的判定入口走 `0x42518F`"，与"是不是数值类"无关** ⇒
  把它们一律拿去验"预览 vs 实战"是**方向性错误**（用户判断正确）✓

### 正确的工作顺序（改成本页的正式口径）
1. **先分类**：按"作用表现形式"把特技分组（至少：**行为/动作类**、**数值加成类**、**触发/响应类**、**状态/免疫类**、**资源/经济类**）——
   权威来源 = 库内族页 `_族域权威映射.md`（族→域）＋ 39 份 `_族-*.md` ＋ `特技族逐族反汇编-第1~4批.md` ＋ 各特技专页（如 `二次行动.md`）
2. **只对"数值类"谈预览**：只有会算出"伤害/减伤/命中/暴击/属性"数字的特技，才存在"预览显示什么"的问题 ✓
3. **行为/状态类**要验的是**触发时机与次数**（例如二次行动 = 每回合一次、`508B00` 状态机），
   判据用**内存/日志**（如 `508B00[unit]` 由 `00 → FF`），**不是**看预览数字 ✓
