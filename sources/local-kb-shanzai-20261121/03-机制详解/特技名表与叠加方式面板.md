# 特技名表与叠加方式面板

## 结论速览

- **个人特技名表**：基址 **文件 `0x9E800` / VA `0x4CC600`**，**255 行 × 16 字节**，
  行格式 **名字 12 字节(GBK) + 2 字节零 + 显示 flag 2 字节(小端)**。
  **行号 = 特技号**。
- **图形工具** `大鲸鱼产生专用/_特技叠加面板.py`：左侧列出「特技号 / 名字 / 是否可叠加」，
  右侧显示判定调用点明细，可**设为叠加 / 设为不叠加 / 撤销**，
  支持**导出配置 / 导入配置 / 写入引擎**。
- 叠加方式语义（判定桩 `0x4101D9` 第 2 个参数）：
  **`0`=叠加（个人+装备累加）**、**`1`=不叠加（只取一个）**、`2`=装备优先回退个人。

## 适用版本

- 复刻版6.6山贼 `Ekd5.exe`。名表在 `.api` 节。

## 已确认事实

### 1. 名表结构（2026-10-14 实测校正）

| 项 | 值 |
|---|---|
| 文件偏移 | `0x9E800` |
| VA | `0x4CC600` |
| 行大小 | 16 字节 |
| 行数 | 255 |
| 名字字段 | **12 字节 GBK**（不足补 `0x00`） |
| flag 字段 | 末尾 **2 字节小端** |
| 行号语义 | **= 特技号** |

逐行复读样例：

```
行 00: B8 A8 D6 FA B9 A5 BB F7 B8 F1 B5 B2  00 00  00 02   "覆海之龙" flag=2
行 01: D5 E6 D4 AA C1 F7 D7 AA 00 00 00 00  00 00  00 05   "真元流转" flag=5
行 24: B7 C0 D3 F9 B1 A9 BB F7 00 00 00 00  00 00  00 00   "防御暴击" flag=0
行 B3: BC F5 C7 E1 C1 AC D0 F8 B9 A5 BB F7  00 00  00 03   "减轻连携攻击" flag=3
```

- 名字搜索验证：`"覆海之龙"` 命中 VA `0x4CC600`；`"防御暴击"` 命中 VA `0x4CC840`
  （`(0x4CC840 − 0x4CC600)/16 = 0x24` ⇒ 行号 = 特技号 ✓）。
- 有名字的行 **252 / 255**（空行 3 个）。

### 2. ⚠️ 旧口径错在哪（已纠正）

| 项 | 旧口径（错） | 新口径（对） |
|---|---|---|
| 名表 VA | `0x4CC800` | **`0x4CC600`** |
| 行格式 | 名字 8B + 保留 7B + flag 1B | **名字 12B + 2B 零 + flag 2B** |

旧口径之所以"看起来能用"：把名字当 8 字节去读，整体**错位 0x20 行（= 0x200 字节）**，
于是读出来的中文虽然也是中文，但**行号与特技号系统性错配**
（例如把 `0x33` 读成"众矢之的"，而 `0x33` 实际是"致命一击"）。
本轮改用「直接搜名字定位基址」打破了这个自洽错误。

### 3. 叠加方式扫描结果（本样本）

- 判定桩调用点 **150 个**；可解析出特技号 **98 个**；未解析 **46 个**（动态/代码洞写法）。
- 分布：**叠加方式 `0` = 23 个调用点**、**`1` = 80 个**、**`3` = 2 个**。
- 同一特技号多调用点：`0x24`、`0x34`、`0x35`、`0x3A`、`0x48`、`0x70` 各有 2 处；
  其中 **`0x48` 两处叠加方式不一致**（`0x4E3081`=0、`0x4E31C5`=1）。

```bat
:: 图形面板（推荐）
大鲸鱼产生专用\_pyrun.cmd 大鲸鱼产生专用\_特技叠加面板.py

:: 不开界面的数据核对
大鲸鱼产生专用\_pyrun.cmd 大鲸鱼产生专用\_特技叠加面板.py --dump

:: 命令行查询/修改（无界面场景）
大鲸鱼产生专用\_pyrun.cmd 大鲸鱼产生专用\_特技叠加检测.py --skill 0x24
大鲸鱼产生专用\_pyrun.cmd 大鲸鱼产生专用\_特技叠加检测.py --apply 0x24 0

:: 导出名表（TSV/JSON）
大鲸鱼产生专用\_pyrun.cmd 大鲸鱼产生专用\_特技名表导出.py
```

面板行为：
- 界面上的修改**先记在内存**（黄色高亮 = 待写入），点「写入引擎」才落盘。
- 写入走 `_dsh写锁.py` 的 `safe_write_exe()`（W1~W5：游戏未运行 → 取锁 → SHA 校验 →
  备份 → 写 → 复读 → 审计）。
- **导出配置**：JSON，含特技号→新叠加方式、每处改动地址/旧值/新值、EXE SHA。
- **导入配置**：载入后若 SHA 与当前引擎不同会提示。

## 风险与边界

- **46 个调用点是动态参数**（特技号由 `al` 算术或栈帧转发算出），面板对它们
  显示「?」且不可直接修改 —— 需编辑对应代码洞。
- **多调用点**：一个特技号若有多个判定点，面板会**一起改**（这是刻意的，
  避免只改一半导致行为不一致）；`0x48` 原本就"一 0 一 1"，改前先定意图。
- 名表里"有名字"不等于"该特技在本版本生效"；生效与否要看是否有判定调用点。
- 叠加方式 `2`（装备优先回退个人）在本样本扫描中**未出现**。

## 证据来源

## 覆盖率提升与「检测不到」的成因（2026-10-14 追加）

### 1. 多入口扫描把覆盖从 123 提到 165

原来只扫 `call 0x4101D9`。实测引擎的判定/取值入口不止一个：

| 入口 | 语义 | 调用点数 | 参数顺序 |
|---|---|---|---|
| `0x4101D9` | 核心双渠道判定（包装层，内部转调 `0x41301E`/`0x413009`） | 150 | 效果值方式/叠加方式/宝物号/特技号 |
| **`0x42518F`** | **双渠道包装**（破坏MP攻击、方寸天地等用它） | **59** | **与 `0x4101D9` 完全相同**（实测反汇编确认） |
| `0x413009` | 取值路径 | 7 | — |

`0x42518F` 函数体（关键部分）：

```
0042518F  55               push ebp
00425190  8B EC            mov  ebp, esp
00425192  51               push ecx
00425193  FF 75 14         push [ebp+0x14]
00425196  FF 75 10         push [ebp+0x10]
00425199  FF 75 0C         push [ebp+0xC]
0042519C  FF 75 08         push [ebp+8]
0042519F  E8 7E 67 FE FF   call 0x40B922
004251A7  85 C0            test eax, eax
004251A9  74 07            je   0x4251B2
004251AB  E8 29 B0 FE FF   call 0x4101D9     ; ← 命中走核心判定
004251B0  EB 05            jmp  0x4251B7
004251B2  E8 67 DE FE FF   call 0x41301E     ; ← 否则走双渠道检查
004251B7  8B E5            mov  esp, ebp
004251BA  C2 10 00         ret  0x10
```

⇒ **两个入口共用同一套 4 参数**，所以扫描结果可以直接合并。

**成果**：调用点 150 → **216**；可解析特技号 123 → **165**。

### 2. 参数回溯放宽

旧实现遇到 `mov ecx,[ebp-0x20]`（传单位指针）就**中断**，把
`push 1 / push 1 / push 0x44 / push 0x30 / mov ecx,[ebp-0x20] / call` 这种
**明明有 4 个立即数**的调用点判成"动态"。现已改为**跳过 mov/lea 继续回溯**。

### 3. 「名表有名字但检测不到」的成因（89 个）

对 89 个未覆盖特技做**立即数引用普查**（`_特技号引用普查.py`），结论分两类：

**(a) 25 个完全无引用 ⇒ 引擎预留名**

```
87 空置      8A 自动提升   8B 霸者之威   8E 提升周围   8F 命若洪炉
93/94 气贯长虹   95/97 穿透攻击   99 天纵之资   9B/9C 远距攻击
AA 封锁攻击范围   E3 踏阵   E4 陆战精通   E5 水战精通   E6 山林精通
E7 火战精通   E8 刀剑震鸣   E9 满弓取敌   EA 碎念焚心   EB 虎啸震惶   EE 气吞万里
```

这些特技号在可执行节里**没有任何立即数引用** ⇒ 名表占位、引擎未实现，
**本来就不存在"叠加方式"可改**。

**(b) 64 个有 `push imm` 引用，但经核验属误匹配或非判定用途**

- 引用数高得可疑（`0x03` 有 398 处、`0x04` 有 524 处）⇒ `6A imm8` 是极常见的
  指令字节，普通函数参数会被当成特技号。
- 逐点核验（如 `0x402520` 的 `push 3`、`0x401177` 的 `push 4`）确认：
  这些是**普通函数参数**，不是特技判定。
- 进一步统计这些 `push imm` 后紧跟的 `call` 目标（`_找漏检入口.py`），
  得到的高频目标（`0x423971`、`0x47CAE3`、`0x47D1F1` 等）经核验为
  **普通业务函数**（经验结算等），**不是隐藏的判定入口**。

⇒ 结论：`每回合获得exp`、`破坏攻击/防御/精神/爆发/士气/移动`、
`麻痹/封锁/混乱/中毒攻击` 等**不走特效判定桩**，其"叠加"语义不适用
（它们要么由数据表配置、要么在命中流程里直接实现）。

## 2026-10-15 修正：名表行布局（**+12/+13 属名字区；有效字段是 `+15` 单字节组号**）

> 数据来源：`Ekd5.exe` SHA256 `25DB2211FE8F495DE4993BAB296C23C180E18679F00A0E43B47B1FD2034B7EAF`，
> 名表 VA `0x4CC600`（文件偏移 `0x9E800`），**对全部 255 行做逐字节分布统计**；证据层级 = 1 静态。

### 实测分布（255 行）

| 偏移 | 不同取值数 | 最常见 | 判读 |
|---|---|---|---|
| `+12` | 11 | `0x00`×241，其余 `0x70/0xF1/0xF7/0xF2/0xF9`… | **不是恒零**（14 行有数据）⇒ 长名字的延续字节 |
| `+13` | 2 | `0x00`×254、`0xDB`×1 | 同上（极少数 14 字节名字） |
| `+14` | 3 | `0x00`×253、`0xAA`×1、`0xED`×1 | **实测恒零**（两处异常值同属长名字残字节） |
| `+15` | **18** | `0x00`×80、`0x04`×70、`0x02`×31、`0x0B`×12、`0x03`×11、`0x05`×10 … | **唯一的有效字段**：值域 `0..0x0F`（16 组） |

- 16 位小端（`+14/+15`）分布全是 `0xNN00` 形态（`0x0000`×79、`0x0400`×69、`0x0200`×31、`0x0B00`×12 …）
  ⇒ 旧口径"flag 2 字节小端"里**低字节恒 0**，真正携带信息的是**高字节（`+15`）**。

### 修正后的行布局

| 段 | 偏移 | 长度 | 说明 |
|---|---|---|---|
| 名字 | `+0..+13` | **最多 14 字节 GBK** | 常见 12 字节（旧口径只记了 12）；不足补 `0x00` |
| — | `+14` | 1 | 实测恒 `0x00` |
| **组号/分类** | `+15` | 1 | **`0..0x0F`（16 组）**，疑为界面的特技分类标签（**语义未证**） |

### 影响与处置

- 旧口径「名字 12 字节 + 2 字节零 + flag 2 字节」**在两处不准**：
  ① 名字区实际可到 **14** 字节；② 有效字段是 **`+15` 单字节**，不是 2 字节小端。
- **改名字/写名表时必须按 14 字节上限处理**，否则 13~14 字节的长名字会被截断或覆盖 `+14/+15`。
- 已同步 `90-来源归档/复刻版6.6山贼错误知识纠正台账.md`（口径收窄）。样本读数（第六节已给）不变。
- **P2**：`+15` 组号的语义（是否即界面分类/排序）未证；判据：改一行的 `+15` 后看界面列表是否换分类（**不动用户存档/剧本**）。

## 2026-10-15 第 10 轮：名表行 `+0x0F`（组号）**用途定案** = 特技"标签/类别码"

> 样本 `Ekd5.exe` SHA256 `25DB2211FE8F495DE4993BAB296C23C180E18679F00A0E43B47B1FD2034B7EAF`；**证据层级 = 1 静态**。

### 1. 名表行的解码器 `0x418D97`（57 字节，`ret 0xC`）—— **直接读 `行 + 0x0F`**

```asm
00418D97  push ebp / mov ebp,esp / sub esp,0x20
00418D9D  mov  ecx,[ebp+0xC]              ; 参2 = 行地址（= 0x4CC600 + 特技号*16）
00418DA0  movzx eax, byte [ecx + 0x0F]    ; ★★ 读行内 +0x0F（本库实测的"组号"）
00418DA4  push eax
00418DA5  mov  al, byte [ebp+0x10] / push eax   ; 参3（字节）
00418DAD  call 0x428346                   ; ★ 按 (参3, 组号) 组织标签文本 → [ebp-0x20]
00418DB6  push [ebp+0xC]                  ; 行的名字（12B）
00418DB9  push 0x48E668                   ; 格式串
00418DC1  call dword [0x4862C0]           ; 格式化（IAT）
00418DCD  ret  0xC
```

**格式串（实测）**：`0x48E668` = **`"%s %s"`**（名字 + 标签）；列表/详情另用
`0x48B447` = `"  %s  %s\n"`、`0x48B45B` = `"  %s\n"`（见 `0x421F13`/`0x421F1B`/`0x41B727` 三处调用）。

⇒ **结论：名表行 `+0x0F`（值域 `0..0x0F`，16 种）是"特技标签/类别码"**，
被解码器取出后与名字一起显示（`"%s %s"`）。

### 2. 名表基址 `0x4CC600` 的**全部读者（6 处）**

`0x41B714`（`shl eax,4 / add eax,0x4CC600` → `0x418D97` → `"  %s\n"`）、
`0x421F01`、`0x421F55`（`imul eax,eax,0x10` → `0x418D97` → `"  %s  %s\n"`；同段还有 `cmp cl,[eax]/[eax+1]/[eax+2]` 的三字节比较 ⇒ 可能是**装备/个人特技位图判定**）、
`0x44D8D2`、`0x466E53`、`0x467B22`。
⇒ 都是"**特技号 ×16 + 基址 → 行 → 解码/格式化**"的同一模式。

### 3. 与"叠加方式"的区分（重要，别混）

| 关注点 | 来源 | 取值 |
|---|---|---|
| **是否可叠加** | 判定桩 `0x4101D9` 的**第 2 个栈参** | `0`=叠加（个人+装备累加）、`1`=不叠加、`2`=装备优先回退（本库既有登记） |
| **标签/类别码** | **名表行 `+0x0F`** | `0..0x0F`（16 种），仅用于**显示标签** |

⚠ 旧口径把名表末 2 字节称作"显示 flag"（含义未解）；本轮定案为 **`+0x0F` 单字节标签码**，
`+0x0E` 恒 0，`+0x0C/+0x0D` 属名字区（见本页"行布局修正"节）。

- **P2**：`0x428346`（实际入口 `0x4282FD`，78B）→ `0x4281C7`（5 参）所取的**类别文本表**地址与 16 个类别名
  （判据：`func 0x4281C7` + 它引用的字符串表；也可用 `string` 搜界面文字反查）。

## 2026-10-15 第 15 轮：★ 纠正 —— 名表 `+0x0F` 那条链的真实被调者是 **`0x452D81`**（`0x428346` 只是跳板）

### 1. 事实（原字节）

```asm
004282FD  55 8B EC                  push ebp / mov ebp,esp      ; ★ 真入口（前一条 ret 0x14 之前是上一函数）
00428300  push [ebp+0x18] / [ebp+0x14] / [ebp+0x10] / [ebp+0xC] / [ebp+8]
0042830F  call 0x4281C7              ; 5 参原样转传
...
00428342  5D                        pop ebp
00428343  C2 14 00                  ret 0x14                    ; ★ 5 参 stdcall（函数到此结束）
00428346  E9 36 A9 02 00            jmp 0x452D81                ; ★★ 这是**跳板**，不是函数体！
```

⇒ **`0x418D97` 里的 `call 0x428346` 实际经跳板进入 `0x452D81`**（5 参）。

### 2. ★ 纠正我在第 10 轮的措辞

- 原写法（作废）："`0x418D97` → `call 0x428346` **组织标签文本**，再按 `"%s %s"` 与名字合成"
  ⇒ 把 `0x428346` 当成"文案组织函数"。
- **正确**：`0x418D97` 的调用**经 `0x428346` 跳板**到 **`0x452D81`**（真正做事的函数）；
  而 `0x428346` 所在函数 `0x4282FD`（5 参）只是把参数转给 **`0x4281C7`** ——
  `0x4281C7` 是 **坐标/偏移计算器**（读两张 word 表 `0x48B8B0` / `0x48B8C0`，
  实测表值域为 `-1/0/1` 这种小偏移，属**排版/描边类**），**不是"类别文字表"**。
- ⇒ **名表 `+0x0F`（标签码）最终产出什么文本/图形，落在 `0x452D81`**；本页此前"类别文案"的推测**未经证实**，
  已降级为 P2（`0x452D81` 待读）。

### 3. ★ 通用纪律（已写入工具链页）：**`call` 目标处若是 `E9 rel32`，必须跟跳到真实被调者**

- 症状：按 `call` 目标反汇编会看到"参数个数对不上"（本例：调用点压 3 个参数，
  而目标所在函数是 `ret 0x14` 的 5 参函数）——这正是**跳板**的典型症状。
- 处置：`db <目标> 8` 看首字节；若是 `E9`，取 `rel32` 算出真实地址再把参数按**真实被调者**核对。
- 识别特征：函数末尾 `pop ebp / ret imm16` 之后紧跟 `E9 rel32`（本样本 `0x428343` 后即 `0x428346`）。

## 2026-10-15 第 16 轮：名表 `+0x0F` 链的**真身链**与产物形状（含跳板纠正）

### 1. 完整调用链（已用 `thunk` 工具自动跟出）

```
0x418D97(输出, 行地址, 参3)                 ; 名表行解码器（读 行+0x0F）
  --call--> 0x428346                        ; ★ 跳板①：E9 头
              --jmp--> 0x452C81             ; ★ 跳板②：序言 + 参数重排 + 尾跳
                         --jmp--> 0x4322D3  ; ★ 内部入口（真身）
```

- **跳板② `0x452C81`（79 字节，`push ebp/mov ebp,esp/push ecx/mov ecx,[ebp+0xC]/mov eax,[ebp+0x10]/jmp`）**：
  只做**参数重排**（把参2 挪到 ECX、参3 挪到 EAX）后尾跳 ⇒ 说明真身约定「**ECX = 行/对象指针，EAX = 参3**」。
- **真身 `0x4322D3`**（内部入口，位于 `0x432220..0x43237C` 内）：

```asm
004322D3  mov  eax, dword [ebp+0x10]     ; ★ 编号（由跳板②从参3 搬进 EAX ⇒ 这里读栈上原参）
004322D6  cmp  eax, 0x14 / jne
004322DB  mov  edx, 0x432407 / jmp 0x43234E   ; ★ 0x14 ⇒ 数据块 `0x432407`
004322E2  cmp  eax, 0x11 / jne
004322E7  mov  edx, 0x432427 / ...             ; ★ 0x11 ⇒ 数据块 `0x432427`
```
⇒ **形状 = "按编号选一段数据块（`0x432407`/`0x432427`/…，数据内嵌在 `.code` 里）"**；
编号来自名表行 `+0x0F`（经 `0x418D97` 的参数链）。

### 2. 同函数族里的**百分比格式化**（强旁证）

`0x432220..0x432246` 是一条独立小函数：
```asm
00432220  push ebp / mov ebp,esp / push eax
00432224  shr  ecx, 5              ; 位数/宽度换算
00432227  imul ecx, ecx, 0xA        ; ×10 ⇒ 十进制
0043222A  test ecx,ecx / jne 0x432233
0043222E  mov  ecx, 0x64            ; 为 0 ⇒ 100
00432233  push ecx / push 0x48E694 / push eax
0043223A  call dword [0x4862C0]     ; 格式化
```
**格式串实测 `0x48E694` = `"+%d%%"`** ⇒ 产出形如 **`+30%`** 的文本。

### 3. 结论（收窄后的表述，替代第 10 轮的"类别文案"说法）

- 名表行 `+0x0F` 的显示产物 = **"按编号选出的内嵌数据块"**（编号 0x11 / 0x14 / … 等），
  该函数族同时具备**百分比文本**（`"+%d%%"`）能力 ⇒ 更像**"数值/百分比标签"**而不是"类别名"。
- **仍未证**：`0x432407`/`0x432427`/… 这些数据块**具体是什么**（字符串？跳转号？）
  ⇒ **下轮首选（离线可做）**：`db 0x432407 <n>` 与 `db 0x432427 <n>` 直读，并枚举真身里**全部分支编号**。

### 4. 本轮附带

## 2026-10-15 第 17 轮：真身的产物性质**降级为未证实**（原第 16 轮推测作废）
