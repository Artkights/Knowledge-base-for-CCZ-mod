# 剧本特技：性能画像与三条落地路线

样本：`复刻版6.6山贼\Ekd5.exe`
脚本样本：`RS\S_85.eex`（38456 字节，1619 条指令 / 320 个 block）、全库 `RS\*.eex`
解析器来源：`ai使用库\小暗补丁6.6\源码\Guide.cpp`（`ParseEex/ParseBlock/ParseCommand` + `kParamCounts/kDwordMasks/kTextMasks`，本次已移植为 Python 并跑通）

## 结论速览

1. **为什么特技只能写在剧本里**：引擎里那个名字最像「挂特技」的指令 `0x71 特效请求`，真身是**战场文字/报告显示**（内部 15 项字符串表：`Lv`/`MAX`/`属性`/`被攻击近接`/`攻击`…），它**不是**特技执行器；引擎自带的特技通道（个人/装备特效表 `0x9F`、`0xB3` 那一套）只覆盖固定语义，新特技没有入口 → 只能靠剧本变量 + 战场指令自己算。
2. **卡顿不是「块太大」而是「块太多 + 条件重扫」**：`S_85.eex` 最大 block 只有 39 条指令，但有 **320 个 block**，每个 block 都带条件链（`0x05`/`0x79`/`0x36`/`0x3F`…）；全库最重的 `R_84.eex` 有 9638 条指令（变量类 2937 条，占 30%）。引擎侧成本 ∝ **事件块数 × 条件链长度**，而不是动作体大小 → 优化重点在「减少被反复测试的条件」。
3. **三条路都能走，而且有一条低风险捷径**：`0x00–0x7B` 里有 **9 个指令号在 173 个 `.eex` 里从未出现**（`0x10 0x1F 0x22 0x54 0x70 0x71 0x73 0x74 0x7A`）→ 可以把其中一个改造成**自定义指令**，让剧本用一条指令完成现在几十条变量运算 + `0x72` 读取的工作（路线②，改动可控制在「表项 4 字节 + 一个代码洞」）。

## 适用版本

- 仅适用复刻版6.6山贼当前样本；所有地址按本 EXE 的节区映射换算，改前必须复读原字节（样本 `Ekd5.exe` SHA256 `4DA289106E4F76CCD1E06CA8B11DA1A27B1E88C333F69CBECCEAB4016FEEE450`）。

> ⚠️ **角色待定（重要）**：上表条目既像「解析/构造函数」，又像「执行函数」——`0x78 整型变量赋值`（全库用了 5510 次，实际生效）对应的是**空占位**，而 `0x79/0x4D` 等走虚派发。最可能的解释是：**解析阶段用这张表构造指令对象，真正执行在对象虚函数里**；也就是说「加一条自定义指令」可能需要同时处理构造与执行两处。这一点必须再验证后才动手改表。

### 2. `0x71 特效请求` 不是特技执行器

```
00466EAF  push ebp / mov ebp,esp / push ecx
00466EB3  mov  ecx,[ecx+0x18]
00466EB6  push [ecx+8]
00466EB9  mov  edx,[ebp+8]
00466EBC  mov  eax,[ecx+edx*4]        ; 取参数
00466EBF  push eax
00466EC0  cmp  al,0x0E / ja 越界
00466EC4  push dword [eax*4 + 0x466F0B]   ; ← 这张表是【字符串指针表】
00466ECC  6A 00 / 68 11 10 00 00 / call [0x4862F4]   ; 格式化输出
```

`0x466F0B` 的 15 项指向 `0x486AC0`(`Lv`)、`0x486AC7`(`MAX`)、`0x486B98`(`属性`)、`0x486C18`(`被攻击近接`)、`0x486B48`(`攻击`)、`0x486B60`(`库存`)…全是**战场报告文字**。
→ 结论：`0x71` 是「请求显示某类战场文字」，**不能用来挂特技效果**；这也从引擎侧解释了「特技为什么只能写剧本」。

### 3. 九个从未使用的指令号（自定义指令的落脚点）

对 173 个 `RS\*.eex` 全量解析统计，**从未出现**的指令号：

| 指令号 | 对齐表名义 | 备注 |
|---|---|---|
| `0x10` | 许子将指导 | 无参数模板，样本零命中 |
| `0x1F` | 地图据点切换 | 同上 |
| `0x22` | 单挑 | 同上 |
| `0x54` | 战场撤退确认 | 同上 |
| `0x70` | 能力选择复制 | 有实现（`0x4644A6`）但用户没用 |
| `0x71` | 特效请求 | 即上面的战场文字显示 |
| `0x73` | 人物五围和测试 | 有实现（`0x4671A5`）但用户没用 |
| `0x74` | 开/禁存档 | 空占位（`0x472D38`） |
| `0x7A` | 对话3 | 与 `0x4E/0x64` 共用 `0x467721` |

→ 任选一个做自定义命令都不影响现有剧本；`0x54`/`0x74` 这类「结构保护/空占位」风险最低。

### 5. 成本模型（依据 + 待实测）

- 每次引擎判定「事件是否触发」都要走该 block 的**条件链**：`0x05 变量测试`（变长数组）、`0x79 变量测试`、`0x36 武将状态测试`、`0x3F 回合测试` → 每条都是一次解释器步骤 + 数据访问。
- `0x77 变量运算` 的处理函数 `0x46776A` 帧大小 `0x78`（120 字节），`0x72 信息传送` 的处理函数 `0x4670B5` 还要再分派子功能 → 单步成本不低。
- `0x02 内部信息` 在每块里都会被执行一次（S_85 115 处）→ 若纯属给自己看的注释，**可以直接删**，这是零风险收益（待确认它是否会在战场显示）。

> 上面三条是「按引擎结构推断」的成本模型：**结论方向可信（块数 × 条件链 主导），具体倍数未实测**。

### 6. 指令是「对象」：表在构造侧，执行走虚函数（本轮新证）

在 .code 里搜到 4 处 `call [reg+0x38]`（`FF 5x 38`）：

| 位置 | 上下文要点 |
|---|---|
| `0x464EE8` | `mov edx,[eax]`（取虚表）→ `call [edx+0x38]`，前置还有 `call [edx+0x40]`、`cmp eax,0x205` |
| `0x464F83` | 同一模式（`call [edx+0x40]` → `cmp eax,0x205` → `call [edx+0x38]`） |
| `0x465369` | 同一模式 |
| `0x472B68` | 就是分派表里 `0x37/0x4D/0x63/0x79` 共用的那个桩：`push [ebp+8] / mov edx,[ecx] / call [edx+0x38]` |

→ **结论：剧本指令被解析成对象，执行走对象虚函数**（`+0x38` 执行、`+0x40` 条件/取值、`+0x10` 取字段）。因此 `0x486FE8` 那张表是**构造/解析侧**（表项里出现空占位 `0x40E240`、以及转发虚函数的桩 `0x472B60`，都与「构造表」相符）。
→ **路线②的正确做法不是改那张表**，而是挂在**已有的多子功能指令**下面（`0x72` 有 33 个子功能、`0x71` 有 15 个、`0x7B` 有 4 个），或走下面的插件通道。

### 7. 引擎 ↔ 外部 DLL 的插件通道（本轮新发现）

- `Ekd5.exe` 的导入表**只有** `WINMM / COMCTL32 / KERNEL32 / USER32 / GDI32 / koeicda / Msimg32 / Jpg / GDIPLUS` —— **没有** `ExtendData.dll`，也没有 `Cmdicon.dll`。
- 但字符串 `ExtendData.dll` 在 `VA 0x48BB81` 出现 1 次，唯一的引用点在 `0x40A2EA`：`push 0x48BB81 / call <加载函数>` —— 也就是**运行期按名字加载插件 DLL**。
- `GetPersonMes / SetPersonMes / GetPersonEffect / AddPersonEffect / ChangePersonEffect / GetRoundChange / CanForge` 这些导出名在 `Ekd5.exe` 里**一次都没出现** → 引擎不是按名字调它们（库里 `semantic-reviews/P0-005`、`P0-006` 审阅的就是这些导出）。
- 另外：引擎大量使用 `call [0x4862F4]` 配合消息号（`0x1011 / 0x101B / 0x1027 / 0x1005 …`）；`0x4862F4` 是 `.text1` 里的一张 **导入名偏移表**（相邻项 `0x8995A / 0x89BFE / 0x89EE4 …`，按偏移解释正好落在 `.text1+0x475A`、`.text2+0x1FE`… 的导入名字符串上，第一项正是 `SendMessageA`）→ **这是 IAT 槽，运行期由加载器填成真实函数地址**，`[0x4862F4] = SendMessageA`。

> 我已更正一处中途推断：早先以为 `call [0x4862F4]` + `0x10xx` 是「剧本系统 API」，实际是 **SendMessageA + 自定义窗口消息**。
> **推论（未证实）**：mod 的扩展架构很可能是「打补丁的引擎发窗口消息 → `ExtendData.dll` 侧处理」，所以**加新能力的低成本做法是在插件通道上加一个消息号**，而不是改引擎分派表。

## 三条路线（做法 / 收益 / 风险）

### 路线① 把特技搬进引擎

- **做法**：在战斗管线挂点（已知可用：`0x437F9F` 攻击计算入口、`0x43F7B8` 地形发挥、`0x435991` 单位地形；特技查询用 `0x42518F` 双渠道包装）加代码洞，按「个人特效号 + 特效值」直接算效果；剧本只留一行触发或完全删掉。
- **收益**：最大。彻底消除解释器步骤与条件重扫。
- **风险**：需要把每个特技的语义翻成汇编，测试成本高；一处写错影响所有单位。
- **适合**：使用频率最高、逻辑最固定的 2–3 个特技。

### 路线② 剧本直接调用引擎（自定义指令）

- **做法（按本轮新证修正）**：**不要**去改 `0x486FE8`（它在构造侧，且执行走对象虚函数）。两条更省力的挂法：
  1. **挂在已有命令的子功能下**：`0x72 信息传送`（33 个子功能）、`0x71`（15 个）、`0x7B`（4 个）都是「子功能号 → 跳转」结构，挑一个**没人用的子功能号**，把它的处理指向代码洞；剧本侧仍然只写一条 `0x72`。
  2. **挂插件通道**：引擎会按名字加载 `ExtendData.dll`，并用 `SendMessageA` + 自定义消息号（`0x10xx`）与外部通信；在插件侧加一个消息号 + 处理函数，剧本侧由一条命令发出该消息即可。
  代码洞内再从指令参数取「单位/字段/目标变量」，**一次调用**引擎已有函数（`0x41B500` 当前HP、`0x472840` 当前MP、`0x4061E4`+`0x40BF0C` 兵种系、`0x42518F` 特效值），结果写回变量。
- **收益**：把「几十条 `0x77`+`0x72`」压成「1 条指令」，改写成本低、可逐条替换。
- **风险**：子功能号若选到「已实现但没人用」的，需先确认它没有别的语义；`0x72` 的子功能分派在 `0x463F9C` 一带（本轮只确认到它调用 `[0x4862F4]` 与虚函数 `+0x20`，**跳转表位置还没定位**）→ 动手前要先把这个跳转表找出来。
- **适合**：先做 1 条试点（比如「取单位当前HP/MP到变量」），验证通路后再扩。

### 路线③ 优化现有写法（零改引擎，先做）

| 手段 | 具体做法 | 预期 |
|---|---|---|
| 删调试信息 | 清掉 `0x02 内部信息`（S_85 115 处；若确认不显示） | 每块少一次调用 |
| 条件合并 | 把「同一变量分别等于 178/181/…」的多个 block 改成**一个 block**：算一次编号 → `0x05/0x79` 分派 | 块数直接下降，条件重扫变便宜 |
| 编号分派 | 用 `变量 = 特技编号`，配 `0x76 无条件跳转` 做表驱动，替代 N 个独立条件块 | 同上 |
| 常量预置 | 常驻量（使用者、战场号、data 序号）只在**回合开始**算一次，别在每个块里重算 | 去掉重复的 `0x77` |
| 少用 `0x72` | 同一次判定里重复读取的字段，读进变量后复用 | 减少子功能分派 |

## 六、路线②的落地点（另有专页）

`0x72 信息传送` 的子功能**不在 EXE 里**：EXE 只整理参数，然后 `SendMessageA(hwnd, 0x102C, 子功能号, …)` 交给插件 DLL `ExtendData.dll`（它自己 `RegisterClassW/DefWindowProcW`，导出里就有 `LoadVar/SaveVar/GetPersonMes/SetPersonMes/GetPersonEffect/AddPersonEffect…`）。
→ 加原生子功能的两种落地（插件侧 / EXE 侧拦截 `0x464599`·`0x4670B5`）、扩展槽表 `0x4F00xx` 全映射、可用引擎函数 ABI：见 **`08-剧本与战场/剧本子功能原生化-路线②落地设计.md`**。

### 通用单条指令执行器（本轮新挖）

```
00464E90  push ebp / mov ebp,esp / sub esp,0x30 / mov [ebp-0x30],ecx   ; ECX = 指令对象
00464E98  ... and eax,0xFFFF / cmp eax,-1 / je ...
00464EA5  call 0x463ECD                       ; 前置检查
00464EB8  mov edx,[ebp+8] / cmp edx,[ecx+0x10] / je ...
00464EC3  mov edx,[eax] / call [edx+0x40]     ; ★ 虚函数：判定/查询
00464ED0  mov eax,[ebp+0x10] / and eax,0xFFFF / cmp eax,0x205 / jne ...
00464EDC  push -1 / mov edx,[ecx] / call [edx+0x38]   ; ★ 虚函数：执行
00464EF1  ... call [edx+0x10] / ... 
00464F04  push 2 / push 结果 / push 0x102C / push [对象+0x10] / call [0x4862F4]   ; ★ 又把结果发给插件 DLL
```

要点：
1. **判定与执行分离**（`+0x40` 判定返回码 `0x205` → `+0x38` 执行）。
2. **同一条指令的执行过程也会跟插件 DLL 通信**（`0x102C` 消息 + 结果码）→ 进一步印证「很多指令语义在 DLL 侧」。
3. `0x464E90` **没有直接 caller**（全库 `E8/E9` 扫描为 0）→ 它是**间接调用**（表/虚表驱动）→ 用静态扫描找不到驱动循环，这也是「重扫频率」至今没测到的原因。

## 十、成本机制：变量操作 = 一条窗口消息往返（机制已证；量级未测）

- `0x77 变量运算` 的 EXE 处理器 `0x46776A` **不做算术**，只解析操作数，然后：
  `push 2 / push [对象+8] / push 0x102C / push [对象+0x10] / call [0x4862F4](=SendMessageA)`，
  以及循环内 `push 操作数缓冲指针 / push 下标 / push 0x1019 / …` 和 `push 下标 / push 0x101D / …`。
- `0x101D` 在 `ExtendData.dll` 内命中 **116 处**、`0x1019` 命中 37 处 → **变量存储与算术都在插件 DLL**。
- 规模：全库变量类指令 ≈ 2 万条（`0x77` 10691、`0x78` 5510、`0x79` 4088）；`S_85` 512 条（占 32%），`R_84` 2939 条。
- **成本链条（机制）**：事件判定/执行 → 每条变量指令 → 一次 `SendMessageA` 往返（user32 + DLL 分派 + 栈缓冲）。
- ⚠️ **量级提醒（重要，避免误导）**：同进程 `SendMessage` 单次约 0.5–1µs，全库 2 万条摊到一整场战斗**可以忽略**。
  真正决定卡不卡的是**这些条件被执行/重扫的频次**：
  - 若是「每回合扫一遍」→ 每回合几百次 ≈ 亚毫秒，不成问题；
  - 若是「每帧扫一遍」（60fps）→ 每秒数万次 ≈ 数十毫秒/帧 → **必然卡**。
  所以「重扫频率」才是唯一决定性的未知量，优先级高于任何写法优化。
- **据此的优先级**（在频率未测前，先做不会错的部分）：
  1. 路线③（合并条件、少算、去掉调试信息）＝ 直接减少消息次数 —— **最确定、先做**；
  2. 路线②（DLL 侧批量/新子功能，一次消息干多件事）—— 次之；
  3. 路线①（战斗公式侧原生化）—— 影响面大但工程量大。

### 怎么测「重扫频率」（可直接做的三种办法）

| 办法 | 做法 | 判读 |
|---|---|---|
| **① 删块对照（最快，零改引擎）** | 复制一份 `R_84.eex`（条件最多的文件）→ 在剧本编辑器里把其中**一个重场景的全部条件块**改成恒真（或删掉条件，只留动作）→ 进同一关对比回合耗时/帧率 | 若明显变快 ⇒ 成本确实在「条件重扫」，且频率高；若没变化 ⇒ 成本在别处（动作体/引擎侧） |
| **② 计数桩（要打补丁，最准）** | 在通用指令执行器 `0x464E90` 入口插 5 字节 `jmp` 到代码洞，洞内 `inc dword [计数]` + 原指令 + 跳回；把计数显示到 `0x02 内部信息` 或写盘 | 直接得到「每帧/每回合执行了多少条指令」 |
| **③ 采样对比** | 同一关，分别只保留「条件块」与只保留「动作体」，各跑 3 回合计时 | 分离条件开销与动作开销 |

> 建议先做 ①（不动引擎、可回退），它能一次性回答「到底该优化条件还是优化动作」。

## 十一、成本模型细化（本轮实测，修正口径）

逐条查了「条件类」与「变量类」指令的 EXE 处理函数，结论比上一版更精确：

| 指令 | EXE 处理函数 | 是否发 DLL 消息 | 成本判断 |
|---|---|---|---|
| `0x05 变量测试`（数组式条件） | `0x41CE40` | **完全不发**（0x200 字节内 `SendMessageA` 命中 0） | **便宜**：纯 EXE 解释 + 内部取值函数（`0x401DFF`、`0x412B30`、`0x4179B4`、`0x41B500`＝当前HP、`0x40FA0B`、`0x4254B4`、`0x42F699`、`0x4107C3`、`0x40C231`） |
| `0x77 变量运算` | `0x46776A` | **是**：`0x102C` + 循环内 `0x1019` | 昂贵：DLL 往返 |
| `0x78 整型变量赋值` | 表项为占位（`0x40E240`）→ 实际走对象虚函数 | 待定（很可能同样经 DLL） | 大概率昂贵 |
| `0x79 变量测试(扩展)` | 与 `0x37/0x4D/0x63` 共用 `0x472B60`（转发 `[edx+0x38]`） | 待定 | 未知 |
| `0x3F 回合测试` | 表项 `0x480612` = `xor eax,eax / ret` | — | 该表项的索引语义再次存疑（条件可能由别处判定） |

**修正后的优化口径**：

1. **优先砍 `0x77 变量运算` 与 `0x78 整型变量赋值`**（全库 10691 + 5510 条，且每条都可能带一次甚至多次 DLL 往返）——比「合并条件块」更直接。
2. 条件类（`0x05`）本身便宜，**合并条件块的收益主要来自「少执行动作体/少走块扫描」**，而不是省消息。
3. 这也解释了为什么 `S_85` 变量类占 32% 是重点：那里的 `0x77` 密集（`block 68` 就是典型：一串 `0x77` 准备参数）。
