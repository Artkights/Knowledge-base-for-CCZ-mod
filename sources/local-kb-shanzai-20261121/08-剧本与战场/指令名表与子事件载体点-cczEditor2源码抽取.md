## 已确认事实

### 一、`code[200][30]`（指令名表）

- 实际条目 **124**；首 `0:事件结束`、末 `7B:信息传送测试`。
- **id 以十六进制书写**，所以表里出现 `a`/`b`/`c`/`d`/`e`/`f`/`10`/`1a`/`1f`/`7b` 这类"字母与两位十六进制"。
- 抽取方法（可复现）：按**完整声明** `wchar_t code[200][30] = {` 定位再配平花括号。
  ⚠ **坑**：只按 `wchar_t code` 定位会**误匹配到 `code_test` / `code_face`**（同名前缀），

## 实现·使用方法

1. **要用这份对照表**：直接读 `大鲸鱼产生专用\_归档\指令名表-cczEditor2-抽取.md`（171 行，四列表）。
2. **要复现抽取**：按**完整声明**正则定位 + 花括号配平（见上"坑"）。
3. **要判某条指令能否挂子事件**：查 `code_test` 标志（非 0 = 可挂），**不要**只看 `01`。
4. **id 换算**：表内 id 是**十六进制**；与文件字节的换算**不能直接用十进制**
   （库内已记：源码 `id == 119/120/121` 对应当前命令字节 `77/78/79`）。

## 风险与边界

1. **本页是"旧工具的口径"，不是 6.6 样本的字节事实** —— 用之前必须用当前样本 `RS\*.eex` 复读交叉验证。
2. **名称是工具里的界面文字，不保证与游戏内显示一致**；且名称列自带 `id:` 前缀（源数据如此）。
3. **`code` 声明为 `[200]` 但只填 124** ⇒ 不能据此认为"id 到 199 有效"；
   实际 id 空间按 **`0..123`**（末项 `7B`）理解，与 `code_test[124]` / `code_instruct[124][13]` 的 **124** 一致。
4. **`code_instruct[124][13]`（每指令参数模板）本轮未成功解析**（2D 数组被压平，脚本已放弃）
   ⇒ 参数模板仍以库内 `LegacyScenarioReader/Writer` 的实现与 `code_instruct` 原始定义为准确来源。
5. **只读纪律**：源码在 `_外部源码\` 下，**绝不写回、绝不复制进游戏目录**（AGENTS §0.0）。

## ★★ 三方互证：`code_instruct[124][13]`（参数槽类型表）

**已成功抽取（2026-10-15 深夜，第三次尝试才对）**，并取得**三方一致**：

| 来源 | 表 | 与其它两方的关系 |
|---|---|---|
| **① 旧编辑器 v0.23 源码** | `int code_instruct[124][13]` | 每行 **13 槽**；槽值 `-1` = 该指令不用此槽，否则为**参数类型码** |
| **② Guide.cpp（攻略层解析器）** | `kParamCounts[124]` | 每条指令的**参数个数** |
| **③ 同上** | `kDwordMasks` / `kTextMasks`（各 124 项） | 哪些槽是 4 字节 / 文本 |

**互证结果（实测）**：
- **`code_instruct` 每行"有效槽位数"（≠ `-1` 的个数）与 `kParamCounts` 逐项比对 ⇒ `124/124` 完全一致** ✅
- 与 `code_test` ↔ `kCanOpenSubEvent` 的 **`124/124` 一致** 相互独立 ⇒ **两张表都被两个来源坐实**。
- **槽位值域**（去掉 `-1`）：**67 个不同值，最小 `0x2`、最大 `0x56`** ——
  这些就是**编辑器给每个参数槽指定的参数类型码**，正对应库内
  `S剧本事件读取口径-Guide.cpp.md`:40 那句「先读 u16 tag（**编辑器类型码**，例如 `0x2`/`0x4`/`0x3`/`0x23`/`0x24`/`0x2F`/`0x30`…）」。
- 产物：`大鲸鱼产生专用\_归档\code_instruct-cczEditor2-抽取.md`
  （**124 行表**：id(hex) / id(dec) / 指令名 / `kParamCounts` / 13 槽原值）。

**★ 抽取此表踩的三个坑（写下来，别重犯）**：
1. **该数组没有内层 `{}`**，是 `{ -1,-1,... }` 一长串 ⇒ 不能靠花括号抓"行"。
2. **它的值混用十六进制与十进制**（`0x5`/`0x26`/`0x35` 与 `-1`）；
   用 `-?\d+` 会把 `0x5` **拆成 `0` 和 `5` 两个数** ⇒ 实测多出 **346** 个（1958 vs 1612）。
   必须用能整体吃掉 `0x` 前缀的 token 正则：`0[xX][0-9A-Fa-f]+|-?\d+`。
3. **源文件本来每行就是 13 个值**（与 `[124][13]` 对齐），所以"逐行取 13 个"最稳；
   但**必须先把十六进制解析对**，否则"每行个数"统计全是假的（会误判成"有的行 20+ 个"）。
- ⚠ 该表的 13 个槽是**编辑器 UI 的槽位**，与 Guide.cpp 的"参数个数"一致；
  但**槽位到文件字节的映射**（tag + 载荷宽度）仍以 `Guide.cpp` 的掩码表为准（本表只给"类型码"）。
