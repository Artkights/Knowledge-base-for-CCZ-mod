# 剧本特技原生化：路线②落地设计（`0x72` 子功能 → 引擎/插件）

样本：`复刻版6.6山贼\Ekd5.exe`（SHA256 `4DA289106E4F76CCD1E06CA8B11DA1A27B1E88C333F69CBECCEAB4016FEEE450`）
姊妹页：`08-剧本与战场/剧本特技性能画像与三条落地路线.md`（写法画像 + 三条路线对比）
关联：`01-核心引擎/复刻版6.6山贼特效与扩展接口.md`（`0x4F0010/0x4F0014` 槽 + 导出审阅）

## 结论速览

- `0x72 信息传送` 的子功能 = **两条并存路径**（2026-10-24 口径修正：原句「子功能不在 EXE 里实现」**有误**——6.6 现读 `0x47D89E`→`[P1*4+0x47D8DF]` 证 EXE 侧有 38 个原生子函数）：路径 A = EXE 原生跳转表；路径 B = 指令对象虚函数先参数整理，再 `SendMessageA(hwnd, 0x102C, 子功能号, 参数…)` 交给**插件 DLL**（`ExtendData.dll`）。现行结论与分工未定项见 `03-机制详解/信息传送0x72-现行结论.md`（L1）。
- 本页后续的 `0x4670B5`/`0x464599` 链、`.text3` 函数槽表与 DLL 事实**均属路径 B**；「EXE 侧只做参数整理」只是路径 B 的形态，不代表引擎全部能力。两路径的响应分工（谁先触发、同名子功能号是否冲突）**未定**（L1 §待验证）。
- `ExtendData.dll` 16 个导出里有 `LoadVar` / `SaveVar`（⚠️**更正**：库内 `P0-007` 已证它们是**存档序列化 Mes/Effect/Meff/Forge 四类表**，**不是剧本变量**）、`GetPersonMes` / `SetPersonMes`、
  `GetPersonEffect` / `AddPersonEffect` / `ChangePersonEffect` / `GetPersonMeff` / `AddPersonMeff` / `ChangePersonMeff`、
  `GetAttack` / `GetBook` / `GetRoundChange` / `CanForge` / `ChangeDir` / `ReloadForge`；
  它还自己 `RegisterClassW` / `DefWindowProcW` / `SetWindowLongW` ——**它拥有那个收消息的窗口**。
- 所以「让剧本特技跑得动」的最省力做法是**加原生子功能**，两条落地处：
  1. **插件侧**（有 `ExtendData.dll` 源码时最优）：在 `0x102C` 消息处理里加一个子功能号，用 C++ 直接读写内存；
  2. **EXE 侧**（没有 DLL 源码时）：在 `0x72` 处理链上拦一刀（`0x464599` / `0x4670B5`），把指定子功能号转进代码洞自己处理。
  两种做法**剧本侧都不用改指令**——照旧写 `0x72`，只是子功能号用一个新的。

## 已确认事实（本轮反汇编）

### 1. `0x72` 的处理链

```
004670B5  push ebp / mov ebp,esp / push ecx
004670B9  push [ebp+8]                  ; 指令对象
004670BC  call 0x464599                 ; ← 参数整理
004670C1  push 2
004670C3  mov  ecx,[ebp+8]
004670C6  push [ecx+8]
004670C9  push 0x102C                   ; ★ 自定义窗口消息号
004670CE  mov  eax,[ebp-4]
004670D1  push [eax+0x10]               ; ★ 子功能号
004670D4  call [0x4862F4]               ; ★ = SendMessageA（IAT 槽）
004670DA  xor edx,edx / cmp eax,2 / sete dl      ; DLL 返回 2 时的特殊分支
004670E2  push edx / push [eax+8]
004670EC  call 0x463F9C                 ; 再次走消息（0x1005）做后处理
```

`0x464599` 同形：`push 2 / push [obj+8] / push 0x102C / push [obj+0x10] / call [0x4862F4]`，并按返回值 `==2` 分支。

**要点**：子功能号来自指令对象 `+0x10`，**EXE 侧看不到范围校验**，直接进消息参数 → 新的子功能号可以被透传给 DLL。

## 落地设计

### 方案 A：插件侧加子功能（推荐，若有 `ExtendData.dll` 源码）

1. 选一个**没人用的子功能号**（库内 `08-72信息传送子功能.md` 记录 0-33；先对照 `xxcs 信息传送子功能表` 确认空闲号）。
2. 在 `0x102C` 消息处理里加 `case 新号:`，参数照现有约定取（指令对象 `+8` 等）。
3. 实现里直接干重活：一次调用把「读变量 → 查单位 → 算效果 → 写变量」全做完；
   可用的引擎函数（均已在库内验证过 ABI）：
   - 当前 HP `0x41B500`（`mov eax,[ecx+0x10]`）、当前 MP `0x472840`（`movzx eax,word [ecx+0x14]`）
   - 人物记录 `[0x4CEA00] + id*0x48`（`0x4061E4`）、兵种 `+0x2B`（`0x406610`）、**兵种系 `0x40BF0C`**
   - 兵种地形记录 `0x41B7D2`、发挥值 `0x41F62A`
   - 特技/特效取值 `0x42518F`（`push 模式/叠加/装备号/个人号; mov ecx,单位; call`）
4. 剧本侧只写一条 `0x72`（新子功能号 + 参数），彻底替掉现在几十条 `0x77/0x78/0x79/0x72` 组合。

### 方案 B：EXE 侧拦截（没有 DLL 源码时）

1. 选空闲子功能号，在 `0x72` 链上挂钩：`0x4670B5`（命令处理）或 `0x464599`（参数整理）入口改 `jmp` 到代码洞。
2. 洞内：取 `[对象+0x10]`（子功能号）→ 若等于新号则自己处理并直接返回；否则**原样执行被覆盖的指令**再跳回。
3. 代码洞可用 `.text3` 尾部或 NOP 区（库内 `代码空洞与安全补丁.md` 有可用洞清单）；
   改动照既有纪律：备份 → 写补丁 txt（无 BOM + CRLF）→ 复读 → `_归档检查.py` 判定。

### 两条路共同的收益点（按 `S_85` 实测排序）

| 目标 | 现在 | 原生后 |
|---|---|---|
| `变量4` 相关判定（被测试 68 次） | 每次事件扫描走 `0x79/0x05` 条件链 | 一条 `0x72` 内联完成 |
| `变量1` 相关判定（47 次） | 同上 | 同上 |
| `block 68` 参数准备（使用者/战场号/data 序号） | 几十条 `0x77` 逐条算 | 一次调用返回三个变量 |

## 风险与边界

- **不要动 `0x486FE8` 那张表**：本轮已证明执行走对象虚函数（`call [edx+0x38]`），那张表是构造/解析侧。
- 方案 A 依赖 `ExtendData.dll` 的**源码/可重建性**；该 DLL 在文件里带 DRM 相关引用（工作区 `GearNtKe.cpp` 里有 `HookKnownImagesFor(..., GetModuleHandleW(L"ExtendData.dll"))`），**先确认是否有源码再动手**。
- 方案 B 属于改 EXE 的新代码，必须逐个特技验证，并保留回滚备份。
- 子功能号必须**先确认空闲**（库内子功能表 + 全部 `RS\*.eex` 实际用量扫描），避免撞上既有语义。

## 变量操作的真实实现（本轮新证，改变结论）

`0x77 变量运算` 的 EXE 处理器 `0x46776A` **不做算术**，它只解析操作数并把活交给插件 DLL：

```
0046776A  push ebp / mov ebp,esp / sub esp,0x78 / push ebx / push esi
0046778A  ... 从 [对象+0x1C..0x28] 取 4 个操作数字段
0046779D  mov edx,[ecx] / call [edx+0x18]                 ; 虚函数
004677B5  push 2 / push [对象+8] / push 0x102C / push [对象+0x10] / call SendMessageA
004677DA  ... 循环：循环次数 = [对象+0x14]
004677F3  lea edx,[ebp-0x60]     ; 栈上操作数缓冲
004677F6  push edx                ; ← 指针
004677F7  push [ebp-0x10]         ; ← 下标
004677FA  push 0x1019             ; ★ 消息：变量运算
00467800  push [对象+0x10]
00467806  call SendMessageA
00467826  push 0 / push [ebp-0x10] / push 0x101D / push [对象+0x10] / call SendMessageA   ; ★ 消息 0x101D
00467844  mov eax,[对象+0x18] / mov ecx,[ebp-0x10] / mov eax,[eax+ecx*4]
00467859  cmp al,0x0E / ja ...
0046785B  jmp [eax*4 + 0x467C62]        ; ★ 15 项运算符跳转表
```

要点（**结论级**）：

1. **剧本变量的存储与算术都在插件 DLL 里**：EXE 只把「操作数缓冲指针 + 下标 + 指令对象」通过 `0x1019`（运算）与 `0x101D`（读写变量，DLL 内命中 116 处）发给 DLL。
2. 因此 **每条变量操作 = 一次 `SendMessageA` 往返**。全库变量类指令 ≈ 2 万条（`0x77` 10691 + `0x78` 5510 + `0x79` 4088）。⚠️ 但**量级取决于重扫频率**：每回合扫一遍可忽略，每帧扫一遍才会卡 → 频率未测前不要把「消息往返」当作已定案的主因（见路线文档第十节的测量方案）。
3. **对三条路线的影响**：
   - **路线③（减少操作条数）从「优化写法」升级为「直接砍消息往返」** —— 收益最确定，优先级最高。
   - **路线②必须落在 DLL 侧**：批量（一次消息干完多次运算/读多个字段）才是对的形态；纯 EXE 代码洞绕不开 DLL 变量服务（EXE 自己不持有变量表）。
   - **路线①** 仍可用于战斗公式侧的原生化，但脚本接口层绕不开 DLL。

> ⚠️ 上一版本页把 `LoadVar/SaveVar` 当成剧本变量接口，已按库内 `P0-007` 更正为存档序列化。

## 附：EXE → 插件 DLL 的消息协议表（本轮扫描）

扫法：找全部 `call [0x4862F4]`（= `SendMessageA`，共 **214 处**），再按调用点前的 **push 序列**解出参数（`SendMessageA(hwnd, msg, wParam, lParam)` 的压栈顺序是 lParam→wParam→msg→hwnd，所以**倒数第 2 个 push 是消息号**）；214 处里能稳定解出 79 处。

**0x1000 段（EXE↔插件自定义段）实测明细：**

| 消息号 | 调用点 | push 数 |
|---|---|---|
| `0x1004` | `0x41C3CF`、`0x466036` | 4 / 9 |
| `0x1007` | `0x463DA4` | 9 |
| `0x1008` | `0x4661C5` | 4 |
| `0x100E` | `0x466052` | 4 |
| `0x1011` | `0x4058B7`、`0x479DC4` | 3 |
| `0x1019` | `0x465634`、`0x46C808`、`0x47A6E3` | 4 |
| `0x101B` | `0x4058DA` | 4 |
| `0x101D` | `0x41C31B` | 4 |
| `0x102C` | `0x464B86` | 4 |
| `0x1030` | `0x464E57` | 3 |

- `0x1019` / `0x101D` / `0x102C` 都在**剧本指令处理链**上（`0x465634`、`0x46C808`、`0x47A6E3`、`0x464B86` 与 `0x72`/`0x77` 处理器同区）→ 与「变量运算交给 DLL」的结论一致。
- 另有 `0x1307/0x130B/0x130C`（另一自定义段，各 3–4 次）以及大量 `0x01xx`（`0x0111` 8 次等，属 Windows 标准段）——需要时可按同法展开。
- ⚠️ 这段协议是**双向**的：DLL 侧有 116 处 `0x101D`、37 处 `0x1019` 的命中，说明 DLL 内部也在用同一批号（含它自己发给 EXE 窗口的部分）。

> 用途：路线② 若要在插件侧加能力，可优先复用 `0x1000` 段的空闲号（如 `0x1005`、`0x1006`、`0x1009`…`0x1018`、`0x101A`、`0x101C`、`0x101E`…`0x102B` 等未在本表出现的号），并保持「倒数第 2 个 push = 消息号」的调用约定。

要点：

1. **反推出的三个基址 `0x486F90` / `0x486FE8` / `0x487198` 恰好就是之前找到的注册点目标**（`0x472940` 注册 `0x486F90`、`0x47298C` 注册 `0x486FE8`、`0x42C1CB` 注册 `0x487198`）→ **「表按指令号索引（index = opcode）」这个读法得到独立印证**；但相邻副本只差 `0x58`（22 项），说明它们**不是各占满 0..0x7B 的整表**，而是**按上下文打包的片段/结构**，索引空间仍不能想当然。
2. **`0x79` 的处理器在不同副本里不一样**（`0x46B3DA` / `0x472B60` / `0x467EF3` / `0x46B671` / `0x468BD1`）→ 所以 **`0x79` 的成本与语义是「按上下文」不同的**，不能一概而论「走不走 DLL」。
3. **实践约束**：路线② 若打算「把一个空闲指令号的表项指向代码洞」，**必须处理全部 8 份副本**（或先确定目标剧本上下文用的是哪一份），否则会出现「有的场景生效、有的不生效」。
4. 反过来说，这也是**天然的实验手段**：8 份副本的差异本身就是「哪个上下文用哪套指令」的线索，可作为下一步定位「S 战场剧本用哪一份」的抓手。

## 附二：两条落地的**坐标级**可行性结论（2026-10-13 实测）

### #2-A 插件侧（`ExtendData.dll`）——**没有源码也能改**

- 工作区**没有** `ExtendData.dll` 的源码工程（只有 DRM 包装 `GearNtKe.cpp:505` 引用了它）。但该 DLL 的代码是正常可反汇编的（库内 `P0-005/006/007` 已反过导出），所以可以**用代码洞方式给它加东西**。
- 它的窗口过程坐标（`ImageBase = 0x10000000`）：

| 项 | 地址 | 证据 |
|---|---|---|
| WndProc 入口 | ≈ **`0x1001A9DB`** | `55 8B EC 81 7D 0C 60 03 00 00` = `push ebp / mov ebp,esp / cmp dword [ebp+0xC], 0x360` —— 典型的消息分派开头 |
