# 姜维传-钟会线-净版 攻击函数→机制差异审阅与移植思考（初版方案）

> 任务：审阅新引擎（姜维传-钟会线-净版 `Ekd5.exe`）从攻击函数到各类机制与 6.6 山贼的差异，思考如何移植。
> 性质：**初版框架方案**，不做深度地址级检索（具体定位/反汇编/实机由 codex 接手执行）。
> 边界：未启动游戏、未写任何游戏文件，RS/SV 未触碰。

## 一、任务与边界

- 审阅范围：从**攻击函数**出发，扩展到伤害计算、暴击/闪避/连击/集气、移动与范围、AI 与调度、特技体系、数据与资源。
- 移植思考：方向性方案，非落地补丁；具体移植须由 codex 按现行规则（特技闸门/判洞/挂点/验证）执行。
- 本方案只给框架与判断口径，不替 codex 做具体地址定位。

## 二、已掌握的对比基础（方案前提）

1. **两套独立构建体系**（前序静态对比已确认）：
   - 6.6 山贼 = 原版曹操传引擎 + 外部 `koeicda.dll` + **内存补丁**（改立即数/借洞/hook）。
   - 新引擎 = **C++ 重编译（MSVC）+ 内嵌 Lua 5 + 脚本化战斗调度 + D3D9/HLSL 渲染**。
2. **地址不可照搬**：6.6 的攻击函数地址（如物理攻击主函数 `0x43DADA`、伤害链 `0x405DE1`、物理伤害计算 `0x43BC4B` 等，库内既有语义基准）在新引擎重编译基底中**大概率不成立**，须全新定位。
3. **逻辑分层**：新引擎 AI 调度/评分走 Lua（`lua_battle_scheduler_v46.lua`），伤害计算等核心逻辑仍在 native（脚本注释自述"shared combat calculator"），攻击执行在 native——即"决策在 Lua、执行在 C++"的分层。
4. **渲染已 GPU 化**（前序审阅已确认），与机制逻辑层正交，不直接影响攻击函数对比。

## 三、审阅维度框架（codex 按此逐项对比）

每项建议给出四栏：**6.6 实现 / 新引擎实现 / 差异定性 / 移植可行性**。

### A. 攻击执行链
- 攻击入口/调度函数（6.6 基准：`0x43DADA` 物理攻击主调度）
- 攻击者能力检查、目标检查
- 攻击动作执行、动画触发
- 攻击收尾（行动状态置位、回合推进；6.6 基准：`0x442718` 唯一改行动状态处）

### B. 伤害计算链
- 物理伤害计算（上下文 `0x4927F0`、伤害数组 `ctx+0x84`；6.6 基准：`0x405DE1`、`0x43BC4B`）
- 策略伤害计算（6.6 基准：`0x497AF8+0x108+4×i`）
- 伤害应用（写 HP、战斗数据记录）
- 伤害预览 vs 真实攻击的同步关系

### C. 战斗数值机制
- 暴击、闪避、连击、反击（6.6 基准：三条路径共用 `0x405DE1`）
- 集气模式（6.6 基准：`4018=0x505EC8`，累计必触发）
- 防御/减伤、异常状态

### D. 移动与范围
- 移动寻路、可达格计算
- 攻击范围/施法范围判定
- 地形影响（6.6 基准：地形遮罩 `0x451347`→`0x4302FC`）

### E. AI 与调度
- AI 目标选择、价值评估（6.6 基准：`0x438484`/`0x4395DC`/`0x4390EF`）
- 回合调度、相位推进（6.6 基准：`phase 0x4B3D18`）
- **新引擎特色**：Lua 调度器（`lua_battle_scheduler_v46.lua` 协议版本 46）——重点核对 Lua 与 native 的边界

### F. 特技体系
- 特技号、flag、名表（6.6 基准：`0xF6` 装备挂特技、`0x96/0x97` 号位）
- 特技挂点与执行
- **重点核对**：新引擎是保留原生特技号机制，还是改为 Lua 技能/脚本体系

### G. 数据与资源
- 单位结构、战场上下文
- E5 资源加载
- 存档格式（对方声明"未改存档格式"，需核对）

## 四、差异审阅方法论（codex 执行口径）

1. **先语义后地址**：先确认新引擎是否保留 6.6 的机制语义（物理攻击、伤害、暴击、集气等概念），再定位实现——语义是否保留决定移植可行性。
2. **分层定位**：先判断机制归属 native（C++ 反汇编）还是 Lua（脚本），再深入。新引擎"决策在 Lua、执行在 native"的分层是关键，攻击函数大概率在 native。
3. **线索优先级**：英文机制命名字符串（attack/damage/crit 等）→ mangled 函数名（`_Z` 前缀）→ debug 信息/PDB 路径 → 反汇编定位入口。
4. **对照基准**：以 6.6 库内既有语义结论（物理攻击.md、伤害链反汇编、函数速查表）为语义参照，但**地址全部现读现定位，禁止照搬**。
5. **证据要求**：每项差异必须给证据（静态反汇编/字符串/实机），禁止"推测即结论"。

## 五、移植思考（方向性，非落地）

移植方向取决于目标，分三种情形：

### 情形 1：把新引擎的机制实现/优化思路移植到 6.6
- **可行性：中等**。6.6 走内存补丁，无法直接移植 C++ 源码或 Lua 调度器。
- **可借鉴**：新引擎的"逻辑分层"思路（AI 评分与伤害计算分离）、脚本化调度的组织方式、渲染 GPU 化路线（已另审）。
- **落地形态**：在 6.6 现有地址体系内，用补丁方式复刻新引擎的机制语义，而非移植代码。

### 情形 2：把 6.6 的特技/机制移植到新引擎
- **可行性：低-中**。新引擎地址体系全新，6.6 的特技挂点/洞地址不可用。
- **须重走**：判洞三步、挂点门槛、占用登记、验证四组——在新引擎基底上全新定位。
- **成本高**，仅在用户明确要在新引擎上实现 6.6 特技时才做。

### 情形 3：双向对齐机制语义（不做代码移植）
- **可行性：高（语义层）**。只对齐机制语义口径（集气、暴击、伤害公式的参数与触发逻辑），确保两边行为一致。
- **价值**：为后续跨基底对照实验、数据互通、特技互认打基础。

### 移植总原则
- **语义可移植，代码/地址不可直接移植**。
- 任何涉及特技的移植须过"新增/移植特技最高优先闸门" + 判洞/挂点/验证全流程。
- 先量化归因再动手，禁止凭印象移植。
- 移植前先确认目标基底 SHA（现读 `_样本时间线.py`），禁止写死。
