# 注入区勘察：代码洞、NOP 填充与页属性

> 目标样本 `Ekd5.exe` SHA256 `2A555B0B0D476CE1B10510406586A6F148513EDCA740BAF67CCBC422F06F0083`
> 触发：用户 2026-10-16 提供 6 份 QQ 群「注入式特技」补丁参考，问"给 Ekd5 新增类似特技"。
> 证据类型：**字节复读**（本页全部数字都是现读的；未实机、未附加调试器）。

## 结论速览

1. **本构建的注入空间【非常充足】**，此前"没有洞"的说法是**片面**的：
   * **`.code` 内有 882 处 `90`(NOP) 填充块，合计 115,898 字节**，最大 **`0x457E2E` = 5,439 字节**；
   * 次大：`0x43045F` 4,324 / `0x43425B` 3,524 / `0x42E641` 3,027 / `0x431FBE` 2,745 / `0x45FACA` 1,630 / **`0x426F17` 1,295**；
   * 而"连续 `00` 零区"在 `.code` 里确实只有 2 处（43 B / 37 B）—— **只扫 `00` 会得出错误结论**。
2. **`.text3` 零 93.6%（383,297 B，最大连续 `0x512DC2` = 127,547 B）—— 但极可能是未初始化数据节（不可执行）**
   ⇒ **不建议作为注入落点**；这很可能就是 §3.6「借洞注入必崩」的真正原因（跳进不可执行页）。
3. **首选落点 = `.code` 内的 `90` 填充块**（在可执行节内），尤其 `.code` 尾部 `0x45xxxx` 那一带。
4. **页属性必须运行时确认**（`VirtualQuery` / dump 页权限）—— 本页只做静态候选排序，**不代替运行时证据**。

## 实现·使用方法

### 判据一：判断参考补丁能否照搬（逐块比对）

对补丁里每个 `-地址 + 字节`，在本构建上求该 VA 的文件偏移并比对：
* **完全一致** ⇒ 已打过；
* **全 `90` 或全 `00`** ⇒ 是填充/零区，**可写**（但零区要另查页属性）；
* **其它** ⇒ **被真实代码/数据占用，照搬会破坏它**。

实测脚本已跑（`_tmp_et1.py` 形态）：读 PE 节表 → VA→文件偏移 → 比对 → 分类为「完全一致 / 全零或全 NOP / 占用」。

### 判据二：候选注入区的排序（静态 + 运行时两级）

| 级别 | 判据 | 说明 |
|---|---|---|
| **静态（已做）** | 落在**可执行节内** 且 是 `90` 填充或零区 且 够长 | ⇒ 得到候选清单（本页 §三/§四）|
| **运行时（必做）** | **`VirtualQuery` 读页属性，确认 `PAGE_EXECUTE_*`** | ⇒ **静态判不出页属性**，这一步不能省 |

**⇒ 推荐首选顺序（待运行时确认）**：`.code` 尾部 `0x457E2E`(5,439B) → `0x45FACA`(1,630B) → `0x456F21`(1,184B) → `0x426F17`(1,295B)
**⇒ 明确不推荐**：`.text3` 的大零区（除非常运行时确认它可执行）

## 风险与边界

1. **`90` 填充块不一定真的空闲**：它可能是编译器对齐填充（安全），
   也可能**被"基址+偏移"寻址间接读写**（则写入会静默改变行为）。**必须运行时验证**（§3.6 原话）。
2. **`.text3` 的大零区是本页最大的"诱惑"也是最大的坑** —— 127 KB 看起来完美，但页属性未知。
3. **参数点常是"实现体内部的立即数/位移"**，不是独立数据区：
   斩杀攻击的 `0x40D018` 就是 `push 0x32` 的立即数；`0x40D054` 是 `FF 75 EC` 里的**位移** `0xEC`
   （参考注释「EC 开启 / F0 不开」= 改它读 `[ebp-0x14]` 还是 `[ebp-0x10]`）
   ⇒ **这种"用改读哪个局部变量当开关"的做法依赖栈布局，极脆**，新增特技时**不要模仿**。
4. **不要用"零区空着"当"可用"**（§3.6 已写）；本页补充：**"全是 `90`"比"全是 `00`"更可信**（至少能确定它在可执行节里）。

## ★★★ 修正（2026-10-16，DSH）：`.text3` 的 127KB 零区**不是**注入空间

> **触发**：用户让挖「特技作用域」，在域 `0x42FC0C` 的反汇编里发现它把 **`0x512DC0` 当表基址**用。
> **`0x512DC0` 正是本页 §三 列出的 `.text3` **最大零区**（`0x512DC2` = 127,547 B）**的起点前 2 字节**。

### 一、实测：`0x512DC0` 是一张**活跃的数据表**（不是空洞）
```asm
0x42FC13  mov  edx, 0x512DC0        ; 表基址
0x42FC18  cmp  byte [edx], 0xFF     ; ┐ [0]==FF 且
0x42FC1B  jne  0x42FC26             ; │
0x42FC1D  cmp  byte [edx+1], 0xFF   ; │ [1]==FF
0x42FC21  je   0x42FC88             ; ┘ ⇒ 【表空，直接退出】
0x42FC23  add  edx, 2               ; 跳过 2 字节表头
0x42FC29  mov  al, [edx+1]          ; 项 +1 = 计数器（0=无效；>99 也跳过）
0x42FC37  movzx eax, word [edx+2]   ; 项 +2 = id(WORD) ⇒ call 0x43E4D6 解析
0x42FC7B  dec  byte [edx+1]         ; 命中则计数器 −1
0x42FC83  add  edx, 4               ; 步长 4 字节
```

**⇒ 表现读字节**：`0x512DC0: FF FF 00 00 00 00 …`（**`FF FF` = 空表标记**）
**⇒ 其前有 1934 字节的 `00`** ⇒ 它是**独立表的起点**
**⇒ 表的容量**：零区长 127,547 B ⇒ **可用 31,886 项（4 字节/项）+ 2 字节表头**
**⇒ 下一个非零 = `0x531FFD`，字节 `65 6E 64 00` = 字符串 `"end"`** ⇒ 该区尾部是**字符串常量**

### 二、配套函数（都在同一族）
| 地址 | 作用 |
|---|---|
| `0x42FC0C` | **遍历表**：逐项按计数器/id 处理，命中则 `dec` 计数器 |
| `0x42FBE1` | **查询**：`call 0x436F16` 查 id ⇒ 命中且计数器 ≠ 0 时 **返回项 `+0`** |
| `0x42FC8C` | **删除**：定位项后 `call 0x42FCE4`（参数 2 或 4）|
| `0x42FCE4` | **删除辅助（memmove 型）**：`call 0x40BB78` 取表尾 ⇒ `末 − 目标` = 要挪字节数 ⇒ 前移 |

### 四、★★★ 得到「判洞三步」（应写入 §3.6 铁律）
> **零区空着 ≠ 运行时可用；而且"连续零字节"本身可能是【数据表的预留容量】。**
