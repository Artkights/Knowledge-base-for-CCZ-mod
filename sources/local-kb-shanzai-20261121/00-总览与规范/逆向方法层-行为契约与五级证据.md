## 结论速览

1. **先写行为契约，再碰代码**：触发条件 / 对象 / 输入 / 预期输出 / 必须保留的原生分支 / 边界场景，
   六项写不全就不许动手；把每条标成**已确认 / 推断 / 待查**。
2. **证据分五级且不可越级替代**：静态检查 → 应用后文件读回 → 运行时读回 → 受控启动与路径观察 → 游戏内验收。
   "补丁已应用""没报错""对话框消失"**都不是**任何一级的证据。
3. **只报实际做到的层级**。组合两个各自验收过的补丁，不等于组合已验收；要看是否改动共享写入 / 共用调用路径。
4. **断点命中只证明"执行到该处"**；`hit_count` 增加**不代表条件成立**（x64dbg 原生命中计数无条件递增后才求值 break condition）。
5. **补丁字节必须有唯一生成源**，写入前断言前像/范围/长度/不重叠，写入后从**磁盘文件**逐字节复读——
   本工作区已把这条固化为 `_dsh写锁.py` 的 `safe_write_exe()`（备份 + 复读比对 + 审计行）。
6. **收尾即落盘**：结论、证据层级、未覆盖分支、回滚位置四件事一起写，缺"未覆盖边界"的结论不得进库当定论。

### 二、五级证据分层（越级即不合格）

| 级 | 证明什么 | 本工作区对应手段 | 不能证明什么 |
|---|---|---|---|
| 1 静态检查 | 生成字节、指令边界、跳转目标、前像断言、节/模块不重叠 | `_dsh反汇编工作台.py`、`exe_bytes` | 程序会跑、会生效 |
| 2 应用 / 文件读回 | 磁盘文件真的变成预期字节 | `_dsh写锁.py` 写后复读比对 + `_改动总账.py` | 内存里也是这个字节、运行时走这条分支 |
| 3 运行时读回 | 进程内该地址当前字节/值正确 | x32dbg MCP `memory_read`、采样脚本 | 该分支**执行过** |
| 4 受控启动 + 路径观察 | 目标能起、目标函数/分支被执行 | 读档入口 `_自动读档进战场.py --go-safe`、x32dbg 断点 + 命中读数 | 玩家看到的效果 |
| 5 游戏内验收 + 回归 | 契约里的成功/失败/边界/原生行为都对 | `_42结束回合.py --probe`、自动战斗、`--ratio` 保命验收 | 未跑的场景 |

**硬规则**：断点命中 = 只到第 4 级；"值符合预期" = 只是瞬时状态；**集气模式相关战斗结论必须在 `4018=1` 前提下取得**（`AGENTS.md` 测试前提）。

### 三、x32dbg 操作纪律（吸收 `x32dbg-debugging` skill + 本工作区 §6/§7）

1. **架构匹配**：本样本 `Ekd5.exe` 是 **PE32 / x86 ⇒ 固定用 `x32dbg`**（x64dbg 无法附加 32 位进程，不存在"更好的选择"）。
2. **先进战场再附加**，别让调试器当启动器；地址一律用**模块基址 + RVA** 核对，旧构建绝对地址不得直接使用。
3. **★ 条件断点陷阱（本工作区新增认知）**：x64dbg **原生**软件条件断点在命中时**无条件先递增命中计数**，再求值 break condition（默认 1，任何非零值都暂停）；
   ⇒ **适配器显示的命中次数增加，不能说明条件成立、也不能说明已暂停**。
   要分别核对四件事：断点状态 / 条件表达式与进制 / 实际暂停状态 / 适配器如何解释计数。
   条件可能在其他位置成立时，应改用**条件跟踪**而不是条件断点。
4. **★ 先放行再叫人**（§7 死规则）：设完断点必须循环 `debug_run` 到 `state == running` 且 `Ekd5.Responding == True`，
   打印"✓ 已恢复可操作"，**然后才**叫用户操作；工具 `_先放行再叫人.py`。
5. **收尾顺序固定**：`breakpoint_delete_all` → `debug_stop`（反了会留入口断点）；一次不超过几个关键断点。
6. **运行时内存写入**：只在目标/地址/长度/预期值全部明确且可恢复时做；立即读回复比；结束前还原或重启到干净基线。
   **运行时写入 ≠ 磁盘补丁 ≠ 重启后仍生效**——这三件事必须分开报告。
7. **命中后的取证顺序**：进程/模块/线程/当前地址 → 前后控制流（确认停在预想分支，而非相邻准备/派发/清理）→ 寄存器+标志+栈+内存范围 → 对比命中前后并追**写入者与消费者** → 采样完再恢复执行。
8. **附加会让进程退出后变僵尸**（`HasExited=True` 仍占进程表）⇒ 写 `Ekd5.exe` 前必须先关 x32dbg。

### 四、Win32 控件追踪（吸收 `win32-control-tracing`，与本工作区 §2.5 第 7 条互补）

- **先确定要追什么行为**：点击/输入、文字刷新、状态（颜色/可见性/启用）是**三条不同路径**，不要互相替代。
- **控件身份三件套分开**：资源编号 ≠ 控件标识符（ID）≠ 运行时 `HWND`；截图上的文字只能当线索。
- 有对话框模板（资源）时记录模板里的类/初始文字/ID，再找 `DialogBoxParam`/`CreateDialogParam` 的回调；
  **没有资源模板不能单独证明界面是自绘的**（可能是内存模板 / 运行时创建子窗口 / 注册窗口类）。
- 静态控件设了 `SS_NOTIFY` 也会经 `WM_COMMAND` 发 `STN_CLICKED`；`WM_COMMAND` 要分 `LOWORD(wParam)`=ID、`HIWORD(wParam)`=通知码、`lParam`=控件句柄；
  **菜单命令与加速键用同一消息但参数含义不同**。
- 文字刷新走 `SetDlgItemText`/`SetWindowText`/`WM_SETTEXT` 或自绘/所有者绘制路径。
- **本工作区已付学费的三条**（与本 skill 同源结论）：
  ① 自绘窗口不认 `PostMessage`/`SendMessage` 鼠标消息，标题页按钮**必须先悬停 ≥0.5s 再物理点击**；
  ② 游戏只在**前台**收鼠标 ⇒ 点之前显式置前；
  ③ **`WM_COMMAND(IDOK)` 只关框、不完成业务动作**（结束回合实测无效）⇒ 用权威实现里的**物理点击**（`_42结束回合.py:click_yes`）。
- **坐标系先量再用**：同一窗口 DPI 未感知/已感知差 **1.25 倍**（实测客户区 624×440 vs 780），先打印两视角 `GetWindowRect/GetClientRect/ClientToScreen(0,0)` 再选口径。

### 为什么（2026-10-15 实例，同一目标两种代价）

- **先反汇编**：花数轮命令才拿到导出表 → IAT 映射 → 猜 API 名 → 拼出 `pow(2, v/10)` 的一半证据，且仍有"倍率公式/口径"要推。
- **后读源码**（用户点出位置后）：**一次读取**就得到公式原文、断言规格（`GearTests.cpp`）、六钩子表、游戏字段布局表与三种模式，
  且**测试文件本身就是可执行规格**（`SpeedMultiplier(0/10/20/-10) == 1/2/4/0.5`）。
- ⇒ **源码级证据 > 反汇编推断**；反汇编仍不可替代的场合：**没有源码时**、或**要确认"磁盘上的二进制真的等于源码编译结果"**（防源码与产物不一致）。

### 与本方法层"五级证据"的关系

- 源码 = **静态证据（第 1 级）的加强形态**，可直接给出**公式与字段语义**；
- 但**不能**据此断言"运行时确实按源码执行" ⇒ 仍须用**第 3 级（运行时读回）/第 4 级（受控启动路径观察）**验收。
- ⇒ 正确顺序：**源码给公式与字段 → 运行时读回给"确实生效"**。
