## 已确认事实

### 战场 UI 操作规则

- 点击我军单位后，单位周围的紫色格子表示该单位当前可以移动到的位置。
- 再次点击紫色格子，且目标格子没有单位占据时，单位会移动到该位置。
- 点击我军单位后，单位周围的红色框格子表示该单位当前攻击范围。
- 攻击必须满足目标敌军位于红色框攻击范围内。
- 除二次行动、再次移动等特技外，人物一回合通常只能执行一次“移动 + 行动”。
- 移动是改变自身位置，可不执行；行动是攻击敌军、释放策略、使用道具或待命。
- 移动必须发生在行动之前。完成行动后，该单位本回合不能再次操作。
- 已完成行动的我军单位形象会从高亮变为灰暗；点击该单位会触发提示：“已经行动完毕。”
- 执行物理攻击的人工流程：
  1. 点击我军单位。
  2. 若敌军已经在红色框内，不移动单位。
  3. 若敌军不在红色框内，先选择一个无人占据的紫色格子移动，使目标进入攻击范围。
  4. 点击右侧最上方“攻击”指令。
  5. 点击红色框范围内的敌军目标。
  6. 等待动画、反击、功勋/经验提示全部结束后停止操作。

### 调试采证规则

- 调试侧默认不主动暂停游戏，避免 x32dbg 令 `Ekd5.exe` 窗口无响应。
- 常驻自动监控优先使用只读 `ReadProcessMemory` 读取 `Ekd5.exe`，不设置断点、不暂停游戏、不写游戏文件。
- x32dbg MCP bridge 在线时，自动监控器只额外记录 bridge 状态和暂停点证据；断点仍需单独明确启用。
- 需要暂停、设置断点或写断点时，必须提前告知操作者，并在设置完后立即继续运行。
- 一次只采一个动作。动作完成后先回复固定短语，再由调试侧抓后快照。
- 快照优先范围：
  - `char_data_004A3E77`：历史报告沿用的旧名称，实际为策略记录区；后续报告应改名为 `strategy_records_004A3E77`。
  - 人物运行时记录：先读 `[004CEA00]` 取得动态基址，再按 Data 号和 `48H` 步长采样。
  - `unit_array_004A7B20`：战术单位数组。
  - `battle_globals_00490000`：战斗相关全局区。
  - 运行时 heap 只作辅助；读取失败或无差异时不得作为否定证据。

## 实现/使用方法

### 常驻自动监控协议

1. 用 `工具整合包\MCP配置\start-x32dbg-6.5.ps1` 打开正式 6.5 未加密基底；脚本默认按目标 EXE 哈希定位正式基底，并排除 `CCZModStudio_TestCopies`。
2. 启动监控：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File "工具整合包\MCP配置\watch-6.5-battle-events.ps1" -DurationSec 1800 -PollIntervalMs 500 -Label "merit-auto" -SaveMemoryOnEvent
   ```

3. 用户正常游玩，不必每一步停下来汇报。
4. 监控器自动输出到 `CCZModStudio_Reports\DebugEvidence\merit-auto-YYYYMMDD-HHMMSS`：
   - `events.md`：人工阅读流水。
   - `events.jsonl`：单位差分事件，适合后续脚本分析。
   - `summary.json`：轮询次数、事件数、错误数。
   - `event-0001/` 等：启用 `-SaveMemoryOnEvent` 时保存事件瞬间关键内存块。
5. 若需要函数调用栈，再围绕已发现的事件时间点开启有限断点或写断点复核。

### 人类操作员协议

1. 调试侧说明当前目标动作和停止条件。
2. 调试侧抓前快照。
3. 用户只执行该动作，不额外选中其它单位、不推进其它回合。
4. 用户回复动作完成。
5. 调试侧抓后快照并做 diff。
6. 调试侧将 UI 观察、内存差分、候选地址和下一步写断点计划写入证据。

### 战场状态读取口径

- 战术单位数组基址：`004A7B20`。
- 战术单位 stride：`30`。
- 当前已用字段：
  - `unit+00..+01`：Data 号；`FFFF` 表示空槽。
  - `unit+04`：出场/显示编号载体，不是 Data 号。
  - `unit+05`：阵营候选，`0=我军`、`1=友军`、`2=敌军`。
  - `unit+06/+07`：战场坐标候选。
  - `unit+0D`：行动状态。
  - `unit+10`：当前 HP。
  - `unit+14`：当前 MP 候选。
- 战场单位身份必须以 `unit+00` 的 16 位 Data 号、当前人物动态基址、游戏画面和剧情上下文交叉确认；不能把 `unit+04` 映射成人物名。

## 风险与边界

- 战场画面中的颜色、按钮和提示可用于操作，但不能单独作为内存结构结论。
- Data 号、战场编号和画面角色名的互转必须另行验证；在完成编号体系闭环前，操作指令应使用画面可确认的人物名、位置和按钮，而不是只使用内存推断的人名。
- 当前还没有稳定的屏幕坐标自动点击器。自动化前必须先把单位坐标、镜头偏移、菜单状态和按钮位置都转成可校验状态。
- x32dbg 的暂停会让游戏窗口无响应；没有必要时优先使用运行中快照。
- 人工操作必须避免连做多个动作，否则 diff 会混入敌军行动、UI 刷新、回合状态和临时文本。

### 2026-06-11 阶段性自动化能力评估

经过测验1和测验1续的长时间采样，当前可以实现的是“只读状态识别 + 半自动调试采证 + 有限操作辅助”，还不能称为稳定的“无人战场操控器”。

已具备的能力：

- 可只读识别战场单位数组：`004A7B20`、stride `30`、当前 HP `unit+10`。
- 可通过 `004927F0` 读取当前攻击者、目标、伤害缓存、暴击、连击/循环和反击/嵌套行动标志。
- 可用 `00405AD5 -> 0043F6DB -> 0043F70C` 稳定观测物理伤害应用和 HP 写入。
- 可区分玩家主动攻击、友军/敌军自动阶段和反击链的主要调用栈形态。
- 可在曹操主动攻击和部分反击/自动阶段样本中观测个人 EXP、武器 EXP、防具 EXP 的战斗上下文缓存写入。
- 可通过人类操作员执行动作，调试侧自动记录断点、调用栈、内存和知识库证据。

尚不能直接全自动操控的原因：

- 没有闭环的“屏幕格坐标 <-> 战场格坐标 <-> 当前镜头偏移”映射；移动和目标点击仍依赖人工画面判断。
- 移动函数和坐标写入只有候选链，缺少“只移动不攻击”的写断点闭环。
- 当前没有可靠识别 UI 子状态的内存状态机：单位已选中、紫色移动格显示、红色攻击范围、命令菜单、攻击目标选择、动画中、弹窗等待等仍未全部内存化。
- 攻击按钮、结束回合弹窗和策略/道具菜单的按钮坐标虽有人工经验，但缺少跨窗口大小和不同 UI 状态的防误点校验。
- 连击判定、命中/闪避/格挡、反击谓词、策略结算、行动结束和回合开始仍有关键地址未闭环，无法安全地把战斗 AI 和 Hook 注入做成通用规则。
- 五维功勋实际存储结构仍未定位；旧候选已证伪或改判，不能用功勋作为自动化奖励反馈。

当前可交付的自动化形态：

| 等级 | 可行性 | 说明 |
|------|--------|------|
| 只读战场监控 | 可实现 | 自动读取单位、HP、阶段差分、伤害事件和断点证据 |
| 人机协同采证 | 可实现 | 用户操作，调试侧自动下断点、采集、归纳、落库 |
| 有限脚本辅助点击 | 局部可做 | 只适合固定窗口、固定关卡、固定状态；必须带防误点门禁 |
| 内部函数级操控 | 尚未实现 | 需要定位战场 action dispatcher、移动/攻击 ABI 和 UI/脚本状态变量 |
| 通用无人战场 AI | 尚不可交付 | 还缺状态机、路径规划、目标选择、输入可靠性、异常恢复和跨版本定位 |

下一阶段最小闭环：

1. 用单独样本闭环移动坐标写入：移动前后只做移动，不攻击。
2. 建立内存化 UI 状态机：空闲、选中、菜单、目标选择、动画、弹窗、自动阶段。
3. 固定 640x440 客户区下做有限点击器，并把每次点击前后的单位数组和 UI 状态作为门禁。
4. 对 `on_action_end`、`on_turn_start`、`on_hit_check`、`on_double_attack_check`、`on_counter_check` 补齐成功/失败样本。
5. 在能可靠回到同一存档/同一战场状态后，再考虑无人批量采样和自动战斗策略。

### 2026-06-11 测验1调试方法沉淀：跨版本/跨游戏复用流程

本流程来自曹操 `unit[0]` 攻击黄巾兵 `unit[77]` 并触发连击的实机调试闭环。它的可复用价值不在固定地址，而在采证顺序。

1. 先定位运行时实体数组，而不是先找公式。用内存快照/差分确认单位数组基址、单位步长、HP 字段和至少两个可画面确认的实体。
2. 对真实变化字段下硬件写断点。本次是目标 HP 地址 `004A89A0`，命中后才确认最终写入指令 `0043F70C`。
3. 从写入点向上追调用栈。本次闭环为 `0043F70C <- 0043F6DB <- 00405ADC <- 00405966 <- 00418330`。
4. 再把调用栈与用户动作绑定。本次动作入口闭环到 `0043DF0A -> 0043DADA`，且 `ECX=004A7B20` 对应曹操。
5. 最后区分“结果应用”和“结果生成”。`00405966` 能解释为什么连击会两次写 HP，但不能替代连击判定或伤害公式。

跨版本/跨游戏迁移时不要照搬绝对地址，应迁移以下锚点：

- 实体数组：基址、stride、实体有效标志、画面可验证身份。
- 字段锚点：当前 HP、坐标、阵营、行动状态等最容易由画面行为确认的字段。
- 写入闭环：硬件写断点、写入指令、setter、上层结果循环。
- 动作闭环：玩家操作入口、命令分支、核心调度函数。
- 结果缓冲：伤害段数、目标编号、旧值/新值、动画/事件派发。

禁止外推：

- 未做移动样本时，不得把坐标候选字段或攻击链函数写成移动函数。
- 只命中 HP 写入时，不得把 setter 或结果循环写成伤害公式。
- 只观察到两次 HP 写入时，不得把“连击判定函数”写成已确认；必须追到第二段伤害记录的生成点。
- UI 事件、动画、事件派发和状态恢复函数不能因为出现在调用栈附近就标记为 HP 写入点。

### 2026-10-13 无人值守验证复现记录：驱动不了 UI，但可"受控执行"补丁代码

本轮目标：在没有人在电脑前的情况下验证「防御暴击 0x24」补丁（见 [暴击](../03-机制详解/暴击.md)）。结论与可复用手法：

**一、UI 自动化（本次再次确认走不通，与 `大鲸鱼产生专用/_引擎知识库.md` 6.4 的结论一致）**

- 不要用 `GetDC(hwnd)` 截图：DirectDraw 显示面下它给出的是**陈旧帧**（同一张标题图重复返回），会误判游戏状态。要抓"实际显示"必须用屏幕 DC（`GetDC(0)` + `BitBlt` 窗口矩形）。
- 窗口自身带菜单栏/工具栏（`文件/功能/情报/扩展系统/加速补丁/简易攻略`），`GetClientRect`+`ClientToScreen` 得到的客户区原点才是点击坐标系；但真实画面存在缩放，靠陈旧帧量出的菜单坐标会点偏。
- `keybd_event` / `SetCursorPos`+`mouse_event` 对该游戏的标题菜单**均无效**（Enter/Space/方向键/点击都不改变状态）；同一套输入对标准 Win32 对话框（`#32770`，如「环境设定」）**有效**（ESC 可关闭）。
- **判断游戏状态的可靠判据是内存而不是画面**：`0x4B422C`/`0x4B422D`（战场宽高，非 0 即已进战场）、`0x4A7B20+n*0x30`（单位表，`data_id=0xFFFF` 表示空）、`0x497AF8`（策略上下文）。用 `ReadProcessMemory`（`PROCESS_VM_READ`）即可无副作用轮询，不需要附加调试器。

**二、受控执行补丁代码（本次成功，推荐手法）**

在没有战斗、无法触发真实暴击时，仍可**在真实进程里执行补丁的代码字节**来验证算术：

1. `debug_attach_pid` 附加 → `debug_pause`（**必须暂停**，否则 `memory_write`/`register_set` 一律返回 `Debugger is not paused`）。
2. `memory_allocate` 取一块暂存区，摆好补丁需要的"帧"：`[ebp-0x28]`=伤害槽指针、`[ebp-0x24]`=暴击标记、`[ebp-0x0C]`=上下文；伤害槽内写入输入值。
3. 把代码洞的**算术段**（去掉 `call`、末尾换 `int3`）写进目标地址，`register_set` 设好 `ebp/esp/eax/eip`，再 `debug_step_into` 逐步执行。
4. 读回伤害槽即为结果；跑完**必须把原补丁字节写回并用 `memory_read` 校验**。
5. 坑：x64dbg 的"当前线程"会在多线程间漂移（游戏有 ~20 个线程），单步可能单到别的线程上；`thread_suspend` 挂起其它线程可减少漂移，但最可靠的是**每步重新读一次当前线程 EIP**，并用寄存器值（而非仅 EIP）判断是否真的执行到位。

#### K-2. 2026-10-13 补：本轮静态走查抓到的 6 个真坑（任何后续自动化脚本都会踩）

写"用 Python 驱动这个 32 位游戏"的脚本时，下面各条**必须**照做；它们都不是臆测，是本轮在源码里逐句核出来的（前 4 条自己核出，后 2 条由一次独立的静态复核抓出）：

1. **句柄别按默认 `c_int` 拿**：`OpenProcess` / `CreateToolhelp32Snapshot` / `GetDlgItem` / `WindowFromPoint` / `GetForegroundWindow` / `GetParent` / `VirtualAllocEx` 的返回值要显式 `restype = ctypes.c_void_p`，否则 64 位 Python 下会**静默截断**成 32 位（写内存可能"看起来成功"却写错进程）。
   ⚠️ 反过来：**凡是第一个参数是进程句柄的 API 必须设 `argtypes`**（否则 Python int → `c_void_p` 会抛 `TypeError`）；而 `SendMessageW` 之类**不要设 argtypes**，因为设了以后 `lParam` 传 Python int（如 `LVM_GETITEMRECT` 的缓冲区地址）也会抛 `TypeError`。
2. **句柄不能再直接 `'%d' % hwnd`**：一旦 `restype = c_void_p`，`hwnd` 就是 `c_void_p` 对象，`%d` 会抛 `TypeError: %d format: a real number is required, not c_void_p`（在 selftest 里就会炸）。一律 `int(hwnd)` 再格式化。
3. **`ShowWindow` 的常量别记错**：`SW_MINIMIZE = 6`、`SW_RESTORE = 9`。本轮在旧脚本里发现写成 `ShowWindow(h, 9)` 当"最小化"用 ✗ —— 那其实是**还原**，会把挡在游戏前面的窗口**弹到最前**，正好和"清障"的目的相反。
4. **`IsHungAppWindow` 的所属 DLL 有分歧**：本工作区旧工具从 `kernel32` 调用**成功过**，Windows 文档写的是 `user32`。⇒ 别赌，两个都试、都失败就跳过（包在 try/except 里）。
5. **`R()` 之类返回的是 `bytes`，不能直接 `%X`/`%d`**：`'%X' % b'\x14'` 抛 `TypeError: %X format: an integer is required, not bytes`。读单字节要 `int.from_bytes(...)` 或取 `[0]`。本轮在自检和战场识别两处都踩到（自检第一屏就崩）。
6. **模块级 `def`/常量的顺序要自己核一遍**：本轮"自检块"调用了一个定义在它**下面**的 `kind()` ⇒ `NameError`，`_pid` 也是先被函数引用、后在主流程才赋值。**没有执行权限时，这类 use-before-def 只能靠独立的静态复核抓**（本轮正是让另一个 agent 纯读文件复核才发现的）。
7. **`%s` 对元组的写法有个隐藏雷**：`'… %s …' % (a, b, c, d)` 是"1 个占位符对 4 个实参"⇒ `TypeError: not all arguments converted`；要打印元组必须写成 `% ((a, b, c, d),)`。本轮真的在"主窗口矩形异常"那条日志上踩到，而且它在主循环里**没有 try** ⇒ 一旦窗口被最小化（`w<=200`）就会终止脚本。**同一行的编辑还要小心删除换行**：本轮一次修复就误把 `got = False` 并到了上一行，制造出一个语法错误 —— 这类"编辑事故"同样只能靠复核抓，所以**改完必须再静态核一遍**。

另外本轮把**读档行的定位**从"列表左边+60 / 上边+7+行号×16"的估算，升级为 `_快速进战场2.py` 的 **`LVM_GETITEMRECT`（`0x100E`，`LVIR_BOUNDS=0`）真实行矩形**：在被控进程 `VirtualAllocEx` 64 字节 → 写入 `0` → 发消息 → 读回 4 个 int（客户区坐标）→ 加上列表窗口原点得屏幕坐标。估算法在行高/字体/DPI 一变就点偏；真实矩形不会。

#### K-3. ★读数口径纠正：`0x4927F0` 是**基址**，不是指针（旧脚本照抄会读到垃圾）

本页 F/G 段与旧监视器把暴击标志写成 `[004927F0]+604`，容易被读成"先解引用 `[0x4927F0]` 拿到 ctx，再 `+604`"。**这是错的**：

- 正确写法：`ctx = 0x4927F0`（**常量**），字段 = `ctx + 0x604`（暴击）、`ctx + 0x00/+0x01`（当前攻击者/目标战场编号）、`ctx + 0x0C`（攻击者战术单位指针）、`ctx + 0x84`（HP 伤害数组首元素）。
- 证据：① 静态多处 `mov ecx, 4927F0` 直接把该地址当结构基址；② [地址语义与Hook契约](../01-核心引擎/地址语义与Hook契约.md) 登记 `004927F0` = `battle_context_base`；③ 静置的 `_防御暴击验证.py`（`_冻结证据_20261024/防御暴击0x24/`）是从 `0x405EF5` 读 `dword:[ebp-0x28]`（伤害槽指针）与 `[0x4927F0+604]`；④ **反证**：`_战场监视2.py` 写 `ctx = rd32(0x4927F0)` 把内容当指针，实测读到 `0x00005500`（`_战场监视日志.txt` 首行 `结算上下文=0x00005500`），根本不是地址。
- ⇒ 凡是要读暴击标志/攻击者/目标的自动化脚本，**直接读 `0x4927F0 + 偏移`**；已经写成 `rd32(0x4927F0)` 的旧脚本（`_战场监视2.py`、`_自动战斗2.py`）属于历史错误，别照抄。纠正记录见 [错误知识纠正台账](../90-来源归档/复刻版6.6山贼错误知识纠正台账.md)。

#### K-4. 2026-10-13 补：怎么"当场判定"暴击归因对不对（不靠调试器）

只看 `+604==1` 是**不可证伪**的。本轮给工具加了两条自证机制，实测时按这两条读日志即可：

1. **伤害自校验**：同一帧里，`ctx[+84]`（HP 伤害数组首元素）应当等于该目标的 HP 差分。
   - 相等 ⇒ 这一帧的上下文**就是**这段伤害的上下文，`+604` 可以采信；
   - 不等 ⇒ 说明上下文已经切到下一段（穿透/连击多段攻击时**属预期**），该段暴击**不可采信**。工具会打印 `⚠ 伤害对不上：HP差分=… 但 ctx[+84]=…`。
2. **取值域自校验**：`+604` 只可能是 `0/1`（知识库口径"0=无，非0=是"）。若日志出现 `⚠ 暴击标志 +604=…异常`，说明 `0x4927F0` 口径或本 SHA 的上下文基址还要再纠 —— **不要在异常值上继续做结论**。
3. **取证行**：每次伤害事件都会跟一行 `ctx: 攻击者slot=… 目标slot=… 伤害槽[+84]=… 目标数组[+10]=… 暴击=… 连击=… 反击=…`，把"当时的原始状态"留在日志里，便于事后复核与二次分析（也便于在没有调试器的前提下重建现场）。
4. **样本量策略**：要判"暴击 / 非暴击"的比例（进而反推减伤），必须有**同一个目标**的两类样本 ⇒ 工具把我方 HP 保底阈值设为 `各人基准血量 × 2/3`（不低于 400），
   让被观测单位能持续挨打；⚠️ 触发过保底的那一段会被标记并从比例统计里剔除，因为它之后被我们改写过血量。

- ⚠️ 战场里引擎会自己把该字节在 `1↔3` 之间反复刷（监控日志每秒都在跳），所以：**别把 `≠0` 当异常去反复重写**（我早期 11 秒写了 20 多次、20 分钟写 60 多次，属干扰），只在 `==0` 且**节流 5 秒**时补写。

**③ 点「是」永远不读档 → 根因是我自己的 `front()` 注入了 ALT**

- 知识库 I 段第 4 条早就写着"**确认框出现后按 ALT = 取消**"，而我的 `front()`（每次点前抢前台）里带 `keybd_event(0x12)` ⇒ **每次点「是」之前先按了一次 ALT**，把确认框取消掉。这就是"点击位置没错、按钮也被按下（`BM_GETSTATE=0x108`）、框也关了，却进不去"的原因。
- ⇒ 抢前台**绝不注入任何按键**，只用 API（`BringWindowToTop/SetForegroundWindow/SetFocus`）；或干脆**先真实点一下标题栏**把窗口点成前台（用户建议，实测 `GetForegroundWindow()` 核对通过）。

**④ 暴击是"预演"写入的，HP 扣减要等动画播完（实测差 11 秒）**

**⑥ 修掉 ALT 之后的新发现：读档一旦真正开始，游戏进程就退出（=用户说的"闪退"）**

- 修掉 `front()` 的 ALT 注入后，流程变成：`主窗口激活(前台核对通过) → 读档窗激活 → 双击第0行 → 确认框激活 → 点「是」` ⇒ **3 秒内主窗口消失、进程退出**（`宽=0`）。
- 关键判读：**读档是由「点『是』」这一下真正触发的**——
  - 修 ALT 之前：读档**根本没启动**（对话框被 ALT 取消/关闭，页面停在标题，所以"怎么点都不进"）；
  - 修 ALT 之后：读档**启动了**，然后在初始化阶段**进程退出**。
- **这就是用户报的"闪退"的可复现形态**：不是访问违例（`%LOCALAPPDATA%\CrashDumps` 无新转储、Windows 应用程序日志无错误事件），而是**干净退出**。
